# mo-shu 学习规划（借鉴 webnovel-writer）

> 依据：`docs/webnovel-writer-研究.md`（五轮研究存档）。本文件是把可借鉴点转化为 mo-shu 实施计划的唯一入口——每条注明学什么、落点、成本、验收方式。
> 日期：2026-08-19。状态：规划（未开工）。

---

## 学习总纲（四条逻辑）

1. **学"确定性纪律"，不学"记忆更多"**——零 token 机检 / AI 语义 / 作者定稿的三分法，是它最强护城河
2. **学"防呆与自愈"，不学"流程更重"**——半提交探测/健康检查/重试预算，而不是批次状态机
3. **learn 只学"带筛选的注入"**——它的 project_memory 只写不筛=死数据（自身教训），我们做必须带细纲命中筛选
4. **真源哲学不动**——mo-shu 的"单一权威 + check 逐字校验"已解决 v6 投影漂移问题（v7 用 git 解决的同一问题），改真源成本巨大且无收益

## 一、工程拼图（v1.1.3，~400 行零依赖）——🟢 第一批

### L1 每章 Git 自动备份
- **学什么**：追踪事务成功后 `git commit + tag chNNNN`（消息 `Chapter {N}: {title}`，title 经 sanitize 防注入）；rollback 用前滚式恢复提交（不丢历史）；create-branch 从任意章建平行分支；无 git 环境降级本地快照（保留最近 10 份）
- **落点**：workflow-chapter.md 步骤 12（追踪事务）之后追加"备份"步骤；新脚本 `scripts/backup_chapter.py`（或并入 tracking_commit.py 子命令）
- **成本**：低（参考 backup_manager.py 逻辑）
- **验收**：写一章 → 自动生成 git tag；手动改坏正文 → rollback 恢复；无 git 目录 → 快照目录生效
- **风险**：需 git 环境；`.moshu-review/`、临时文件进 .gitignore；仓库需初始化（无 git 时降级路径兜底）

### L2 半提交探测（probeCommitAfterError）
- **学什么**：commit 报错后用 parent/tree/message 三件套遍历 rev-list 判三态（committed / not-committed / unknown），unknown 宁停不删——防"git 偶发返回码 ≠ 未提交"导致的重复提交
- **落点**：L1 备份脚本内部（captureCommitExpectation + probeCommitAfterError）
- **成本**：~60 行
- **验收**：模拟 commit 中途失败 → 不产生重复 tag/提交

### L3 git 人话化 + 健康检查
- **学什么**：陈旧锁 60s 阈值 + 删除前二次 stat 防 TOCTOU；半提交 stash；.git 损坏只指引不自动动；全中文输出（作者永不看英文报错）
- **落点**：L1 前置检查（git-health）
- **成本**：低
- **验收**：手动放一个陈旧 index.lock → 自愈提示；正常场景无感

### L4 机检"阻断 vs 候选"分层（字符级零依赖）
- **学什么**：机检 = **6 阻断 + 4 候选**（v7 实际构成；候选永不拦截）——阻断：字数±30%（硬边界；流程层另有 90%/110% 动作阈）/ 禁词 / 禁句式 / **复读（字符级 6-gram ≥3）** / 必填字段 / 条目变动形式；候选：**新专名（`([一-龥]{2,3})(冷笑道|笑道|…)` 启发式 + 名册排除）** / **信息差关键词（泄密候选）** / 高频意象（CJK 4-8 gram Apriori 分层，内存有界）/ 句式偏离。候选永不拦截
- **落点**：moshu-write 写后收尾（check-ai-patterns 之前）加一道 `scripts/mechanical_check.py`；拆书 Stage 2 摘要硬检查可复用其中"条目形式/复读"项
- **成本**：~300 行，全字符级零依赖（绕开中文分词）
- **验收**：对已知 AI 腔文本命中阻断项；对正常文本零误报（候选不拦截）；新专名候选正确排除名册内名字
- **风险**：检测误报——照搬"只出候选不拦截"纪律；中文统计全用字符级

### L5 重试预算补全
- **学什么**：自动修复 2 轮硬上限 + **草稿 sha256 幂等**（同 hash 重检不扣预算）+ author-confirmed 单独记账 + 严格 schema fail-closed + 按章持久化（定稿后清章）
- **落点**：moshu-write 现有"机检修复预算 2 轮"补幂等与持久化（`追踪/重试预算.json` 或并入追踪事务）
- **成本**：低
- **验收**：同草稿重复检查不重复消耗预算；预算文件损坏时 fail-closed 不猜测

## 二、数据闭环（v1.2）——🟡 第二批

### L6 追读力四维标注
- **学什么**：hook 五型（危机/悬念/渴望/情绪/选择）+ 强度；爽点模式（精简）；微兑现 7 类（信息/关系/能力/资源/认可/情绪/线索）；硬约束 vs 软指导（软违规记债务可申诉）
- **落点**：事务 delta 加 `reading_power: {hook_type, hook_strength, coolpoint_patterns, micropayoffs}`；taxonomy 精简为 mo-shu 自用版（新 references 文件）；卷复盘消费趋势
- **成本**：低-中（字段 + schema 扩展 + 文档）
- **验收**：逐章记录可见钩子/爽点标注；卷复盘给出本卷追读力统计
- **风险**：taxonomy 文档需精简防 reviewer 标注漂移；标注是 AI 判断非确定性计算（明确地位）

### L7 evidence 溯源链
- **学什么**：状态/伏笔/角色变化带 `evidence: ["chapter:12:event"]`，可审计"为什么变成这样"
- **落点**：事务 delta 各 changes 项加可选 evidence 数组（纯增不改，check 校验格式）
- **成本**：低
- **验收**：任意伏笔当前状态可追溯最近一次推进的章与事件

### L8 outline 相关性筛选
- **学什么**：渲染上下文.md 时，用本章细纲文本对伏笔/角色做子串命中优先（命中者先取，再按埋设章近远补齐）——替代现"活跃伏笔截断 8 条"
- **落点**：tracking_commit.py 渲染函数内排序（**规则必须确定性化**以兼容 check 逐字比对）
- **成本**：低
- **验收**：本章细纲提及的伏笔必然在上下文.md 中；check 仍通过
- **风险**：筛选规则必须无随机性（webnovel 的 outline 子串匹配可确定性化）

### L9 审查指标落库 + 趋势回灌
- **学什么**：review 收尾写轻量指标 JSON（S1-S4 计数/维度结论）；写前准备读"近 5 章高频问题维度"作为约束（趋势只提示不裁决）
- **落点**：moshu-review 收尾落 `追踪/审查指标.json`（或并入事务）；workflow-chapter 写前准备 (a)-(g) 加一步读取
- **成本**：中
- **验收**：连续 3 章 S1 同维度 → 第 4 章写前任务书出现该维度约束
- **风险**：避免过度量化——趋势只提示；报告体积受控（轻量 JSON 非 md 全文）

### L10 章间"悬了太久"预警
- **学什么**：已有 10/10/30 阈值（伏笔/悬念/感情线），补按章预警（"是提醒不是错误，收不了可以接受"）
- **落点**：轻量 `report_overdue.py`（读派生视图现算悬久章数）
- **成本**：低
- **验收**：伏笔悬置超阈值 → 写前/批末提示

### L11 实体名册 + 别名反查
- **学什么**：正名/别名/类型/首现章一张表（唯一真源不双存）；commit 时校验新专名；resolve-alias 反查
- **落点**：`追踪/名册.md`（或派生视图）；tracking_commit commit 时校验；拆书导入时生成
- **成本**：低
- **验收**：同人异名/同名异人可机械检出；新专名出现在正文 → commit 提示登记
- **风险**：需定"谁维护名册"——拆书导入生成 + commit 增量校验

## 三、体验与查询（v1.3）——🟡 第三批

### L12 写前五段任务书
- **学什么**：开篇委托 / 这章的故事 / 这章的人物 / 怎么写更顺 / 收在哪里（把写前材料翻译成纯写作语言，屏蔽系统词）
- **落点**：workflow-chapter 步骤 3"指令确认"升级为固定五段结构
- **成本**：中
- **验收**：narrative-writer 收到五段任务书可独立起草（不依赖其他材料）
- **风险**：任务书过重拖慢日更——设 token 预算

### L13 经验库（带筛选的 learn）
- **学什么**：`learned_patterns: [{pattern_type, description, source_chapter}]` 随事务提交；**细纲命中才注入写前任务书**（只写不筛=死数据——它的教训）
- **落点**：新事务字段 + `追踪/经验.md` 派生视图 + 渲染时子串筛选
- **成本**：低-中
- **验收**：作者记一条"钩子模式"→ 本章细纲含相关词时注入，否则不注入
- **风险**：必须"写→筛→注入"三件套齐上；与文风库分工明确（文风=表达层统计，经验=结构层模式）

### L14 explorer 本地 BM25 检索
- **学什么**：纯本地词频索引（无向量无外部 API），搜正文/逐章记录/对标，chapter≤N 过滤，中文子串兜底
- **落点**：moshu-explorer 增加 `bm25_search` 查询类型（或独立脚本）
- **成本**：中
- **验收**："第 30-50 章发生了什么"可检索出相关章节；无网络依赖
- **风险**：中文无分词召回质量有限——明确作为 grep 的补充而非替代

### L15 候选制纪律
- **学什么**：给建议的环节（拆书模板/题材卡/技法路由）每类 ≤3 条候选 + **未命中如实声明降级**（"无匹配模板，走通用框架"），候选是材料不是答案，不替作者选择
- **落点**：拆书模板选择、题材正文提示卡、对标推荐、匹配章节挑选的 prompt/协议
- **成本**：低
- **验收**：无匹配题材时明确降级声明而非硬凑

### L16 degradation 显式标记
- **学什么**：读文件失败/降级时显式标 `degraded` 并先向作者呈报缺料，不静默基于残缺数据工作
- **落点**：各 Stage 失败处理（读对标缺失/文风缺失/摘要缺失时的降级路径）
- **成本**：低
- **验收**：任何降级路径的输出都带显式标记

### L17 作者友好三段式报告
- **学什么**：各 skill 收尾固定三段式——总状态 / 产生的文件 / 问题与下一步
- **落点**：各 skill 收尾模板统一
- **成本**：低
- **验收**：抽查各 skill 收尾报告格式一致

# 第二部分：SparkArc Studio 学习点（S1-S13）

> 依据：`docs/sparkarc-研究.md`（3 轮子代理：agent 设置/创作流程/质量保障）。SparkArc 教我们"闭环与协议"（webnovel 教"工程化与防呆"，两者互补）。

## Agent/协议层

### S1 落盘回执协议
- **学什么**：子 agent"必须真实落盘 + 字数实测才算完成"，只输出草稿 = 打回重做（`create_or_rewrite_script` 判定）
- **落点**：moshu-narrative-writer 模板 spawn 契约强化（防"写了没保存/没达字数就宣称完成"）
- **成本**：低 | **验收**：agent 只返回草稿不落盘 → 主会话打回

### S2 机器可消费修改单（fix_ticket）
- **学什么**：审稿输出 `decision + overall_grade(S/A/B/C/D) + dimension_grades + hits(evidence/severity/reason/suggestion) + fix_tickets(target/edit_goal/must_keep/operations) + rewrite_brief`——JSON 结构化、五档不用数字分（LLM 不稳定有 `_normalize_grade` 兜底）
- **落点**：moshu-review 输出契约升级（给每个 REJECT/CONCERNS 项补 edit_goal/must_keep/operations 三件套）
- **成本**：低 | **验收**：审查报告可直接喂 narrative-writer 重写
- **风险**：LLM JSON 解析失败——照抄 `_clean_json_block` 兜底

### S3 三模态提示词（system/chat_system/pipeline_system）
- **学什么**：同一 agent 在"聊天/委派/专有生成"三种入口不串味；共同规则抽 base 段 + tool reference 自动注入防三份漂移
- **落点**：agent 模板结构（mo-shu spawn 已是 pipeline 模式，抽 base 段）
- **成本**：低 | **风险**：多份 prompt 维护成本，需 tool reference 机制

### S4 文风档案分块分析（UnifiedStyleAnalyzer）
- **学什么**：30k token/块 + 块间上下文摘要传递 + 末块合成完整档案——超长文本分析不超窗
- **落点**：moshu-style 长篇小说（如 914 章）文风分析增强
- **成本**：中 | **风险**：串行分析慢、块间摘要损失细节

## 流程/闭环层

### S5 质量工单闭环（最高价值）
- **学什么**：审稿意见 → fix_ticket 持久化进状态层（quality_memory）→ **写前自动注入写手上下文** → 复审通过（PASS 且无新 ticket）才关闭工单——"审完不丢，批评影响后续写作"
- **落点**：`_tracking-state.json` 加 `quality_tickets` 段（ticket_id/target 三元定位/must_keep/operations/status）；日更写前注入 open 工单；复审关闭
- **成本**：中 | **验收**：审稿发现的 S1 问题 → 下章写前任务书出现对应约束 → 复审通过后工单关闭
- **风险**：工单误关/膨胀——用 chapter+维度 定位，避免全量

### S6 写评分离
- **学什么**：写手不审自己的稿（独立上下文 + 独立角色）；SparkArc 的 Critic 无落盘工具只读审；webnovel 的两审也用独立新鲜上下文
- **落点**：narrative-writer 的"写后去 AI 味自审"职责移出——独立为审查视角（并入 moshu-review 或 deslop），写作 agent 只管写
- **成本**：低（任务书重排）| **验收**：写后审查不再由写作 agent 自己执行

### S7 三圈记忆 + 按场景时间点过滤
- **学什么**：章内最近 3 场（硬）→ 前 2 章章末锚点（跨章情感）→ 梗概+节拍全局线（软）；前置按位置过滤的实时状态事实包（`_scene_position` + `eligible_scene_ids` **防止把未来剧情注入当前场景**）
- **落点**：写前上下文组装（增强 L8 outline 相关性筛选：加"场景时间点过滤"）
- **成本**：低-中 | **验收**：写第 N 章时上下文不含第 N+1 章及以后的状态
- **风险**：与 tracking_commit 渲染的确定性兼容（过滤规则确定化）

### S8 大纲场景契约字段
- **学什么**：细纲场景带 `knowledge_before/after`（知情边界）、`forbidden_setup`（禁止提前发生）、`causal_dependencies`（因果依赖）、`setup_refs/payoff_refs`（伏笔引用——机器可检查）
- **落点**：细纲模板补字段（mo-shu 已有"视角/信息差/信息留白"，补**伏笔引用 setup_refs/payoff_refs**）；Phase 5 契约检查脚本化
- **成本**：低 | **风险**：字段膨胀拖慢细纲产出——设默认值

### S9 任务板进度持久化
- **学什么**：Auto-Write 游标落盘（currentChapter/SceneIndex + nextResume + lastError），断线续写按 seq 续读，可任意场次继续
- **落点**：日更批量加 `追踪/_write-progress.json`（当前章/已完成/下批起点）
- **成本**：低 | **验收**：日更中断 → 重新开始自动从断点继续

### S10 结构 stale 传播
- **学什么**：梗概→节拍表→大纲：上游更新 → 下游标 `stale` + 写前警告注入（"过期产物只能作历史参考，不得覆盖较新的上游事实"）
- **落点**：卷纲/细纲版本关系（现有 check-outline-copy 只查正文与细纲重合，无 stale 传播）
- **成本**：低 | **验收**：改卷纲后，相关未写细纲标 stale 并警告

## 文风/质检层

### S11 风格执行卡 + 作者回避负面清单
- **学什么**：文风档案带"10-15 行可执行 bullet 写作指令"（风格执行卡）+ "作者回避"负面禁忌（≥5 条，从分析中累积）**同源产出**；**稳态 vs 高潮态语体档位**（情绪强度切换指令）
- **落点**：`文风库/文风.md` 模板补「作者回避」节；与情绪模块联动语体档位
- **成本**：低 | **风险**：负面清单靠 LLM 可能幻觉，需锚点支撑（只记有原文例证的回避）

### S12 脱敏短例（5-15 字 + 占位符）
- **学什么**：抽象指令 + 脱敏例证分离（人名地名换占位符，跨题材通用），锚点保留原文可回查
- **落点**：文风库锚点旁加脱敏指令行（可复用）
- **成本**：低

### S13 最终可见正文验收口径
- **学什么**：按解析结果统计"最终可见字符"（排除全部标记/构思块）；软目标 + 节奏浮动（±30%）不硬切
- **落点**：字数验收脚本口径统一
- **成本**：低

# 第四部分：架构重组评估（团队化拆分）

> 用户提出的设计思想：**把项目拟人化为团队，每个成员单一专职**。本部分评估 mo-shu 的 skill/agent 是否符合，以及是否要拆分。

## 4.1 思想验证：两项目都是"团队化"

| 项目 | 团队结构 |
|---|---|
| webnovel-writer v7 | 事实审查 + 编辑审（双角色）+ 单一 skill 调 CLI（薄 skill 厚脚本） |
| SparkArc | 导演（编排）+ muse/lorebook/showrunner/scriptwriter/critic（灵感/设定/策划/执笔/评审五专家）+ 工具面 + 任务板 |
| mo-shu 现状 | 主会话（编排+部分生产）+ 7 agent（按需 spawn）+ 10 skill 分职责 |

**认同用户判断**：moshu-write 是 mo-shu 里最大的 skill（references 80 文件，热路径 setup+chapter+daily 合计 ~35KB 去空白），因为它把**创作设计（Phase 1-3：选题/设定/大纲）+ 执行生产（Phase 4-5：正文/质检）**耦合在一起。按团队思想应拆。

## 4.2 拆分方案评估：moshu-write → moshu-plan + moshu-write

| 维度 | 拆分后 |
|---|---|
| **moshu-plan**（创作规划） | Phase 1 选题确认 / Phase 2 核心设定 / Phase 3 卷纲+细纲 / 中途补纲——消费 outline-*/genre-*/character-* 方法论（~15 文件），产出 `设定/`、`大纲/`；热路径 = SKILL + workflow-setup |
| **moshu-write**（正文执笔） | Phase 4 单章 / 日更 / 修订——消费 workflow-chapter/daily + writing-* 技法 + anti-ai/banned-words（~10 文件），产出 `正文/`、`追踪/`；热路径 = SKILL + workflow-chapter/daily |

**衔接**：与 moshu-analyze → moshu-write 同模式——项目文件（设定/大纲/追踪）就是契约，无需额外状态层。日更续写需读细纲（属 plan 产物）→ 按"对标书路径查找"同款规则回退读取，不跨 skill 复制。

**收益**：① 各自热路径变轻（plan 路径不再背 chapter 的 14KB）；② 职责单一（规划 skill 不碰正文，执笔 skill 不碰大纲方法论）；③ 与拆书/文风/审查/扫榜的"一 skill 一事"对齐。

**代价**：① 场景路由表调整（moshu 路由 → 两个 skill）；② 开书后写正文的衔接说明（Phase 4 入口提示读 plan 产物）；③ 契约守卫（behavior-contracts）同步；④ doc-budget 重排。

**结论**：**值得拆**。但拆分粒度到此为止——设定产生归 plan（创作设计的一部分），不独立 skill（Phase 2 太小）；灵感归 scan/plan；拆书/文风/审查/去味/扫榜/导入已独立。

## 4.3 设定专家（lorebook）学不学——修正回答

**之前的判断"不需要设定 agent"要修正**。SparkArc 的 lorebook 给我们的启发不是"加一个 agent"，而是三件事：

1. **设定的持续性**（最值得学）：设定不是开书一次性产物，而是全创作周期持续维护的对象（角色档案更新/关系图/设定一致性）。mo-shu 已有雏形（细纲后设定补全 + 追踪角色状态 + 转正机制），但**没有专职守护者**——按团队思想，设定维护应明确归属：
   - 产生 → moshu-plan（拆分后）
   - 状态维护 → 追踪系统（已有）
   - **一致性守护 → 可在 plan skill 明确"设定守护"职责**（每批细纲后补全 + 与追踪转正联动），或新增一个低成本设定守护 agent（见 4.4）
2. **输出纯度/反注入规则**（学）：lorebook 拒收网页/代码误输出（`_is_invalid_worldview_document` 自动重试）——mo-shu 的设定生成可加同款校验（生成结果必须是设定文档，不是对话/代码）
3. **作者确认关系图**（学）：关系只写长期稳定关系，临时互动明确禁止写入——mo-shu 的 `设定/关系.md` 可加同款纪律

## 4.4 Agent 层调整（团队思想落地）

| Agent | 现状 | 调整 |
|---|---|---|
| moshu-architect | opus，题材+世界观+大纲+钩子+情绪弧线（过宽） | **拆分候选**：moshu-planner（结构/大纲/钩子/弧线，opus）+ moshu-lorekeeper（世界观/势力/关系/设定守护，sonnet）——成本更低（lorekeeper 不必 opus）；或保持现状（agent 可选 spawn 用得不频繁，拆分收益有限）——**列入可选，观察使用频率再定** |
| moshu-character-designer | 角色专职 | ✅ 符合团队思想，不动 |
| moshu-narrative-writer | 写+审（写评合一） | **修正**：只管写（S6 写评分离） |
| moshu-consistency-checker / explorer | 边界靠 prompt | 边界写死（P7） |
| 导演 agent | 无（主会话确定性路由） | ❌ 不学（LLM 导演 = webnovel v6 覆辙；skill 架构下主线程编排更稳） |
