## 一、产品愿景与定位

**mo-shu 是一套跑在 Claude Code 上的中文网文创作技能集**：以 skill 为产品本体、确定性脚本为地基、references 方法论库为知识层，覆盖扫榜→拆文→开书→日更→审查→去味→复盘的长篇创作全链路。

V2 阶段的定位不变、形态不变、不重构。本轮目标用一句话说清：

> **把守卫从"护结构"扩到"护叙述"，把写作系统的状态判定从"AI 读文档猜"升级为"脚本出证据"。**

现状判断（依据 `docs/研究-v3/04-mo-shu-现状盘点.md`，该档案 2026-08-21 已归档）：
- 代码本体质量高：12 静态守卫 + 19 回归实测全绿，字节级共享资产同步、版本链、预算硬约束齐备。
- 三类短板：①叙述性内容无守卫（"9 个 skill"数字已过期无覆盖）；②追踪 schema 缺"谁知道什么"（信息差）与悬置预警维度，卷复盘纯 AI 冷路径；③审查无工单化闭环、e2e/evals 薄。
- 三参考项目的共同教训（05 §二）：重后端/大换血全被证伪——V2 是**增量强化**，每批独立提交、可回滚。

## 二、原则（全文最高约束，规格与施工冲突时以本节为准）

1. **证据溯源原则**：每条设计必须标注「移植（源码路径）」或「mo-shu 自定（含验收标准）」；无源码依据的参数删除或显式标注。规格引用的行号以本次研究实测为准（05 §一教训：档案锚点存在 ±3 行漂移）。
2. **作者红线**：作者定稿权不可动摇。任何自动裁决必须带作者确认点；机检候选（candidate）**永不拦截**流程，只呈报（移植 v7 `mechanical-check` issues/candidates 两列）。
3. **三层分工宪法**：脚本做确定性、AI 做语义、作者做品味（现有 `skills/moshu-write/SKILL.md:19`）。新增能力先问"能否挂现有 skill/references/脚本"，防平行管线（移植 spark-arc `AGENTS.md` §8 新增流程决策树，阶段 3 落入 AGENTS.md）。
4. **兼容四原则**（任何批次不得破坏）：新字段/新文件全可选增量；老数据零丢失；迁移带备份；渲染规则确定性可重放。
5. **一批一提交**：严格按当期批次规格（`docs/规格/<世代>/批N-*.md`；V2/V2.1 世代已收官归档，新世代由作者发起）的文件级改动清单施工，不扩大范围；验收命令全绿才提交；失败先判因，禁止改断言变绿。
6. **删改同步**：删除/改名任何机制，必须同步清理全部文档引用（全仓 grep 验证零残留）——DeterminFlow `052f264` 六处同步清理是范本。
7. **临时产物不入库**：临时验证脚本与输出放 `/.tmp/tests/<任务>/`，用完即删；正式回归测试须能长期守护。

- **关键决策**：新脚本 `skills/moshu-write/scripts/check-prose-candidates.js`：输入本章正文 + `文风库/文风.md`（moshu-style 产物，句长/标点基线）+ `追踪/信息差.md`（3a 产物）；输出 `{candidates: [...]}` 三类：①高频意象（正文内同一意象词≥阈值次，阈值读基线档位）；②句式偏离（段均字数/对话占比 vs 基线区间外）；③信息差兑现（正文命中已登记信息差关键词→提示"可标记兑现"）。**输出无 blocking 字段**（结构上不可能拦截）；由 moshu-write 日更流程在机检步骤后调用、结果呈报作者。不做"新专名比名册"（中文专名提取确定性不足，防自造，附录 C）。
- **验收锚点**：test-prose-candidates.js（fixture 正反例：候选命中/干净文本零候选/缺基线时降级提示而非报错）；behavior-contracts 增"候选永不拦截"契约。
