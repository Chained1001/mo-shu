# mo-shu 开发标准

> 版本：v1.4（2026-08-25 升级：v1.3 + 脚本准入第四问（防线数，≥2 需作者特批）与守卫退役规则（§3.2/§4.2，B48 守卫生命周期治理）；v1.3 含 §4.3 审计需修项守卫化评估纪律（B42，与审计法 v1.7 同步）；v1.2 含 §8.3 推送后 CI 确认（强制）/§9.1 推送+CI 节点/§2.5 交互模态三规则/§7.1 审计法入列（六种各一份）/§5.3 体积红线软化/通用性原则声明及三条 B28-B29 教训（§5.1 全副本登记/§5.2 锚点引用副本可达/§2.3 下沉前守卫耦合检查）。build 特有流程规则不进本文件，归 workflow-build.md）
> 定位：**后续所有开发的准入门槛**——新增/修改技能、脚本、守卫、agent 时必须过本标准。
> 与 AGENTS.md 的关系：AGENTS.md 是宪法（红线/不学清单/术语），本文件是工程规范（怎么写代码/怎么建文件/怎么管版本）。
> **通用性原则**：本文件仅含跨 skill 通用规范——任何案例/技能特定的流程规则归各技能的流程文件（如 workflow-build.md），不进本文件。

## 一、架构原则（不可违反）

### 1.1 三层分工宪法
- **脚本做确定性**（算术/结构断言/文件操作——零 LLM 零联网）
- **AI 做语义**（方法论指引/融合/生成——受字段和纪律约束）
- **作者做品味**（停靠裁决/提交确认/方向把控——唯一确认点）
- **新增能力前先问**：这件事该哪层做？确定性事务上脚本，语义事务留 AI，品味判断留作者。

### 1.2 文件即真相
- 一切状态来自文件系统证据（台账/日志/state JSON），不凭对话记忆猜
- 结构化载荷（JSON/事务）先落文件再以 `--input <文件>` 提交脚本（宪法 §2.8）
- append-only 日志（施工日志/审核记录/变更日志）——禁止修改历史条目

### 1.3 技能域分离
- 每个技能一个用户意图域，边界清楚，不跨域产出
- 新技能必须通过：①AGENTS.md §5 决策树 ②Agent 使用判据（AGENTS.md §5 Agent 判据）③本标准的全部准入
- 技能间通信是 prompt 级引导（"建议 /moshu-research"），不是函数调用

### 1.4 Agent 选型四判据
批量并行 / 上下文隔离重型阅读 / 审查隔离 / 条件性重活——四条全不沾则不开 agent。任何 agent 必须：fallback 主线程 + 部署物全套（模板+spawn 协议+契约摘要+agents_version bump）。

## 二、技能设计规范

### 2.1 SKILL.md 格式
```yaml
---
name: moshu-<域名>
version: X.Y.Z
description: "一句话定位。触发方式：/moshu-<name>、<中文触发词>。<边界声明>。"
---
```
- description 必须含：定位 + 触发词 + 边界（"XX 归 /moshu-xx"）
- 版本 bump 时机：行为变化（新字段/新流程/新红线）→ minor；措辞/勘误 → patch

### 2.1b Stage 命名规范（B26）
- 流程步骤命名从 1 起编号：**Stage 1, Stage 2, ... Stage N**
- 子步骤命名：**Stage N-M**（如 Stage 2-3 骨架表）
- 子步骤是**引用时的定位口径**（如"见 Stage 2-3"），不要求在文档中新增子标题
- 禁止从 0 开始编号、禁止用"步 N"等旧称

### 2.2 references/ 组织
| 类型 | 命名 | 体积上限 | 说明 |
|---|---|---|---|
| workflow | `<域>-workflow.md` | doc-budget 登记 | 主流程，触发即全量加载 |
| cold-path | `cold-path.md` | 不登记 | 低频路径，按需加载 |
| methodology | `<主题>-methods.md` | 按节精读 | 方法论文档，带「节名」锚点 |
| cards | `<类型>-cards.md` | 冷路径 | 卡片集（节拍/人物/命名等） |
| templates | `output-templates.md` | 按需 | 产物落盘模板 |

#### 方法论文件格式规范（B25）
- **设计方法用苏格拉底问句**（被迫回答具体内容），不用清单式指引（"要做什么"→ AI 打勾通过）
- 每节问句 ≤5 个；问句格式：具体问题 + "答不出说明设计未完成"
- 反面清单必须附（"标签式回答 = 未完成设计"）

#### 模板填空式提示（B25）
- 关键字段的空格子用填空式提示而非空位：`{假胜/假败：主角此时错误地相信____，但读者已经知道____}`
- 目的：迫使填入具体内容，杜绝标签式填充（"直面X"四个字不够格）

- **方法论文件禁互引**（AI 看不到对方——SparkArc E2 教训）；纪律正文自包含
- **按节精读**：引用带「节名」锚点的方法论时，先 grep/offset 定位只读所需节

### 2.3 热路径体积管理
- workflow 主文件登记 doc-budget，预算=实测×1.05 取整
- 超限处理序：先压缩 → 仍超则下沉冷路径 → 最后调预算（_comment 写理由）
- 冷路径文件不登记预算，但加头注声明加载时机
- **下沉前守卫耦合检查（B29 教训）**：下沉任何节到冷路径前，先 `grep -rn "节名" scripts/` 确认无守卫（static-check / closure / behavior-contracts）依赖此节在热路径——有依赖则不下沉只加注记（方法论副本索引先例）

### 2.4 产物目录规范（书项目内）
```
设定/          → 核心设定（题材定位/关系/弧线/世界观/采风-CF*）
大纲/          → 大纲/卷纲/单元卡/整合记录/变更日志
追踪/          → tracking state（build 不写，write 侧独占）
正文/          → 章节正文（write 侧独占）
对标/          → 对标视图（从拆文库复制，B16 轻量化后可只有登记）
```

### 2.5 交互模态三规则（B15+B26 成文）
1. **封闭选择**（候选可枚举 ≤4 项）→ 一律 AskUserQuestion 弹窗
2. **开放采集**（无候选、要自由表达/创作审阅）→ 对话式
3. **过程性动作**（不是选择，是即将执行的操作）→ 声明即将做 + 可显式跳过（如采风默认执行）

## 三、脚本规范

### 3.1 命名
- 守卫：`check-<能力>.sh|.py`（护仓库结构）
- 机检：`check_<能力>.py`（护作品，各 skill 内 scripts/）
- 回归：`test-<能力>.sh|.py`（长期守护，顶部"守护对象"声明）
- 工具：`<功能>.py|.js`（sync/bump/impact 等）

### 3.2 新脚本准入四条件（缺一不合并）
1. 正式回归测试 + 守护对象声明
2. CI 三处同步：`.github/workflows/cross-platform.yml` + `CONTRIBUTING.md` + `scripts/README.md` 索引
3. 如涉及跨 skill → 登记 `shared-assets.json`
4. **防线数第四问（B48）**：该不变量已有几道防线？（如版本一致性 = agents-version-sync 仓内 + bump 工具内建 + deploy verify 运行时；计数 = story-numbers + adapter + manifest.agents_count + verify 动态）——**≥2 道需作者特批**，防守卫增殖（各守不同表面才可留，纯重复防线不新增）

### 3.3 脚本纪律
- **零 LLM 零联网**（宪法反模式 #8）
- 退出码：0=通过 / 1=违规 / 2=参数或环境错误（三分类：缺/空/坏）
- candidate 永不拦截（宪法 §2.7）
- 宁可漏拦不可误伤（不确定→降级 candidate 或放行）
- **格式容错（B24）**：解析器应容忍合理格式变体（括号注释/中文量词/bullet 前缀/括号后缀）——解析不到的一律降 candidate 不升 blocking；原则：产出什么格式机检都应能读
- 断言跟模板走——模板变更须同批同步（清单类断言最易过期）

### 3.4 版本 bump 纪律（agents_version / setup_skill_version）
- **必须使用** `scripts/bump-agents-version.py`（确定性脚本）——禁止手工 grep+replace
- bump 脚本覆盖面（agents_version）：current-contract.json / 9 个 SKILL.md（反引号+无反引号两种格式）/ session-start.sh / deploy-manual.md / UPGRADING.md / deploy.py DEFAULT 常量
- **--setup-version（B24）**：setup_skill_version 独立轨，覆盖 6 处（SKILL.md frontmatter / current-contract / 哨兵样例 / UPGRADING / deploy-manual / deploy.py DEFAULT+CLI 帮助）；与 agents_version 可独立使用
- bump 后必跑：`check-current-skill-contracts.sh` + `check-moshu-setup-deployment.sh` + `check-agents-version-sync.py`
- **UPGRADING.md 加 vN-1→vN 变更条目**（说明改了什么、为什么需要重部署）

## 四、守卫准入与生命周期

### 4.1 准入条件（架构/契约类测试）
1. 守护跨模块稳定不变量
2. 直接覆盖统一收口（shared-assets / current-contract / behavior-contracts）
3. 普通迭代不频繁改断言

### 4.2 生命周期
- 新增 → 登记 CI + scripts/README + CONTRIBUTING
- **零命中超过两个月** → 候选下线（走作者裁决，不静默删）
- 断言过期 → 同批更新模板和断言（不单独改断言——宪法 §8 禁止改断言变绿）
- **守卫退役规则（B48）**：守护场景下线时守卫必须**同步退役**（反模式 #2 的守卫版——删机制当次全仓清理：删守卫文件 + CI 清单 + README 注册表行 + CONTRIBUTING + 配对回归，一处不漏）；守卫永不经由「保留但不再跑」静默搁置——不接 CI 即走豁免标注或退役裁决

### 4.3 审计需修项的守卫化评估（B42）
- 审计发现（审计法 v1.7 分级清单）的**需修/候选项修复时，同步评估可守卫化**：可自动化的（数字口径/称谓/字段契约/双份维护/命名锚点）必须转守卫（守卫/回归/契约/对账），或记录不转理由（一次性数据修复、纯语义判断）
- 可转未转项进守卫化 backlog（原评估文件已删除，历史在 git；未结事项由 B66 整体审计批重估），由后续治理批消化
- 修复提交的验收含「守卫化评估」说明：该项已转/未转及理由——防同类问题下次审计复发（版本散射/双份维护/称谓遗留是高频复发面）

## 五、shared-assets 使用规范

### 5.1 何时登记
- 跨 skill 使用的 reference / script → 登记（source + targets）
- 单 skill 专属 → 不登记
- **全副本登记（B29 教训）**：任何文件在 `moshu-setup/references/agent-references/` 存在的，必须在 shared-assets targets 里——不在 targets 的 setup 副本是同步缺口（genre-prose-cards 事件：B28 改了 write+build 但 setup 漏了→CI 红）

### 5.2 同步纪律
- 改 write 源 → 必须 `sync-shared-assets.py sync` → `check-shared-files.sh` 全绿
- **不手工双写**（改 target 会被下次 sync 覆盖——B17 偏差①先例）
- 新增共享文件 → 登记 + 首次 sync + 守卫绿
- **锚点引用副本可达（B29 教训）**：在共享文件中加跨文件 markdown 链接时，目标文件必须在所有 targets 副本中存在——reference-closure 只查主位置不查副本面；plot-emotion-system 事件：锚点加了但 setup 副本无目标文件→static-check 降 11/12

### 5.3 体积红线
- 单文件 >1500 行的共享脚本 → 候选拆分子命令（tracking_commit.py 1799 行为已知候选，待性能优化批处理）
- 副本数 >4 的组 → 评估是否提升为仓库级脚本（不走 shared-assets）

## 六、版本管理

### 6.1 四轨对齐（每次发版必查）
| 轨 | 权威 | 守卫 |
|---|---|---|
| 套件版本 | `skills/moshu/VERSION` | check-story-numbers |
| 插件版本 | `marketplace.json` plugins[] | check-claude-adapter |
| skill 版本 | 各 SKILL.md frontmatter | check-claude-adapter |
| agents_version | `UPGRADING.md`（权威）+ current-contract.json | check-agents-version-sync + check-current-skill-contracts |

### 6.2 发版流程
1. 版本四轨对齐（bump 脚本 + 手动）
2. CHANGELOG 置顶新条目
3. 守卫全量跑绿
4. commit + tag + push + `gh release create`
5. 事后 CI 确认全绿

### 6.3 版本号语义
- **major**：破坏性变更（不兼容旧项目）
- **minor**：新技能/新字段/新流程（用户可感知）
- **patch**：措辞修正/勘误/守卫修复

## 八、CI 纪律

### 8.1 三处同步（新脚本/新守卫必做）
- `.github/workflows/cross-platform.yml`
- `CONTRIBUTING.md` 本地清单
- `scripts/README.md` 索引

### 8.3 推送后 CI 确认（强制——v2.3.0/v2.3.6 连环红教训）
- 每次 git push 后必须等待 CI 完成：gh run watch 或轮询 gh run list --limit 1 --json conclusion
- CI 红 → 立即判因修复（gh run view --log-failed），修复推送后再等 CI 确认绿
- 未确认 CI 绿之前不开工下一批（与审核闸门同级）
- CI 等待超时（>5 分钟）→ 手动查看日志判因，不得跳过

### 8.2 跨平台
- macOS + Windows 双平台必须全绿
- Windows 前置：`export PYTHONIOENCODING=utf-8`
- Shell 用 `#!/usr/bin/env bash`，路径用正斜杠

## 九、施工流程规范

### 9.1 批次生命周期
```
出规格 → 作者确认 → flash 施工 → 验收全绿 → 请求提交 → 作者确认提交 → 审核（旗舰）→ 落档 → 推送 → CI 确认绿 → 下一批
```

### 9.2 规格必含
- 现状事实（grep 锚点，行号以 grep 为准）
- 设计总纲（含通用性四问检查）
- 文件级改动清单（逐文件列改什么/怎么改）
- 禁止事项（硬约束，施工前逐条核对）
- 验收命令（逐条可跑，含退出码）
- 提交规范（消息格式）

### 9.3 偏差申报
- 施工中发现规格与现状不符 → 停下走待决问题
- 合理解读规格歧义 → 偏差申报记施工日志
- **禁止**：改断言变绿 / 顺手优化 / 扩大范围

## 十、设计原则速查（贴墙上）

| 原则 | 一句话 |
|---|---|
| 案例→方法论四问 | 去作品化成立？多题材适用？强制会变滥调？有回退？ |
| 填充测试 | 用成熟作品反填我们的表格，填不顺处=方法论缺口 |
| 库存 vs 接线 | 残差发现后先 grep 库存——库存缺才立新节，接线缺只加引用行 |
| 通用性优先 | 产出通用方法论而非案例定制（单一作品的解法≠通用原则） |
| 版本散射预防 | agents_version bump 只用脚本，不用手工 grep |
| 冷热分离 | 低频路径下沉冷 reference，主线减负 |
| 按节精读 | 带「节名」锚点的方法论只读所需节，不整文件读入 |
| 苏格拉底式方法论 | 设计问句替代清单——迫使具体回答，杜绝"直面X"标签 |
| 填空式模板 | `{____}` 占位提示迫使填入具体内容，空格子允许标签 |
| 默认执行+跳过 | 过程性动作默认做+显式跳过（不是弹窗选要不要） |
| 标签消费检出 | 消费方只用了名字/标签未用实质内容=苏格拉底化不足 |
| 机检格式容错 | 解析器容忍合理格式变体——宁可漏拦不可误伤 |
| Stage 命名 | 从 1 起编号+Stage N-M 子步骤（引用口径） |
