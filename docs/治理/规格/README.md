## 1. 开工顺序（严格串行，不得跳批）

```
批0 → 批1 → 批2 → 批3a → 批3b → 批3c → 批4 → 批5 → 批6 → 批7 → 批8 → 批9
```

版本里程碑：批 0-2 → v1.1.3；批 3-5 → v1.2.0；批 6-9 → v1.3.0。当前进度看 [docs/治理/施工日志.md](../施工日志.md) 状态总表——**只认状态表，不凭记忆猜**。

## 2. 每批标准流程（flash 严格执行）

1. **读**：本文件 → 施工日志状态总表（确认上一批已关闭）→ `批N-*.md` 全文。
2. **复核现状**：规格"现状事实"节逐条 grep/跑命令复核；**行号可能因前序批次漂移，以文字描述+grep 结果为准**；发现规格与代码不符 → 走 §5 待决问题，不得自行改规格。
3. **施工**：严格按"文件级改动清单"；规格没写的**不做**（不做顺手优化、不重构、不改无关文件）。
4. **验收**：规格"验收命令"逐条跑，全部退出码正确才算完成；失败先判因（读报错→定位→最小修复），**禁止改断言变绿**。
5. **记日志**：按 §4 格式在施工日志追加本批条目。
6. **请求提交**：向作者展示验收结果，**作者明确说"提交"后**才执行规格"提交规范"的 git commit（一条消息、只含本批文件）；提交后把哈希回填日志。作者未确认前不 commit（AGENTS.md 红线 1/2）。
7. **等待审核**：状态改"待审核"；审核结论出来前不开工下一批。
8. **推送与 CI 确认（开发标准 §8.3）**：审核通过+落档后推送；推送后必须等待 CI 完成（gh run watch 或 gh run list），红了立即修复再等绿——CI 未绿不开工下一批（与审核闸门同级）。

## 3. 状态机（状态总表唯一权威，文件即证据）

```
待施工 → 施工中 → 待提交确认 → 已提交/待审核 →（审核通过→已关闭 ｜ 审核打回→修复中→待审核）
```

- 状态只由文件系统证据支撑：`已提交` 必须有日志里的提交哈希；`已关闭` 必须有审核文件"通过"结论。
- 打回后修复：只改审核文件列出的问题，改完在审核文件"整改回执"节逐条回执，再进"待审核"。

## 4. 施工日志条目格式（append-only，禁止改历史条目）

```markdown
## 批N：名称（状态：施工中）
- 日期：YYYY-MM-DD
- 验收输出摘要：<每条验收命令一行：命令 → 退出码/关键输出>
- 偏差记录：<与规格不符处及原因；无则写"无">
- 提交：<hash 或"待作者确认">
```

## 5. 待决问题协议（flash 卡住时）

遇到规格未覆盖、规格互相矛盾、验收无法达标三类情况：
1. **停在该步**（已完成且验收绿的部分保留）；
2. 在施工日志本批条目下追加 `### 待决问题`：现象/已尝试/疑似原因/需要谁决定什么；
3. **不得**：自行改规格、绕过验收、扩大改动范围。等作者或规划模型在日志里回复 `### 待决答复` 后继续。

## 6. 审核协议（规划模型/作者侧）

审核输入=规格+施工日志+`git log/diff`（只读）。每批五查：
1. **规格符合性**：diff 逐文件对照"文件级改动清单"（多改/漏改即打回）；
2. **验收复跑**：抽跑规格验收命令（独立复现，不信任日志转述）；
3. **禁止事项**：逐条核对规格"禁止事项"节；
4. **范围外改动**：`git show --stat` 与改动清单比对，零范围外文件；
5. **日志完整性**：条目格式/偏差记录/哈希齐全。

审核产出追加到 `docs/治理/审核记录.md`（单文件按批分节）：结论（通过/有条件通过+条件/打回+问题清单，每条带证据路径）→ flash 在同文件对应批次的"整改回执"小节逐条回执。**审核记录与规格同级别，flash 不得修改除"整改回执"小节外的任何内容。**

## 7. 环境须知

- 验收命令中 `python3` 在 Linux/CI 直接可用；**Windows 本地用 `python` 等价替代**（先探测 `python3`→`python`→`py -3`，与 skill 文档惯例一致）。
- js 测试直接 `node scripts/test-xxx.js`（自执行模式，非 `node --test`）。
- 临时验证产物一律 `/.tmp/tests/<批次>/`，提交前删除。
- 两工具若不在同一工作副本：由作者用 git 同步（push/pull），日志与审核文件随仓库走。

## 8. 红线速查（违反即停，详见根 AGENTS.md）

git 只读默认（提交须作者明确说）/ 参考项目绝对只读 / 归档区已删除（历史在 git） / 一批一提交 / 禁改断言变绿 / 候选永不拦截 / 不学清单 14 条勿静默引入。

## 9. 作者提示词模板（跨窗口复制即用）

> 原则：提示词只负责"指路+授权"，细节全在文件里。一个窗口干一批最干净。

**① 施工窗口（flash，开新窗口或续窗口）——开工/续批**：
```
读仓库根 AGENTS.md 和 docs/治理/规格/README.md，按协议开工：先看施工日志状态总表确认当前批，读对应批N规格，复核现状事实后施工，验收全绿后写日志，然后停下来向我请求提交确认（未经我明确说"提交"不得执行任何 git 写操作）。遇到规格未覆盖/矛盾/验收无法达标：停手，把待决问题写进施工日志等我答复，不得自行发挥。
```

**② 施工窗口——提交确认（flash 请求后，你决定提交时）**：
```
确认提交。按批N规格"提交规范"的消息格式，只提交本批改动清单内的文件（禁止 git add -A，禁止包含 docs/归档/ 和其他批次的文件），提交后把哈希回填施工日志，状态改为"已提交/待审核"。
```

**③ 施工窗口——审核打回后的整改**：
```
读 docs/治理/审核记录.md 中批N的审核结论，只整改问题清单列出的问题，改完在"批N 整改回执"小节逐条回执（问题编号→处理→复跑命令与结果），复跑该批全部验收命令，然后停下等我确认提交。
```

**④ 旗舰窗口（审核侧）——发起审核**（仓库需先同步到同一工作副本或 git pull）：
```
审核 docs/治理/规格/<世代>/批N 的施工：按 README.md §6 五查（规格符合性对照文件级改动清单 / 独立复跑验收命令 / 逐条核对禁止事项 / git show --stat 查范围外改动 / 施工日志条目完整性），结论追加写入 docs/治理/审核记录.md（通过或有条件通过或打回+问题清单，每条带证据路径），并更新施工日志状态总表的审核列。全程只读代码，不改任何施工产物。
```

**⑤ 施工窗口——待决问题答复**（你或旗舰侧答复后，回 flash 窗口）：
```
施工日志里批N的待决问题已有答复（见日志"待决答复"节），按答复继续该批剩余步骤，其余规则不变。
```
