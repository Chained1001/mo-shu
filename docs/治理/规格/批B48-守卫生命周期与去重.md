# 规格 · 批 B48：守卫生命周期与去重

- 版本：v1.0（2026-08-25）
- 依据：作者裁决（守卫面盘点+去重立项）。盘点结论：**真冗余近零**（static↔closure 为文档声明的互补对；计数/版本多道防线各守不同表面），结构性问题在**生命周期缺位**（8 守卫未接 CI 待处置、无末次能红验证登记、准入无防线数问、元递归无终点）。本批做减法与治理，不做守卫增殖。
- 前置：TS 补测批闭环后开工（串行，工作区含其在途改动）。

## 一、现状事实（盘点实测）

1. 总量：**56 守卫**（audit-guards.py 口径：48 接 CI + **8 个未接入**——含一次性/平台限定工具，标"需人工核对"）。
2. 互补对核实：check-reference-closure 头注明写「与 static-check 互补：static-check 扫 Markdown 链接，本守卫扫文件名文本提及」——**非冗余**，合并候选撤销。
3. 多道防线核实（各守不同表面，保留并登记纵深理由）：版本一致性（agents-version-sync 仓内 ↔ bump 工具内建 ↔ deploy verify 运行时）；计数（story-numbers README 面 ↔ adapter marketplace 面 ↔ manifest.agents_count 契约面 ↔ verify 动态源目标面）。
4. 唯一合并候选：TS13（bash 测 deploy.py 行为）↔ test-deploy.py（python 同域，跨平台无 python3 假红）——待作者裁决。

## 二、文件级改动清单

1. **Step 0 名单呈报（先于一切改动）**：跑 `python scripts/audit-guards.py` 取 8 个未接 CI 守卫全名单，逐个呈报作者三选一裁决：接入 CI / 明确豁免（注明理由：一次性工具/平台限定）/ 退役删除。裁决前不动任何文件。
2. **守卫注册表**：`scripts/README.md` 守卫索引表扩两列——「事故出身」（该守卫因哪次事故/观察而生）与「末次能红验证」（日期或"未登记-待体检"）；`scripts/audit-guards.py` 扩展：校验每个 CI 守卫在 README 有行且两列非空（缺即红）。初始值：本轮 TS 补测批验证过的填 2026-08-25，其余"未登记-待体检"。
3. **开发标准 v1.3→v1.4**：脚本准入三条件扩为四——第四问「该不变量已有几道防线？≥2 道需作者特批」；补「守卫退役规则」：守护场景下线时守卫必须同步退役（反模式 #2 的守卫版，删机制当次全仓清理）。
4. **元递归终点声明**：审计法 v1.8 纪律节加一句——「2e 为元层终点：不再出现以守卫/审计系统本身为对象的更高层守卫（audit-guards.py 与 2e 封顶）」。
5. （待作者裁决）**TS13 并入 test-deploy.py**：迁移三条回归（空文件/残留清除/占位符）至 python 侧，TS 套件删 TS13 节；:188 假红面不因此消失（TS9 仍需 python3），收益为 deploy 行为测试单点化。
6. 走查记录 v11 落批。

## 三、禁止事项

- 不新增任何守卫/测试（本批是减法与治理批——除 audit-guards.py 的注册表校验扩展属其自身职能）。
- 不动 TS 补测批产物（其闭环后为既成事实）。
- Step 0 裁决前不改文件；audit-guards 扩展不得引入对外部工具依赖。
- 失败先判因；与规格不符走待决协议。

## 四、验收

1. `python scripts/audit-guards.py` → 全部守卫有注册表行且两列非空（或明确豁免标注）。
2. 开发标准 v1.4 与审计法终点声明在位。
3. 守卫矩阵全绿（含 TS 套件 shim 跑通——假红遮蔽纪律 v1.8）。
4. 8 个未接 CI 守卫全部有裁决落档（接入/豁免/退役三态之一）。
5. 若裁决含 TS13 合并：test-deploy.py 含迁移回归且 TS 套件无 TS13 残留引用。
