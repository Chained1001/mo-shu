### 7.1 Agent 1 · 视角一：畅销作家（日更 500 万字级职业写手）

**走一遍全流程（第一人称）**——开书：轮 3 让我先写一篇"理想书评"当尺子（workflow-build.md:161），把"写好点"翻译成可对照的成品书评，是全流程最聪明的对齐装置；轮 2 一屏六问还在问我"预计更新节奏"时我脑子里的书已写到第三章，好在有默认兜底（workflow-build.md:211）；Phase A 全速不停靠（workflow-build.md:138-146）——别在我一个字没写时反复拦我。日更：「不做'是否继续'式确认」（workflow-daily.md:36）、"一章写完不问用户直接写下一章"（workflow-daily.md:56）——就要这样，别用"继续吗？"谋杀心流；连续快写 2-3 章再统一打磨（workflow-daily.md:47）说明设计者真懂批量生产节奏。但每章开写前的 A 段是一道沉重的流程税：13 项上下文清单+召回链逐章重跑，三遍法每遍开头命令"先读方法论书"（chapter-core.md:80、89、126、150）单章 6 处约 15 分钟——书不在仓库里，AI 只能表演"我读过了"。批末把刚机检过的同一批文件再整体重跑（workflow-daily.md:83）是流程不信任自己的证据。审查：review-log 把建议带回下批细纲（review-workflow.md:104）——审查结果真的回流写作；审稿令牌（review-workflow.md:189）治"没读输入就编报告"；must_keep 保底（review-workflow.md:330）——我被"修复式毁伏笔"坑过不止一次，这条我真想要。完结：末卷终章写前先读完结清账未清零项（chapter-core.md:84）、"未清零项逐一回收或经作者宣告有意留白"（outline-workflow.md:84）——千章烂尾是网文第一死因，把清账做成确定性工具+作者专属裁决权，完全正确。

**苏格拉底问句抽查（偷懒的 AI 会怎么答）**：
1. 章首钩子问句（chapter-core.md:161"开头三句能让读者不划走吗？…给出不可拒绝的理由或重写"）——偷懒 AI 答："以退婚冲突切入，悬念已建立。"刚写完这章的同一个 AI 自问自答，判定权在自己手里；章首钩子强度无外部校验（C 段只机检章尾 trailer，chapter-core.md:183），而 A 段手里明明有对标书同位置章节可对照却不强制引用。**真思考的好问句+荣誉自评的执行机制=大概率模板填空。**
2. 一进一出自检（outline-workflow.md:81"本章解决了哪个小问题？欠下了什么新问题？"）——细纲模板必填「核心事件」「章尾钩子」两字段（outline-workflow.md:35、44），自检永远可从同模板抄答案，结构上不可能"答不出"；它要防的"章章欠账"是跨章节奏问题，单章自检看不见邻居——有效版本其实是批末交叉核对③（outline-workflow.md:25）。**单章问句沦为抄字段仪式。**
3. reviewer 严苛指令（review-workflow.md:199"你的任务是【找问题】，不是验证正确性"）——工单经济学里 S4 几乎零成本、S1 要跨文件追踪，堆 S4 就能表演严苛；但系统有真实防御：审稿令牌逼真读输入（:189）、Agent 4"继承的开放项"硬清单（:300、316）、must_keep（:330）。**半防住：防住了"没读就编"，没防住"读了但挑软柿子"。**

**像/不像判定**：像一位跟了我十年的责编组长手带的"连续性部门"——数值仲裁序、悬置章距、卡文递三选项、完结拿清账表对数，真懂得伺候长篇。但不像作家的工具，像 QA 部门的工具：假设每处都会出错于是层层设卡；防的是"会偷懒的 AI"，伺候的却是"会疲劳的作者"——重叠处（卡文协议/数值仲裁/清账）极好，不重叠处全是纯税。

**三个最好的点**：①卡文阻塞协议（chapter-core.md:113）——日更作者第一大痛处的第一流水兜底；②数值正本优先级（chapter-core.md:34）——一条规则终结长篇连载最常见的掉订事故；③禁情绪母题扎堆（outline-structure-theory.md:302）——只有写过长篇的人才写得出的规则，教科书里没有。

**三个最需改进的点**：①三遍法每遍强制"先读方法论书"（chapter-core.md:80、89、126、150）——离线萃取进写法卡，会话内零方法论阅读；②A 段 13 项+召回链逐章重跑（chapter-core.md:15-30、39-57）——单元级一次召回缓存，章级只声明覆盖差异；③批末校验叠层（workflow-daily.md:83）——只重跑当批被改文件，批末语义核对合并单一出口。

**如果只能改一处**：砍掉"每遍先读方法论书"的强制仪式（chapter-core.md:80）——全流程唯一零故事价值、且必然催生"表演式合规"的强制步。

### 7.2 Agent 1 · 视角二：产品经理

**像/不像判定**：像专业生产力工具（IDE、剪辑软件）的架构：状态机+原子写、优雅降级、断点恢复、"候选永不拦截+作者裁决"的所有权模型（chapter-core.md:186；review-workflow.md:329）把控制权给足。但不像 2026 年消费级 AI 写作产品：没有"五分钟写出第一章"的第一次价值时刻，核心工件全是开发者语汇（state 修订号/工单 JSON/英文元数据 key/构建台账六态），价值感知全靠批末口头汇报替它说话（workflow-daily.md:96）。

**上手曲线/价值感知/摩擦点**：上手曲线——从安装到第一章要连闯 build 四轮问答+理想书评+档位（workflow-build.md:154-163）、对标/虚拟对标（:241-248）、文风三选项（chapter-core.md:42）三道闸，第一次"啊它帮到我"来得太晚；价值感知——单章价值具体可感，系统级价值被开发者工件包裹；摩擦点——fail-fast（chapter-core.md:238）与批末多层核对恰好征在作者心流最值钱的日更时段。

**三个最好的点**：①双 Phase 构建（workflow-build.md:79-83、138-146）——时间到首个可见产物的路径被刻意压短+成熟弹窗纪律（:19-24）；②全链路优雅降级（review-workflow.md:50 embedded fallback、chapter-core.md:42 文风三选项、workflow-build.md:83 断点恢复）——缺件时明示降级而不是死掉或装死；③作者所有权模型（chapter-core.md:186、review-workflow.md:329、cold-path.md:107"重合度"措辞+:99 强制引证可审计）——"机器干活、作者拍板"贯彻一致。

**三个最需改进的点**：①首章前置依赖链过重（workflow-build.md:241-248、chapter-core.md:238）——给官方"冷启动快路"：默认值先行+明示降级+后台补齐；②开发者语汇外泄（review-workflow.md:14-19、358）——给作者渲染"改哪/怎么改/别动什么"三层人话视图；③概念密度即支持成本（chapter-core.md:34 满是 B58/B59/B62 批次补丁号）——补"作者词典"，补丁号收文末变更注记。

**如果只能改一处**：增加官方冷启动快路——把第一次价值时刻压到会话前五分钟。

### 7.3 Agent 2 · 视角一：AI agent 系统架构师

**像/不像判定**：像一台「星型拓扑的编排流水线」：主会话是唯一编排者，8 个 agent 是按创作价值链切分的窄职责专家，agent 间永不直连，协作经文件系统与主会话中转；有生产级 job runner 特征——spawn 令牌防伪、模型分级（haiku 查询/sonnet 写作/opus 架构）、显式 maxTurns 及预算理由、fallback 降级主会话并强制报告。**不像** Autogen/CrewAI 式"多智能体社会"——更像「带外包专家的单人指挥官」，这个形态对长篇写作是对的：创作需要单一上下文权威，不是群聊。

**三个最好的点**：①审稿令牌+verify-token 横跨全部报告型 agent（moshu-narrative-writer.md:26-28、moshu-evaluator.md:20、moshu-consistency-checker.md:24-26、moshu-architect.md:23-25）——把"审查者是否真读了输入"这个纯语义问题转化为可机检的字节比对，且声明边界（只证读了 prompt，不证读了文件）；②上下文隔离做在读取协议层而非靠自觉（moshu-consistency-checker.md:55"prompt 里没有这两个值时不自行读取 _tracking-state.json"；moshu-architect.md:204-206 否定式声明封死越权读取——agent 模板里少见的高级做法）；③fallback 链完整且诚实标注降级代价（moshu-evaluator.md:8 自评偏差标注 Fallback、moshu-narrative-writer.md:192"不得声称已统计"、moshu-chapter-extractor.md:289-291 haiku 失败升级 sonnet 重 spawn 一次）。

**三个最需改进的点**：①spawn 协议声明与实调的接缝——consistency-checker 契约要求传 `last_committed_chapter`/`state_revision`（moshu-consistency-checker.md:55），A2 路径传了（chapter-core.md:15），D2 的 spawn prompt 只传项目目录/范围/类型两值缺失（chapter-core.md:201）——8 模板各写"被调用协议"、各工作流各写 spawn prompt，两侧人肉对齐，是拓扑里唯一没有单一真源的接口；②同一策略双份文本维护已现实化漂移——"匹配章节挑选"算法在 explorer（moshu-explorer.md:188-191）与主会话手动路径 (e)（chapter-core.md:43）各写一遍且细节措辞已不一致，两条路径无 shared-assets 式同步守卫；③三遍法第 2/3 遍执行者与上下文归属未指定（chapter-core.md:123-173）——若主会话执行须整章读回正好击穿文件模式省下的预算；若同 agent 自审则违背创作者/审查者分身判据——拓扑上真实的失败模式敞口。

**三层边界清洁度（附评）**：总体干净——脚本守身（tracking_commit.py:2-8"工具只验证/合并/渲染/原子提交"）、pace_meter 恒退出码 0+裁决归作者（:2-9、379）、卡文强制上报（chapter-core.md:113）、evaluator"不做决策"（moshu-evaluator.md:75）。两处存疑：完全可确定化的字数指标最终依赖 agent 自报（moshu-narrative-writer.md:192、301），主会话"供校验"但校验动作无定义——该确定化的仍在靠自觉；D3"删除优先"（chapter-core.md:207）授权 AI 自主删句是语义层代理品味裁决的灰色区。另 consistency-checker 用 haiku 做跨章因果推理（:10、80-109）与任务难度错配——chapter-extractor 的升级重试机制未复制到一致性检查。

**如果只能改一处**：把 8 个模板的"被调用协议"与各工作流 spawn prompt 收成一份双向生成的单一契约真源——spawn 接口是目前唯一还在靠人肉对齐、且已经漏过参数的部件。

### 7.4 Agent 2 · 视角二：大模型（transformer/attention）专家

**像/不像判定**：主体在**顺应** attention 衰减规律——热路径预算闸、减法加载、派生视图 O(1)、写稿干净上下文铁律、few-shot 锚点按场景路由，全部在压缩噪声、前置关键信息。**不像**的部分在量的层面：热路径规则文本随批次单调累积（doc-budget 的 why 链是铁证），正文 spawn 付约 13K 字符写手模板、日更路径付约 36K 流程文本，一章 3000-6000 字的创作反而在约 80K 字符规则包围中进行——流程规则在与正文争夺生成时的注意力；个别交付契约埋在长模板尾部（注意力衰减最不利位置）。

**三个最好的点**：①预算体系是真正的强制函数（doc-budget.json:3-8 度量口径钉死/只登记每次会话都付的文件/超限处置序"先删等量再显式调额"+组合路径组预算）——把上下文膨胀从无声滑坡变成每次增长都要留痕答辩；②派生视图字节双闸+点名注入预算是**确定性注意力裁剪**（tracking_commit.py:28-48：状态卡 8KB/12KB、逐章记录 1536/3072、出场区 2500 降级序）——降级是确定性的（按出场顺序），不让模型自己决定扔什么，同 state 永远渲出同一张卡；③写稿遍干净上下文铁律+few-shot 保真（chapter-core.md:95-101"不参考、不回忆建细纲时的规划讨论"、:35 减法加载、moshu-explorer.md:198-201 锚点 300-500 字不截断）——few-shot 的完整性与场景匹配正是 in-context learning 起效的两个注意力前提。

**三个最需改进的点**：①每章指令负载与创作素材配比失衡（doc-budget:170-178 正文 agent 组 45100+日更组 36200，模板 13300"每章每次 spawn 都付"）——规则绝大多数章间不变却按章全量重付；改进：写手模板拆「稳定内核（每书一次）+本章增量卡（每章付）」；②三遍法第 2/3 遍把全文拉回衰减不利位置或退化为自审——同上下文换帽是伪新鲜眼；改进：第 2/3 遍由独立 spawn 新实例执行（读落盘稿），令牌机制现成；③写手模板的操作契约沉在尾部（moshu-narrative-writer.md:250-301 的交付契约处于 30K 字符文本衰减最深处，而注意力最优位置 30-40 行只有"细纲边界"）——交付契约上移到头部块。

**苏格拉底问句措辞质量（抽样分析）**：
1. 第 2 遍 LOCK 四查（chapter-core.md:135"如果不有趣，是因为{____}（无欲望/无困境/无反差）？答不出说明主角设定不锐"）——强制填空+三选一分类学预先收窄答案空间（给 CoT 搭骨架）+"答不出"绑定失败语义；弱点在闭环：自评不留产物，长期会沦为仪式填空。
2. 角色辨识度（chapter-core.md:138"挑一段双人对话逐行标注是谁说的；标不出=对话无个性…换个人说还成立吗？成立=无语声个性"）——**三者最好**：把判断转化为可执行操作（逐行标注）+反向检验（换人仍成立=失败，反事实推理是注意力真正展开的 CoT 形态）+绑定可验证产物（语声锚/称谓行）。不会被当填空题。
3. evaluator 新鲜度（moshu-evaluator.md:49-51"举 2 个例子（作品名+桥段名）。举不出来说明什么（太平淡 or 太新没验证）？"）——数量化+格式化+"举不出"有生产性出口（二选一归因）；配套 :73"不确定标『存疑』禁编造"把幻觉风险纳入措辞契约——能触发真实检索式 CoT 的问法。
- **对照组**：hard_flaw 允许"或声明『无』"（moshu-evaluator.md:38-39、108）——"必须主动搜索过才算"无可验证产物支撑（自由文本字段不要求检索词/位置引用）；对比 consistency-checker 每条 finding 带"文件：行号"（moshu-consistency-checker.md:192-197），evaluator 的"无"是零成本退出。**好问句三要素=强制具体指认+绑定可验证产物+失败有语义；"无"出口恰恰缺第二要素。**

**如果只能改一处**：narrative-writer 每章全量模板改「稳定内核+本章增量卡」两级装配——释放的注意力预算直接还给细纲/状态卡/锚点，单点改动对生成质量杠杆最大。

### 7.5 四视角收束与既有发现的交叉注记

- 四份评估的「只改一处」：作家=砍方法论阅读仪式｜PM=冷启动快路｜架构师=spawn 契约单一真源｜LLM 专家=模板两级装配——四个方向互不冲突，共同指向**「把每章固定成本降下来、把接口收成单真源」**。
