# 审计法（唯一审计方法 SOP）

- 版本：v2.1（2026-09-01 固化 B94-96 三条实战教训：①**2d 版本管理补「第七查无条件原则」**——agent 模板 diff 以 git 实测为准，规格/施工声明零变更不构成豁免（B95 假零教训）；②**纪律节补「独立重跑 grep」**——对规格涟漪面结论独立全域名重跑，不采信规格自述（B94-96 三批连续漏项教训）；③**2a 补「运行时路径依赖」类**——hook 读文件/脚本常量/模板路径参数三类消费者，grep 引用面抓不到（B96 hook→VERSION 教训））。v2.0（2026-08-28 升级：**产品双基线审计**——v1.x 审的是「实现内部自洽」，v2.0 起增加两条：①**3c 产品承诺符合性**（PRD/FSD 作为与代码平等的审计基准，双向核对——产品承诺的流程/功能/设计是否落实、实现新增是否已反哺产品文档）；②**前置「产品基线新鲜度检查」**（审计对象涉及能力变化而产品文档未反哺时，先反哺再审计——防对着过时尺子量出假差）；③**3a 补「旅程锚定走查」**（以 PRD 用户旅程每步为起点，走查该步机制链的真实触发点——从「作者按下什么」到「机制在哪触发」，补「流程落实」维度）。动因：B66 开源强化整批审计（作者质询：审计不仅审代码，也要审流程/功能/设计落实、且要对着产品文档）。v1.9 内容：v1.8 + 三条实践经验——①平台假红清单补第四类「解释器版本差异」（pathlib 排序 3.13 变更教训：本地 3.12 全绿、CI 3.14 必红，本地验证不能代表 CI 解释器版本）；②基线步补「CI 等价验证」方法（git archive 提取 blob 树/模拟提交树复现 CI 场景——外部审核实证用过，SOP 化）；③2a 结构盘点补「跨技能形态/触发面一致性」观察（三技能走查发现形态三足鼎立+触发词收缩不齐——差异需显式判定为合理复杂度或漂移候选）。来源：setup/scan/analyze 三技能走查+指纹 CI 红判因+外部审核方法。v1.8 内容：守卫与测试有效性审计（2e 四查）+ 纪律三条 + 术语两条 + 元递归终点声明（B48）；v1.7 内容：分级清单加「可守卫化？」标注 + 修复时同步守卫化评估；开发标准同步 §4.3）
- 适用范围：任何模型对本仓库任何 skill / 机制 / 守卫的审计，以此为准。**对象可以是多技能业务链**（联合审计——按上下游关系一起审，衔接面[流程衔接表/路由/产物交接]是缺陷高发区，三轮实战中路由残留全部发现在衔接表）。
- **这是唯一审计方法**。历史审计（审计-V3、V4——已随归档区删除，收敛结论在本文件）与旗舰审计为过程产物，本 SOP 是它们的收敛形态。
- 与相邻机制的分工：行为契约（behavior-contracts）锁「话在不在」、能力接线（capability-wiring）锁「链通不通」——本审计法用于**人查**（跨 skill / 跨公约数的结构审计 + 方法论有效性审计），三者互补，不互相替代。

> 方法沿革：V3（逐 skill + 根因三分类）→ V4（基线 + 机制链 + 轻扫）→ 旗舰六步法 → v1.0 收敛（批B7）→ v1.1 产消对账 → v1.2 引用内容抽检 → v1.3 领域完备性补漏 → **v1.4 实测驱动升级**（填充测试/消费深度/通用性/版本工具化/模态/冷热/苏格拉底/实测回归）。

## 六步流程（v1.5：第 2 步含 2a/2b/2c/2d，v1.8 增 2e、第 3 步含 3a/3b、第 4 步含工具化专项、第 5 步含实测回归）

1. **基线**：先跑全量守卫矩阵（`bash scripts/*.sh` 与 `python scripts/test-*.py`）+ 与本域相关的回归测试，记录全绿基线（任何红先判因，**禁止修**——审计不是修复，修是施工侧的事）。**平台假红清单（v1.3，v1.9 补第四类）**：判因先排四类已知假红——①Windows GBK 控制台（`PYTHONIOENCODING=utf-8` 后复跑）；②chmod 权限位 no-op（test-shared-assets mode-drift 类，CI Linux 为准）；③符号链接/权限探测 skip；④**解释器版本行为差异（v1.9）**——同平台不同 Python/Node 版本的标准库行为（如 pathlib 默认排序 3.13 改按 parts 比较，本地 3.12 与 CI 3.14 排序不同致指纹不一致），跨版本敏感逻辑（排序/哈希/编码）本地验证不能代表 CI 解释器版本，须以 CI 版本为准或显式规避。排除后才算真红。**CI 等价验证（v1.9）**：本地无法直接跑 CI 时，涉及行尾/路径/解释器版本敏感逻辑，用 `git archive HEAD` 提取 blob 树（= CI 检出字节）复算，或模拟提交树（旧树+覆盖改动文件）复现——不能只信工作区结果（外部审核实证：模拟提交树指纹复现 CI 值）。

2. **结构与引用审计**：
   - **2a 结构盘点**：列出被审计目标（skill / 机制 / 守卫）的 SKILL / references / scripts 清单与体量，核对「按需加载」纪律（热路径 vs 冷路径是否登记进 doc-budget）。**安全面轻扫（v1.3）**：脚本的路径参数（--project/--input/--dir 类）是否 resolve 后限制在预期根内（防 `../` 穿越，参照 DeterminFlow local_archive.py:30-40 双重防护范本）；输入文件解析失败是否明示（缺/空/坏三分类）而非静默。**冷热分离检查（v1.4）**：热路径文件（触发即全量加载的 workflow）内容是否全部高频消费——低频段落（在主流程中被引用 <2 次）标记为冷路径下沉候选，**下沉前查守卫耦合**（v1.6：grep scripts/ 确认无守卫依赖）。**跨技能形态/触发面一致性（v1.9）**：同类技能的形态（薄壳+workflow 流程权威 / 内嵌流程+专题路由 / 多薄壳+内核）与触发面（命令+规范短语的收缩口径）是否一致——差异需显式判定：服务于复杂度（如 scan 内嵌因流程线性简单）为合理，无依据的不一致为漂移候选（三技能走查实证：触发词 setup 2 枚/scan 4→2/analyze 9→2 未收缩——「触发面逐技能收缩」成为整体议题）。**运行时路径依赖（v2.1 新增）**：引用面 grep 之外，另核①hook 读文件（session-start.sh→VERSION）②脚本读常量/路径字面量（deploy.py）③模板路径参数——删除/迁移任何文件前先核这三类消费者；此类依赖 grep 引用面抓不到（B96：hook 版本源靠施工发现）。
     **shared-assets targets 完备性（v1.6）**：列出 build/references/ 中所有在 `moshu-setup/references/agent-references/` 有同名副本的文件，核对是否都在 `shared-assets.json` targets 里——不在的为同步缺口（genre-prose-cards 事件）。
   - **2b 引用内容抽检**（v1.2，分层不全读——可达 ≠ 内容对）：
     - **热消费深读**：被审计目标流程**高频指示加载**的 references 抽 2-3 个深读内容——与当前机制是否矛盾、是否真的包含下游要读的那个节/字段、内部二级引用是否可达（B4 教训：引用的引用也要闭包）。
     - **过时信号全扫**：全部引用文件 grep 已删除/已改名的机制名（如 workflow-setup 类墓碑名——closure 守卫的"非资产宇宙忽略"规则会静默放过这种提及，只有审计能抓）。
     - **体量异常标记**：异常大（从未裁剪，候选瘦身）或异常小（空壳，候选充实）的引用文件标记呈报。
     - **通用性四问（v1.4）**：对逆向萃取/案例启发的方法论节追加四问——①去作品化成立？（拿掉具体作品原则还成立吗）②多题材适用？（都市/女频/悬疑用得上吗）③强制会变滥调？（必填会不会制造新模板）④有回退路径？（不适用的怎么豁免——B17"弱绑定回退"为合格先例）。未过四问的方法论条目标记为"案例残留"归候选级。
     - **苏格拉底问句有效性抽检（v1.4）**：对含苏格拉底问句的方法论节，抽 1-2 个问句**模拟回答**——如果 AI 能用 ≤5 字标签回答（如"直面X"），说明问句不够强制，归候选级（问句改进建议）。
   - **2c 填充测试（v1.4 新增）**：拿一部成功作品的已知结构，反填被审计域的核心模板（骨架表/角色弧线/要素表）。**填不顺处 = 方法论盲区**。残差发现后先查库存（grep 方法论库），区分三种缺——**库存缺**（方法论文件不存在该内容→立新节）vs **接线缺**（存在但流程未引用→加引用行）vs **深度缺**（存在且引用但内容不足以覆盖成功作品的丰富度→充实内容）。三种缺的修法不同，混淆会导致假缺口或重复建设。
   - **2d 开发标准合规检查（v1.5 新增）**：对照 `docs/治理/开发标准.md` v1.3 检查被审计目标（按目标类型取相关节——skill 审 §1-§3+§6-§8+交互模态、脚本审 §3-§4、流程审 §9+交互模态；不必全审）——
     - SKILL.md 格式（frontmatter name/version/description 齐全？）
     - Stage 命名（从 1 起？Stage N-M 子步骤？无步 N 残留？）
     - references 组织（方法论是否苏格拉底格式？模板是否填空式？）
     - 脚本规范（命名？准入三条件？格式容错？版本 bump 用脚本？）
     - 版本管理（四轨对齐？bump 脚本覆盖 agents+setup？）
     - **第七查无条件原则（v2.1 新增）**：`templates/agents/` 是否有 diff 以 **git 实测为准**，规格/施工侧声明的「零 agent 模板变更」不构成豁免——有 diff 即必须 bump（盲区 #13）。B95 实证：规格 A2 列 5 模板改造而盲区 #13 声明零变更，自相矛盾未被发现直至审核。
     - 文档规范（五种各一份？append-only？）
     - CI 纪律（三处同步？）
     - 交互模态三规则（封闭弹窗/开放对话/过程默认+跳过）
     不合规项按性质归需修级（违反规范）或候选级（格式微偏）。
   - **2e 守卫与测试有效性审计（v1.8 新增）**——触发条件：被审计对象配有 check-*/test-* 或 TS 类套件，或审计中发现「守卫理应拦截却未拦」的事故。四查：
     - **存量能红验证**：抽既有断言构造违规 fixture，确认真的会红——防「摆设绿」（B44 红灯验证的存量版；断言存在 ≠ 断言有效）。
     - **锚点漂移扫描**：断言指向的文件/节/文本与被审对象现状逐条对齐（实例：TS10「先自检参考目录」断言在 v3 结构统一后仍指 SKILL.md，被 :188 假红遮蔽数周未暴露）。
     - **覆盖缺口盘点**：按三分类出具——**断言虚假**（危险，需修）/ **锚点漂移**（潜伏，需修）/ **覆盖缺口**（排队，按风险排序：灾难分支零覆盖 > 成对清单不一致 > 一般覆盖扩展）。
     - **成对清单一致性**：模板↔剥离名单、源↔副本、manifest↔实测这类成对集合做双向差集（实例：settings 模板命令 ↔ MANAGED_HOOK_SCRIPTS 名单漂移则新 hook 脱管）。
     - **元递归终点（B48）**：2e 为元层终点——不再出现以守卫/审计系统本身为对象的更高层守卫（audit-guards.py 与 2e 封顶；守卫/审计的治理走注册表、退役规则与人工审计，不叠守卫）。

3. **机制链与产消审计（核心——"守卫锁话不锁链"）**：
   - **3a 机制链**：枚举该目标的端到端链，**每链双向走查（v1.3）**——①**正常路径**：文档是否指示调用、脚本是否有该能力、消费方是否真的消费；②**异常降级路径**：缺件（上游文件缺失时明示还是静默）、坏格式（解析失败三分类：缺/空/坏）、中断恢复（断点机制存在且可续）、**幂等重跑**（同输入重跑结果一致）。每链判 **闭合 / 断裂 / 半闭合** + 证据。**人机分工点核验（v1.3）**：链上的自动动作是否越权——该有作者确认/裁决的点（采纳前校验/修订裁决/提交确认）是否齐备，无人确认的自动生效项呈报。**交互模态一致性（v1.4）**：列出全部交互点，逐个标注模态（弹窗/对话/默认执行），检查是否符合模态规则——封闭选择→弹窗、开放采集→对话、过程性动作→默认执行+可跳过；不一致处归需修级。
   - **3a+ 旅程锚定走查（v2.0）**：以 PRD §2.4 用户旅程的每一步为起点（安装/开书/日更/审查修订/卷复盘），列出该步应触发的全部机制（含新批次引入的），逐个走查「真实触发点」——文档指示（流程文件含该步吗）+ 执行能力（脚本/agent 支持吗）+ 实际消费（产物被下一步用了吗）。旅程步与机制的映射缺漏（某步该有某机制却没接线）与反向（某机制没有任何旅程步会触发它=死机制）都呈报。
   - **3b 产消对账**（v1.1，双向清单化）：
     - **正向（产出侧）**：列出该目标的**每个产出物**（文件/字段/标记），逐个问「谁消费？」——grep 全仓找显式消费点。按四级定级（v1.4 从三级扩为四级）：①**显式消费**（有消费点实证）✓；②**定位声明**（产出侧明文声明为学习材料/作者参考，B6 式显式决策）✓；③**标签消费（v1.4）**（消费方引用了该产出但只用了名字/标签，未使用其实质内容——如填了"直面共鸣"四个字但无具体事件/选择/代价）→ **需修级**（苏格拉底化不足的信号）；④**悬空**（既无消费也无声明）→ 候选呈报。
     - **反向（输入侧）**：列出该目标的**每个必需输入**（上游产物/字段/前置条件），逐个问「谁产出？」——上游存在 + **字段级吻合**（上游真产该字段吗？A2 教训：write 必读单元ID 而 build 未产，链断在字段级而非文件级）。反向断裂定级高于正向悬空（必需输入缺失会拦死下游）。
     - **capability-wiring 对账**：该域的产消关系是否已登记进 `scripts/capability-wiring.json`？登记面与实际面互查——**漏登记**（实际接线但未登记，守卫盲区）与**假登记**（登记了 consumer 但实际未消费）都呈报。
     - **向后兼容核对（v1.3）**：涉及数据结构/文件格式的域，核对兼容四原则（宪法 AGENTS §9）——新字段全可选？老数据零丢失？迁移带备份？渲染可重放？
   - **3c 产品承诺符合性（v2.0）——双向基线核对**：
     - **前置检查「产品基线新鲜度」**：先比对 PRD/FSD 与被审对象现状——若实现已有能力变化而产品文档未反哺，**先反哺再审计**（过时尺子量出的是假差）；反哺本身作为审计的步骤 0 产物留档。
     - **正向（产品→实现）**：PRD 能力全景/用户旅程/FSD 规格逐条问「实现了吗、接进流程了吗、触发点在哪」；**研究档符合性（v2.0）**：开源研究的学习台账（如 研究/开源强化/00 §6.5）逐行核对「承诺学的机制→落地批次→移植形态」三层忠实——**研究了没学**（台账标移植却无实现）与**学了走样**（实现与来源机制/规格设计依据不符）都呈报；台账显式标「未移植/已裁/已覆盖」的项核对其决策记录存在即可，不算缺口——分三档：**落实**（机制在+流程接）/ **半落实**（机制在但流程未接=死机制）/ **未落实**（产品承诺无对应实现）。
     - **反向（实现→产品）**：实现新增的机制/字段/流程逐条问「产品文档收了吗」——设计依据（spec/研究档）与 PRD 表述是否一致（防 PRD 写的是旧设计）。
     - 档案分档沿用：【事实】（触发点实证）/【文档宣称】/（推断）。

4. **一致性轻扫**：版本口径（**枚举消费面后核对**[v1.3]——grep 全部出现点含代码字面量与 usage 串，session-start/deploy.py usage 两例教训：抽样核对必漏）/ 术语表（AGENTS.md §9 术语表）违例 / 悬空引用 / 数字口径 / doc-budget / 路由与判定表一致性。**版本字面量散射专项（v1.4）**：版本一致性检查用**确定性工具**——`python scripts/bump-agents-version.py <当前值+1>` dry-run 列出全部出现点，逐条核对是否与 `scripts/current-contract.json` 一致；**手工 grep 已被证明不可靠**（观察 024：7 类文件 2 种格式连续漏了 5 处），SOP 明确禁止以手工 grep 作为版本一致性的唯一验证手段。

5. **历史回归**：历次审计该域发现的**已修项**抽查复验，确认没有回潮。**实测观察回归（v1.4）**：test2-1/test2-4 等实测项目产出的使用观察文件中的已修项也纳入复验——实测发现的问题比结构审计发现的更真实（用户亲手碰到），回潮风险更高。

6. **分级汇总**：**阻断**（机制断裂或拦死流程；反向产消断裂[必需输入无产出]归此级）/ **需修**（真实缺口；标签消费归此级）/ **候选**（呈报；正向产消悬空/通用性四问未过/苏格拉底问句不够强制归此级）/ **存疑**——每条带证据（文件路径:行号）+ 档案分档（【事实】/【文档宣称】[v1.3：文档自述未实测——须复现或显式降档] /（推断）/ 存疑）+ **「可守卫化？」标注（v1.7）**：✅已转（已落地守卫/回归/契约）/ 🔶可转未转（进守卫化 backlog）/ ❌不可转（须一句理由，如一次性数据修复）——防同类问题下次审计复发。

## 纪律

- **自我推翻**：子代理或初判结论，须经本人复跑核实后再定级（V3 曾推翻"64 组"误报——初判需复核）。
- **独立复核**：转述必抽验（旗舰审施工、施工审规格，同一精神）——复核是转述的默认检，不信任日志转述。**复现证据落档**（v1.1）：审计报告中的载荷性主张（如"上游确实产出该字段""谱系级零消费"）须附复现路径（grep 命令/行号快照）随报告写入——B6 教训：事后补录的证据不如随手的。
- **独立重跑 grep（v2.1 新增）**：审核/审计侧对规格的涟漪面结论（「零引用/零残留/零消费」）**必须独立重跑全域名 grep**，不采信规格自述；全域名=skills/ + scripts/ + .github/ + .claude-plugin/ + CLAUDE.md.tmpl + README×2 + AGENTS.md + 全部 .json 契约。B94②/B95①③/B96①③ 三批实证：规格涟漪清单合计漏 8 处，全部由验收 grep 网兜住。
- **只查不改**：审计产物的**唯一写入 = 审计报告文件**；发现问题只呈报，不修复——修复须另行走规格（作者发起新批次）。
- **B6 先例**：显式声明的「零消费」≠ 缺陷——先查有没有定位声明（如 `拆文产物定位声明` 的"学习参考不读取"）再定级，避免把显式决策误判为缺陷。（v1.1 起此定级路径已内化为 3b 正向四级定级的中档。）
- **候选永不拦截**：审计的候选类发现只呈报作者，不阻断流程、不改变退出码语义（AGENTS.md §2.7）。
- **审计不替代实测（v1.4）**：本 SOP 是结构+方法论审计，不是功能验证——端到端跑通须靠实测（干净目录安装+全流程走查），实测发现的问题回填本 SOP 的历史回归清单。
- **守卫化评估（v1.7）**：修复需修项时同步评估——可自动化的必须转守卫（守卫/回归/契约）或记录不转理由；已转项从下次审计的"复发面"消失，这是审计边际收益固化的唯一途径（B31-B37 版本散射/双份维护/称谓遗留反复复发 → B38-B41 契约/对账/锚点守卫化后的经验）。
- **假红遮蔽（v1.8）**：假红的危害不止误报——它挡住其后所有未执行的断言（TS10 实例）。凡遇假红必须以等价替代（如 python3→python shim）**跑完全套**，跑不完视为该套件未审计。
- **grep 三陷阱（v1.8）**：过滤条件吃目标（-v 过宽）/ 词语言不匹配（中文词 grep 英文行）/ 管道截断（head 吃后段命中）。做「零命中」断言前，先用已知正例校验该 grep 能命中——**验证命令本身要先被验证**（2026-08-25 会话内三犯）。
- **交叉审计（v1.8，可选）**：重大「通过」结论可请另一侧复验关键断言——setup 三例实证：施工侧抓旗舰 CLAUDE.md.tmpl 盲区、TS13 回归拦下首修逻辑错误、本地验收暴露 CI 未跑路径的潜伏断点。

## 术语（本 SOP 内部）

- **端到端链**：一组「生产者产出 → 文档/流程指示 → 消费者读取/消费」的完整通路。审计断言对象。
- **守卫锁话不锁链**：行为契约守卫只锁"约束文本在位"，不锁"机制是否真的被用"——机制链审计补这一面。
- **半闭合**：生产者与文档有一方缺失/文档指示但脚本缺能力，或消费方未接线等"部分接通"状态。
- **产消对账**（v1.1）：双向清单化的生产-消费核对——正向逐产出问消费（四级定级：显式消费/定位声明/标签消费/悬空）、反向逐必需输入问产出（含字段级吻合）、capability-wiring 登记面对账。
- **字段级断裂**（v1.1）：上游文件存在但下游必读的字段未被产出（A2 单元ID 案例）——文件级 grep 查不出，须对照下游消费字段清单逐一核。
- **引用内容抽检**（v1.2）：分层的内容级审计——热消费深读 2-3 / 过时信号（墓碑名）全扫 / 体量异常标记；与文件级守卫（closure/shared-assets）互补，覆盖"可达 ≠ 内容对"的盲区。
- **墓碑名**（v1.2）：已删除/已改名的机制名（如 workflow-setup.md）——closure 守卫的"非资产宇宙忽略"规则会静默放过对其提及，是 CI 盲区，由 2b 过时信号全扫覆盖。
- **异常降级链**（v1.3）：机制链的另一半——缺件/坏格式/中断恢复/幂等重跑四问；与正常路径共同构成"每链双向走查"。
- **平台假红**（v1.3）：Windows GBK/chmod no-op/符号链接探测三类环境性假失败——基线判因时先排除，CI Linux 为权威。
- **文档宣称**（v1.3）：证据第四档——文档自述未经实测的数字/能力，须复现或显式降档后方可引用。
- **填充测试**（v1.4）：用成功作品的已知结构反填被审计域的核心模板——填不顺处=方法论盲区；残差须区分库存缺/接线缺/深度缺三种（观察 023）。
- **标签消费**（v1.4）：消费方引用了产出物但只用了名字/标签，未使用实质内容——苏格拉底化不足的信号（test2-4 教训："直面X"式回答 vs 具体事件/选择/代价）。
- **通用性四问**（v1.4）：案例→方法论必须过的抽象测试——去作品化/多题材/不造滥调/有回退（观察 022）。
- **版本散射**（v1.4）：版本字面量分散在多类文件多格式中，手工 grep 不可靠——须用 bump 脚本 dry-run 作为确定性枚举工具（观察 024）。
- **摆设绿**（v1.8）：断言存在但从不红的守卫/测试——上线时的红灯验证不保终身，存量断言会被锚点漂移悄悄废掉。
- **锚点漂移**（v1.8）：断言盯住的文本随内容迁移/重构失配——断言不再检验任何真实行为却仍显示绿（或被假红遮蔽从未执行）。
- **冷热分离**（v1.4）：热路径文件中低频内容（主流程引用 <2 次）应下沉冷路径——audit 时标记候选。
- **交互模态一致性**（v1.4）：全部交互点应符合模态规则（封闭→弹窗/开放→对话/过程性→默认执行+可跳过）——3a 走查清单项。
- **苏格拉底问句有效性**（v1.4）：方法论问句应迫使具体回答——模拟回答可 ≤5 字标签完成 = 问句不够强制（B25 教训）。

- **开发标准合规检查**（v1.5）：对照开发标准的十节逐条检查——审计不仅查链通不通，也查符不符合工程规范。
