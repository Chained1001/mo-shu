## 1 机制清单

### M1 分层摘要冻结（L0-L5）
- 证据：long-novel-writer `references/memory-protocol.md:16-40`、`references/file-contract.md:26-33`；README 来源标（`README.md:22` 文档宣称）
- 机制：正文（L0）之上建 L1 单章摘要（300-500 字，写完即冻结）→ L2 chunk（3-5 章，≤800 字）→ L3 篇章 arc（10-30 章，≤2000 字）→ L4 卷（≤3000 字）→ L5 全书（≤2000 字，卷末重生成、旧版归档进「历史版本」段）。生成规则「只读下层，不改下层」；**L1-L4 一经写定永不修改**，事实纠错走 continuity-issues + 实体档案变更记录，不回改旧摘要。上层摘要只在对应边界章触发（chunk/arc/volume 末章判定：读 blueprint 中当前章与下一章的归属编号是否不同，`memory-protocol.md:143`）。
- 输入→输出：某层级末章落盘时，拼接该层包含的所有下层摘要 → 生成并冻结本层摘要文件。
- mo-shu 映射：mo-shu 追踪事务只有「单权威 state + 派生视图」一级；卷报告（`skills/moshu-write/scripts/tracking_commit.py:1647`）是卷级产物但属清账报告而非摘要层。**「近三章速记」栏（tracking_commit.py CONTEXT_HEADINGS）≈ 滚动的 L1，但无 arc/chunk 中间层，也无冻结语义**——mo-shu 的状态卡是持续覆盖式更新，恰是 lnw 所称「电话传话稀释」的结构。
- 结论：**可移植（分层思路 + 冻结语义）**。中间层（arc/chunk）粒度与剧情单元卡天然对齐；L1 冻结 + 关键词反查可解「追踪视图全量读入」缺口。非 RAG，不触 §6。

### M2 正典账本（canon/ 五文件，只追加 + retraction + 单调性校验）
- 证据：long-novel-writer `references/memory-protocol.md:59-103`、`references/file-contract.md:394-471`
- 机制：五个只追加文件承载「叙述性文字无法机器比对」的约束性事实——`facts.jsonl`（原子事实 ≤100 字 + 10-50 字原文引用 source + `known_by` 字段）、`promises.jsonl`（承诺/誓言带 `deadline_day` 与 status：pending/fulfilled/broken/abandoned，状态变化追加 `-U` 条目）、`progression.jsonl`（境界进阶数值化 value，**写后校验检查新值不得低于同 system 历史最高值**，防境界倒退）、`rules.md`（世界规则，冲突时原条目旁加 ⚠️ 不删除）、`timeline.md`（按故事日 Day N 追加）。**canon 不进写前上下文**（体量线性增长），只在写后校验时按出场 entity 过滤载入，单次过滤结果通常 ≤5k token（`memory-protocol.md:103`）。正典本身错误走 `FACT-XXXX-R` retraction 条目，不修改原条目。
- mo-shu 映射：mo-shu 的 timeline 事件/伏笔/信息差已是结构化 JSONL 语义（追踪事务），但**缺「硬事实断言层」**：无「能力上限/物品归属/人物死亡/地理距离」类的只追加账本，也无进阶单调性校验。原文引用字段（source）防「回收时模型合理化杜撰」与 mo-shu 伏笔账本的证据语义相通。
- 结论：**可移植（facts/progression 子集最有价值）**。对百万字数值走形（境界倒退、宝物重名）是确定性防线，可直接挂进 D 段追踪事务的 JSON 提交。

### M3 POV 知识边界（known_by + disclosure 事件）
- 证据：long-novel-writer `references/memory-protocol.md:65-73`、`references/file-contract.md:411-416`
- 机制：`facts.jsonl` 每条可带 `known_by`（知道该秘密的角色 slug 列表，留空=公开）；新角色得知时追加 `type:"disclosure"` 条目（记录告知对象与出处）。写前组装时按出场角色过滤「已知秘密」列表，写后校验第 2 项专查「角色是否使用了其 known_by 之外的信息」——定位为「长篇后期最常见的 OOC 类型」。
- mo-shu 映射：mo-shu 信息差（`追踪/信息差.md`，知情人 knowers + 读者已知 reader_known + 登记状态，`skills/moshu-write/scripts/tracking_commit.py:528,609`）**已覆盖且更全（含读者侧）**。lnw 的增量仅在「写后校验把知识边界列为独立检查项」。
- 结论：**理念可学（校验项），登记结构不必引入**。mo-shu 信息差可加一条机检/审查维度：本章角色言行是否动用了未登记的知情人信息。

### M4 写前组装协议（9 步固定顺序 + token 预算表 + 槽位降级）
- 证据：long-novel-writer `references/memory-protocol.md:105-147,249-266`
- 机制：每章写前按固定顺序拼接：①metadata+story-bible（永载）②当前 L4/L3 摘要（按「实际存在的最高层」查表降级填充，含 6 种存在性组合的填充表）③当前+下一章 blueprint + 最近 10 章 index 的节奏检查（同 scene_type 连续 ≥4 章提示换类型；tension 连续 5 章 ≥7 或 ≤3 提示调节奏）④最近 3-5 章 L1 ⑤上一章结尾段原文 500-1000 字（第 1 章跳过）⑥出场实体档案（按 blueprint 命中过滤）+ 已知秘密 + 台词样本 ⑦活跃伏笔 ⑧禁用桥段/悬置副线/到期承诺 ⑨keywords 反查 top 3-5 相关章 L1。预算表给每项典型占用（合计 ~25k-40k，`memory-protocol.md:262`）；预算超限时裁剪顺序：先砍检索命中 L1 → 再砍非出场实体，**不砍 story-bible/活跃伏笔/出场实体**。
- mo-shu 映射：mo-shu A 段准备 + 上下文.md（8KB 目标/12KB 上限，`tracking_commit.py:30-31`）已是精选注入，但来源是覆盖式状态而非冻结摘要层，也无「按存在性降级的槽位表」与「预算超限裁剪优先级」。
- 结论：**理念可学（裁剪优先级 + 槽位存在性降级表）**。裁剪优先级是「story-bible 永不砍」式的确定性规则，可写进 write 流程的 A 段。

### M5 写后校验闭环（前置字数门 + 8 项语义 + 双 agent 防自审 + 修复路由）
- 证据：long-novel-writer `references/memory-protocol.md:149-231`、`references/prompts/consistency-check-prompt.md`（全文）；README 来源标（`README.md:44` 文档宣称）
- 机制：正文生成后不直接落盘，分三阶段——A 暂存产物（L1 草稿/新 facts/实体更新，全内存不落盘）→ B 校验：**0 号字数门先做**（机械检查：`tr -d '[:space:]' | wc -m` 含中文标点计数，比对 `[target×(1−tol), target×(1+tol)]`，tol 缺省 0.15；偏短调扩写、偏长调缩写、偏离 >30% 直接重写、最多 2 次扩缩后转重写；字数门失败语义校验仍执行）+ 8 项语义（正典冲突/POV 边界/硬约束/进阶合法性/命名 grep 禁用变体/桥段重复+伏笔对齐/scene 打分/台词样本更新）→ C 通过后 13 步固定落盘顺序。**双 agent 模式**：支持 subagent 的环境把校验委托给独立干净上下文（只传正文+过滤后 canon+硬约束+naming+最近 20 章 plot_beats，不传写作上下文），防写作 agent 自我合理化；不支持时手动换窗口。修复路由三档：轻微→局部修复；严重（违反硬约束/进阶回退/关键伏笔遗漏）→重写；无法修复→登记已知问题再落盘。
- mo-shu 映射：mo-shu C 段机检链 + review 四 reviewer 已是同类；**增量有三**：①字数门作为 0 号前置项（确定性最强先跑，省 LLM）；②校验视角独立性被明文规定为协议（与 mo-shu 审查隔离原则同源但落到每章）；③修复路由按问题严重度分档（mo-shu 工单未分档路由）。
- 结论：**可移植（0 号字数门 + 修复分档路由）**。字数门是纯确定性脚本活，可进机检链第一项。

### M6 台词样本滚动 + 上一章结尾段锚注入（文风/语声防走形）
- 证据：long-novel-writer `references/memory-protocol.md:129,202`、`references/file-contract.md:517-538`
- 机制：每个主要角色一份 `dialogue-samples/<slug>.md`，**不冻结、滚动保留最近 5 条**代表性台词（每条带背景注记，如「一字作答」）；写后校验第 8 步从本章摘 1 条替换最旧一条；写前第 6 步加载出场角色样本作语气参考（非硬约束）。写前第 5 步固定注入上一章结尾段原文 500-1000 字「用于文风与节奏衔接，不是整章」。首次登场角色该槽位填「首次登场，无历史样本」。
- mo-shu 映射：mo-shu style 技能产出静态文风画像（句长/标点/对话比统计），write 流程对标片段注入；**缺「按角色的语声样本」与「结尾段原文衔接锚」两个动态文风锚**。百万字后期人设走形多表现为「说话不像他了」，统计画像管不到语声层。
- 结论：**可移植**。两个锚都是轻量文件 + 固定槽位，与 moshu-style 的确定性统计互补（统计管文风、样本管语声、结尾段管衔接）。

### M7 naming.md 规范名称表 + 禁用变体 grep（中文人名/称谓一致性）
- 证据：long-novel-writer `references/file-contract.md:473-486,84-91`
- 机制：立项时从设定文档提取全部已命名实体生成「实体 slug | 规范写法 | 禁用变体」三列表（例：寒铁剑｜禁「玄铁剑、黑铁剑」）；新实体首登场时补行；slug 规则全拼 kebab-case、同音字加数字、一经写入冻结。写后校验第 5 项：grep 本章正文，**命中禁用变体直接报错**。
- mo-shu 映射：mo-shu 无对应物（角色状态有 identity 字段，但无「禁用变体」负向词表与 grep 检查）。这是纯确定性检查，成本极低。
- 结论：**可移植**。可与 banned-words 机检合并为同一检查器（正向：banned；负向：变体命中报错），挂进 C 段机检链。

### M8 副线悬置预警 + 承诺到期提示（防配角失踪/誓言蒸发）
- 证据：long-novel-writer `references/file-contract.md:503-515`、`references/memory-protocol.md:132`
- 机制：`subplots.md` 每条副线记「最后推进章节」；写前自动提示**距上次推进超过 20 章的活跃副线**。`promises.jsonl` 写前加载「距本章故事时间 ±200 天内到期且 status=pending」的承诺。两个阈值（20 章/±200 天）为该项目自定参数。
- mo-shu 映射：mo-shu 悬置章距（updated_chapter 距 last_committed_chapter 差值）+ 卷报告悬置预警已是同类（`tracking_commit.py:1659`），且作用于伏笔。**增量在「副线/配角线」与「承诺到期」两个实体类型**——mo-shu 只盯伏笔。
- 结论：**理念可学**。若在追踪事务中加 subplots/promises 事件类型，悬置预警逻辑可完全复用现有章距机制；阈值须 mo-shu 自定并标注验收。

### M9 章节索引 YAML（scene_types/emotional_tone/keywords/plot_beats）
- 证据：long-novel-writer `references/file-contract.md:316-344`
- 机制：每章落盘一份 YAML frontmatter 索引：出场人物/实体、plot_beats、`scene_types`（action/dialogue/introspection/exposition/transition 五值可多选）、`emotional_tone` 三维 1-10 打分（tension/despair/hope）、埋/回收伏笔 ID、新增 FACT ID、keywords。用途：①按实体/伏笔/关键词反查章节（写前第 9 步，**非向量，纯文本关键词检索**）；②写前节奏检查（M4 之③）；③桥段重复检测（最近 20 章 plot_beats 对比）。
- mo-shu 映射：mo-shu 追踪事务有 timeline 事件（含 characters 上限 12），但**无逐章索引文件、无场景类型/情感打分维度**。反查能力是「追踪视图全量读入」缺口的直接解法。
- 结论：**可移植（index 反查 + 打分维度）**。打分维度可并入追踪事务的章节提交字段；反查实现保持关键词文本匹配即不触 §6。

### M10 记忆快照与分叉写作
- 证据：long-novel-writer `references/memory-protocol.md:284-347`
- 机制：每 50 章或卷末（先到者）复制记忆层（entities/canon/summaries/账本，**不含正文**，正文走 git）到 `snapshots/ch-NNNN/` + snapshot-meta（触发章/故事日/当前卷）。用途：①回滚（记忆层覆盖回来 + 正文 git checkout 到 tag）；②分叉写作（复制快照到新目录探索「另一条路」，两线独立）。
- mo-shu 映射：mo-shu 每章一次追踪事务 + state_revision 已具备审计链，无定期快照/分叉。快照非「每章全量快照」（§6 禁项是每章快照——此项是每 50 章记忆层快照，粒度与对象都不同），但需谨慎对照。
- 结论：**理念可学（卷末记忆层存档点）**。卷报告已是卷末产物，附加快照语义成本低；分叉写作对多卷并发有参考价值（每卷独立目录线）。注意：不得演化为每章快照。

### M11 导入既有作品 13 步（反推记忆层）
- 证据：long-novel-writer `references/file-contract.md:163-242`
- 机制：已有正文无记忆结构时——切章 → 粗填 metadata → **全量生成 L1** → L1 拼接+代表性原文段反推 story-bible → 提取实体清单（用户勾选必建/建议建）→ 逐实体导入档案 → 按节奏回填 volume/arc/chunk 边界 → 生成 naming（扫正文补口语变体入禁用列）→ 反向填充 canon 四件（FACT/PROMISE/PROG/timeline 按 chapter 升序）→ 逐章提取伏笔（active 累积传入）→ 回填 L2-L4（token 受限时优先最近一卷）→ N+1 章起生成 blueprint → 首次快照。≤10 章作品给退化路径。
- mo-shu 映射：moshu-import 同域。lnw 的可借鉴点：**「先全量 L1 冻结、一切反推只吃 L1+代表段」的两级提炼设计**（控制导入成本），以及「伏笔逐章提取时前序结果累积传入」的时序处理。
- 结论：**理念可学**。

### M12 角色动态信息：8 类 × 每类上限 3 条的队列式状态

### M16 字数控制双模式 + 多轮预算运行时（advance/close 两段策略）
- 证据：NovelForge `backend/app/services/ai/generation/continuation_budget_runtime.py:10-316`；README 来源标（`README.md:80-83` 双模式文档宣称）
- 机制：模式一 `prompt_only`（提示词约束，文风自然省 token）；模式二 `balanced`（控制模式）：按「目标总字数 − 已有字数」规划多轮（≤1000 字 3 轮、否则 5 轮封顶），每轮生成前构建「续写预算」提示块（当前总字数/目标/剩余/本轮建议规模/本轮硬上限），**推进期**（剩余 >1000 或轮次富余 >3）每轮建议 220-2200 字；**收尾期**（剩余 ≤1000 或仅剩 ≤3 轮）按 600→300→100 字阶梯收束，末轮提示「只做结尾收束、不开新支线」；每轮 max_tokens = 建议字数 ×2.4、硬上限 = min(剩余, 建议字数×1.10)；生成后按句界（。！？!?…\n）裁剪超限文本；全程注入「大纲边界优先级高于字数目标，绝不可越入下一章内容凑字数」（`continuation_budget_runtime.py:11-14`）。
- mo-shu 映射：mo-shu 机检链有字数检查（后置），无多轮预算式前置控制。网文日更字数刚性（起点 2000/3000 字档）下，「预算提示 + 句界裁剪 + 大纲边界优先」三件套是确定性字数工程。
- 结论：**理念可学（预算提示块 + 句界裁剪 + 边界优先级声明）**。系数（2.4/1.10/600-300-100）为该项目自定，引入须 mo-shu 自定并标注验收。

## 2 与 mo-shu 差异对照

| 维度 | mo-shu（现状） | long-novel-writer | NovelForge | Long-Novel-GPT |
|---|---|---|---|---|
| 状态权威 | 单权威 `_tracking-state.json` + 派生视图，每章一次原子提交 | 无中心 state；文件即状态（账本+档案+摘要群），固定 13 步落盘顺序 | SQLite/Neo4j 数据库（Card/KGRelation 等表） | 前端内存 xy_pairs，无持久状态层 |

## 4 （推断）与存疑

1. **（推断）lnw 的实战有效性未经证实**：86 星、无独立示例作品仓库、无测试；其 README 数字（「典型写前上下文 25k-40k token」`README.md:25`）与 memory-protocol §四「9 项通常能压到 50k-150k token」（`memory-protocol.md:135`）自相矛盾，§六预算表（合计 ~25k-40k，`memory-protocol.md:262`）与前两者又不一致——文档宣称，未经实测。采用其机制时以 mo-shu 实测为准。
2. **（推断）lnw 对 agent 纪律的要求高于 mo-shu**：无脚本强制的落盘顺序与校验门（dev 分支无 CLI），全靠 SKILL.md 协议文本约束 agent 行为；mo-shu 有 tracking_commit.py 原子提交与机检链。**（推断）lnw 机制若移植，必须落 mo-shu 的确定性脚本收口，不能照搬「协议文本即护栏」模式**。
3. **（存疑）NF 的关系图谱抽取质量**：类型约束靠 17 种 kind 的静态表 + 自动降级「关于」（`memory_service.py:512-521`），降级会损失语义；对话样本 ≥20 字才入库的阈值无说明依据（该项目自定参数）。
4. **（存疑）NF 章节上下文注入上一章正文全文**（previous:1，`card_types.py:240`）而非 lnw 的「结尾段 500-1000 字」——两项目取舍相反；对 3000 字级网文章节全文注入尚可，对更长章节前者成本更高。（推断）mo-shu 宜取结尾段锚 + 摘要层组合。
5. **（推断）entity_snapshot 的约束力是软的**：NF 的卷末快照只进阶段大纲生成 prompt 作目标态声明（`card_types.py:217`），无写后校验对照「是否达到快照」——若 mo-shu 引入，应做成卷末机检/卷报告对照项才闭环。
6. **（存疑）LNG 分层提炼的「一行一句 ≤50 字」**是该项目自定粒度，无对照实验；mo-shu 若做 L1 层需按自身近三章速记的密度自定。
7. **（推断）三项目都没有解决「文风统计画像的定期重校」**：mo-shu 的最大痛点（百万字文风走形）在三项目中最接近的答案是 NF 的「审核 AI 味报告段 + 文风约束知识库常驻注入」与 lnw 的「台词样本 + 结尾段锚」，但均无「间隔 N 章重跑文风统计并与画像基线比对」的机制——**这是三项目共同的空白，也是 mo-shu 可以自建增量的位置**（style 画像基线 + 定期重跑对照，全部确定性，零冲突）。
