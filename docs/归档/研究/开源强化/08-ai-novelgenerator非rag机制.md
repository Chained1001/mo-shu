## 1 机制清单

### M1 按任务分配模型（五槽任务-模型路由）——本项目招牌之一

- 证据：`config_manager.py:16-22`（`GENERATION_CONFIG_KEYS` 五键）、`config_manager.py:112-118`（默认档位）、`config_manager.py:189-199`（normalize 迁移）、`config_manager.py:204-213`（指向不存在配置的校验）；`ui/config_tab.py:558-585`（五个下拉框「生成架构/生成大目录/生成草稿/定稿章节/一致性审校 所用大模型」）、`ui/config_tab.py:592-610`（保存）、`ui/main_window.py:112-125`（启动回填+失效兜底）；消费点 `ui/generation_handlers.py:37-43`（架构）、`:92-98`（目录）、`:133-139`（草稿）、`:346-352`（定稿）、`:423-429`（审校）、批量模式 `:552-558`（草稿槽）+ `:658-664`（定稿槽）。
- 机制：配置分两层——「模型预设」（`llm_configs`，每预设含 api_key/base_url/model_name/temperature/max_tokens/timeout，默认 5 预设，`config_manager.py:36-82`：Flash 档 max_tokens 8192、Pro 档 32768）与「任务选择」（`choose_configs`，五个任务槽各指向一个预设名）。默认路由：草稿=DeepSeek V4 Flash（便宜档）、章节目录=Gemini 3.5 Flash、架构=Gemini 3.5 Flash、**定稿=DeepSeek V4 Pro（强档）**、一致性审校=DeepSeek V4 Flash。UI 五下拉即改即存；预设改名有过期名迁移表（`config_manager.py:24-30`，旧模型名映射到当前预设）。生成函数不感知路由——UI handler 在调 cores 层前解引用预设七参数逐个传入（纯参数传递，无模型注册中心）。
- **重要名实偏差（代码事实）**：`final_chapter_llm`（默认 Pro 档）名字叫「定稿章节所用大模型」，但 `finalize_chapter` 实际只做三件簿记：全局摘要更新 + 角色状态更新 + 向量库写入（`novel_generator/finalization.py:37-113`，仅两个 LLM 调用：`summary_prompt`/`update_character_state_prompt`），**不重写正文**。真正的正文创作全部发生在草稿槽（默认 Flash 档）。即默认配置实际是「便宜模型写全文、最强模型做摘要/状态维护」——（推断）设计意图是「草稿便宜、终稿打磨用强档」，但「打磨重写」从未实现，只剩字数不足时的一次扩写（且单章模式扩写用定稿槽模型 `generation_handlers.py:371-381`、批量模式却用草稿槽模型 `generation_handlers.py:669-681`，两处不一致）。
- mo-shu 映射：mo-shu 在 build 阶段已用 agent frontmatter 钉模型档位（`skills/moshu-setup/references/templates/agents/`：architect=opus、narrative-writer/evaluator=sonnet、extractor/consistency-checker/explorer=haiku，8 个 agent 全部带 `model:`，实测 grep），**「按角色分档」我们已有且更彻底**；缺口在 write 日更主流程——B 段三遍苏格拉底/C 段机检/D 段追踪事务都在同一主会话，无法分档。可借鉴的具体经济学：①「辅助判定/簿记类任务钉低档」——我们追踪事务的摘要/状态更新、机检候选的预筛可钉 haiku 档 agent；②「温度按任务区分」——他们的检索关键词生成与知识过滤固定 temperature 0.3（`novel_generator/chapter.py:241,407`），正文 0.7，审校 0.3（`consistency_checker.py:35`）——mo-shu 目前 agent 模板无温度约定，可在 spawn 协议里加一行档位说明。本项目的反面教训同样有价值：**档位语义必须与任务实义对齐**（其「定稿槽=强档」实为簿记，钱花在刀背上）。
- 结论：**理念可学**（任务-档位映射表 + 温度分档；具体落地待作者裁决是否开批——注意 mo-shu 主会话模型用户自选，skill 只能钉 agent 档，故范围限于 spawn 类任务）。

### M2 四步雪花架构 + 断点续传

- 证据：`novel_generator/architecture.py:49-202`；中间态 `partial_architecture.json`（`:22-47` load/save，`:199-202` 完成后删除）。
- 机制：主题+类型+章数+每章字数+用户指导 → 依序四步 LLM 级联：核心种子（单句故事公式：主角+核心事件+关键行动+灾难后果+隐藏更大危机，25-100 字）→ 角色动力学（3-6 个角色，每个含背景/秘密、驱动力三层、弧线五段、关系冲突网）→ 世界观（物理/社会/隐喻三维度，每维至少 3 个可与角色决策互动的动态元素）→ 三幕式情节架构（每阶段 3 个关键转折点+对应伏笔回收方案）。**每步成功后立即落盘 partial JSON，重跑时按 key 存在性跳过已完成步**（`:90,109,125,142,158` 四处 if-shortcut）；角色动力学完成后额外生成初始 `character_state.txt`（`:125-140`）。四段拼装成带节标记的 `Novel_architecture.txt`（`:181-192`）。
- mo-shu 映射：build Phase A 的 architect/explorer/character-designer 管线已是同类且更细（角色弧光/驱动力等我们 references 均有）；**增量价值在「步级断点续传」**——moshu-build 若中途失败（API 断/作者中断），重跑是从头还是续？我们靠文件证据判定（SKILL 流程按文件存在性推进），架构类多步产物若各自落盘即可续，点已在；明确不缺。
- 结论：理念可学（步级检查点；mo-shu 现有文件证据判定已近似覆盖，无需新机制）。

### M3 章节蓝图分块生成 + 续传 + 100 章滑窗

- 证据：`novel_generator/blueprint.py:20-35`（`compute_chunk_size`：按每章约 200 tokens 粗估，`max_tokens/200` 取整到 10 再减 10，下限 1）、`:37-48`（`limit_chapter_blueprint` 正则切章、只保留最近 100 章）、`:99-132`（检测已有蓝图最大章号、从下一章续块）、`:150-179`（从零分块）。
- 机制：架构文本 → 一次或分块生成全章目录；每块生成后即追加落盘（失败保留已生成部分）；续传时**已有目录只注入最近 100 章**防 prompt 超长；每章目录为 7 字段结构（见 M9）。
- mo-shu 映射：我们细纲是「每章一个文件」，天然无超长问题且支持任意章续写——**形态优势已在**；他们的 200 tokens/章粗估常数是 mo-shu 反模式 #5（自造数字参数）的标本。分块+落盘+续传的骨架与我们 build 管线同构。
- 结论：不学（形态已被我们每章一文件方案超越；数值估算属自造参数反面教材）。

### M4 一致性维护四件套（非向量部分的全貌之一）

- 证据与机制（四个各自独立的机制）：
  1. **全局前文摘要**：`global_summary.txt`，定稿时用 LLM 把新章融入旧摘要（上限 2000 字），失败则保留旧值（`novel_generator/finalization.py:64-96`；prompt 见 `prompt_definitions.py:361-376`）。写第 N 章时全文注入 prompt。
  2. **角色状态树**：`character_state.txt`，树形五类（物品/能力/状态[身体+心理]/主要角色间关系网/触发或加深的事件），初始版由角色动力学生成（`architecture.py:125-140`），定稿时 LLM 增删式更新（「直接在已有文档基础上增删、淡出视线的角色可删除」，`finalization.py:87-96`）；原子写（`finalization.py:23-35`）。写第 N 章时全文注入。
  3. **前三章原文滚动窗 + 前章结尾锚**：读 `chapters/chapter_{N-3..N-1}.txt` 全文（`novel_generator/chapter.py:27-40`），取最近非空章的末 800 字作「前章结尾段」注入（`:393-397`）。
  4. **当前章节短摘要**：每次生成草稿前，LLM 把前三章全文（截 4000 字）压缩成 ≤800 字「当前章节摘要」，带当前章与下一章的元数据做定向（`chapter.py:42-114`）；**无缓存，每章重算**（连带检索词生成与知识过滤，每次 Step3 共 3 次辅助 LLM 调用 + 1 次正文生成，见 §4.5）。
- 组装顺序（`chapter.py:496-524`）：前文摘要→前章结尾段→用户指导→角色状态→当前章节摘要→当前章 7 字段→下一章 7 字段→知识库参考。第一章走独立精简 prompt（`chapter.py:350-367`）。
- mo-shu 映射：我们 D 段追踪事务（单权威 state+派生视图+信息差登记）是其 1/2/4 的结构化升级版（我们事务化/原子提交/可回放，他们是覆盖写+LLM 自由文本）。**两个可直接对照的增量点**：①「前章结尾 800 字锚」——mo-shu B 段写作时是否物理注入上一章结尾段？（推断：三遍法基于细纲与状态卡，未见显式结尾锚；这是廉价高效的衔接手段，值得核对补强）②「短摘要无缓存每章重算」反面——成本高；mo-shu 派生视图即缓存方案，优势已在我们。角色状态树五分类（物品/能力/身心状态/关系网/触发事件）可与我们角色快照字段对照（B59 角色语声样本之外，「触发或加深的事件」类目是他们有而提示词层面明确的）。
- 结论：理念可学（前章结尾锚——待核对 mo-shu 是否已有；角色状态五分类——对照补强项）。

### M5 下一章目录预注入（防越界写作）

- 证据：`novel_generator/chapter.py:334-343`（取 N+1 章七字段）、`:515-523`（注入正文 prompt）；摘要生成也带下一章元数据（`:93-100`）。
- 机制：写第 N 章时把第 N+1 章的定位/核心作用/悬念密度/伏笔/简述一并给写手，约束本章收尾给下一章留口，防止把下一章剧情提前写掉。
- mo-shu 映射：细纲每章一文件，写 N 章时读 N+1 章细纲是天然操作；（推断）moshu-write 的 13 项准备是否明确包含「下一章细纲预读」需核对；若有则同构，若无则一行清单的事。另他们用「在生成第 X 章前不要出现结局章」类约束防抢跑（`prompt_definitions.py:306`），与我们细纲章距预算同目的。
- 结论：理念可学（一行准备项级别的小补强，价值中）。

### M6 检索距离规则与重复度分档（近章防复用）

- 证据：`novel_generator/chapter.py:176-193`（`apply_content_rules`：正则识别片段所属章号，距当前 ≤2 章标 `[SKIP]` 跳过、3-5 章标 `[MOD40%]` 需改写 ≥40%、更远标 `[OK]` 可引用核心）、`:195-216`（`apply_knowledge_rules`：近 3 章内容跳过、历史章节需 30% 以上改写、第三方知识优先）；正文 prompt 中重复度分档规则（>40% 必须重构叙事角度/20-40% 替换至少 3 个关键要素/<20% 保留概念改表现形式，`prompt_definitions.py:606-610`）。
- 机制：对检索/上下文片段按「章距」打使用约束标签，再随 prompt 下发——用确定性正则+prompt 双层压制「AI 复读近章情节」。
- mo-shu 映射：这是 deslop/review 的邻域问题（我们管 AI 味，他们管情节复读）。**「章距分档」是确定性思路**（正则可测），但阈值 2/3-5/40%/30%/20% 全是无源码依据的自造数字（宪法反模式 #5 标本）。可学的是「上下文片段按新鲜度分级给使用指令」这个理念——mo-shu 注入派生视图时可给「近期章节梗概：仅作衔接不作情节来源」类分级标注（挂 B58 按需注入一起考虑）。
- 结论：理念可学（分级使用指令），数字不学（自造参数）。

### M7 角色库（文件制分类管理 + LLM 导入 + 出场注入）

- 证据：`ui/role_library.py`（1599 行管理界面：`角色库/<分类>/<角色名>.txt`，分类增删改、角色改名/冲突检测、文件名安全校验防路径穿越 `:54-83`）；从既有文本导入角色（LLM 按树形格式抽取 → 正则逐行解析树形结构 `:403-447`、`:525-582` → 勾选导入 `:584-630`）；写作时按本章「核心人物」名单把角色文件全文替换进 prompt 占位符（`ui/generation_handlers.py:202-244` 单章、`:595-631` 批量；占位符多变体匹配+按行回退两段式替换）。
- 机制：跨书复用的角色资产库（人类编辑优先），单章写作时按出场名单精确注入对应角色卡全文。
- mo-shu 映射：①「按出场名单注入角色全文」= B58 追踪视图按需注入的角色侧（我们已做两层：出场展开/背景列名——他们是「出场即全文」，粒度比我们粗）；②「从既有小说文本 LLM 抽取角色卡+正则解析+人工勾选」= moshu-import/analyze 的邻接能力，我们的拆书管线更系统；③跨书角色库 mo-shu 无对应物（设定资产跨书复用），但属于产品范围扩张，非缺口。
- 结论：理念可学（出场注入粒度对照，已被 B58 覆盖）；跨书角色库不引入（范围外，且与「知识治理重三件套」擦边）。

### M8 章节生成回路（单章五步 + 批量连写）

- 证据：单章：UI 按钮 Step1-4 + 批量（`ui/main_tab.py:62-100`）→ Step3 先构建完整 prompt 并**弹可编辑对话框等用户确认/取消**（`ui/generation_handlers.py:183-280`，含角色库注入与实时字数）→ 草稿生成（空响应重试 ≤3 次，`novel_generator/common.py:61-85`：剥 `<think>` 标签与代码围栏，空则重试，3 次仍空抛错）→ 落盘 `chapters/chapter_N.txt` → 用户在文本框自由编辑（`main_tab.py:38-54`）→ Step4 定稿确认（askyesno `:324`）→ 字数 <70% 目标时询问是否扩写一次（`:331-338`；扩写为单次 LLM 调用，无字数二次校验循环）→ finalize（摘要+状态+向量库，M4）。
- 批量：对话框一次配置（起止章/期望字数/最低字数/自动扩写勾选 `:465-549`）→ 循环「构建 prompt→草稿→（低于 70% 且勾选则自动扩写一次）→落盘→finalize」（`:551-717`），**中间无任何人工确认点**；某章草稿为空则抛错终止整批（`:655-656`）。
- 一致性审校是**旁路可选按钮**：单次 LLM 调用，结果只打进日志区（`generation_handlers.py:414-461`），不回流、不触发重写、无结构化工单。
- **判定：无多轮自我修正回路**——没有 evaluator 循环、没有审校驱动的重写、没有质量门禁；唯一的循环是「空响应重试」和「字数不足一次扩写」。
- mo-shu 映射：write 的 B 段三遍苏格拉底 + C 段机检链 + D 段追踪事务、build 的 Phase B evaluator 打磨环，均为我们显著领先项；本项目反证了「无修订环的直出管线」上限（与 02 号研究 autonovel 修订环的结论互证）。唯一可对照小点：**「发送前可编辑的完整 prompt 预览」**——GUI 形态专属；mo-shu 技能形态下等价物是 B 段准备产物落盘（我们 13 项准备即事实上的 prompt 原料清单），无需引入。
- 结论：不学其回路本身（落后于我们）；批量连写的自动化程度见 §3（触 §6）。

### M9 网文/长篇 prompt 方法论（转述，AGPL 不抄原文）

- 证据：`prompt_definitions.py`（中文 671 行，14 个具名 prompt；英文版 `prompt_definitions_en.py` 691 行同构）。
- 方法论清单（逐条转述）：
  1. **架构层**——雪花写作法四步（M2）；角色「驱动力三层」（表面物质追求/深层情感渴望/灵魂哲学需求）与弧线五段（初始→触发事件→认知失调→蜕变节点→最终状态）、关系网必须含「一个合作纽带+一个隐藏的背叛可能性」；世界观三维（物理/社会/隐喻）要求每维元素「可与角色决策互动」；三幕式的节拍名词：错误抉择、虚假胜利、灵魂黑夜、嵌套三层认知颠覆（表面解→新危机→终极抉择）、余波留 2 个开放悬念因子。
  2. **蓝图层（节奏工程）**——每 3-5 章一个悬念单元含完整小高潮；单元间「认知过山车」（连续 2 章紧张→1 章缓冲）；每章 7 字段（定位/核心作用/悬念类型[信息差/道德困境/时间压力]/情感基调迁移[如怀疑→恐惧→决绝]/伏笔操作三态[埋设/强化/回收]/认知颠覆强度 1-5 星/一句话简述）；禁止在末章前出现结局章。
  3. **正文层（场景张力）**——首章要求 ≥2 个「动态张力场景」，四类各有细则：对话场景（潜台词冲突+非对称对话长度显权力）、动作场景（≥3 个感官描写+短句加速/比喻减速）、心理场景（认知失调的行为矛盾+决策前价值天平）、环境场景（宏观→微观→异常焦点的透视+非常规感官组合）。
  4. **防复读**——重复度分档（M6）+ 继承权重数字（摘要 prompt 内含 70% 递进/30% 创新的配比要求）。
- mo-shu 映射：mo-shu 的 references 体量远超（beat-cards/emotional-arc-design/character-design-methods/commercial-core-methods/genre-prose-cards 等，`skills/moshu-write/references/` 实测 20+ 文件）。**可对照补强的差异点**：①「认知颠覆 1-5 星」与我们情节点密疏预算同轴，星级化表达更直观，可对照细纲模板字段；②「伏笔操作三态（埋设/强化/回收）」与我们的信息差登记/悬置章距互补——我们登记「谁知道什么」，他们显式管理「本章对某伏笔做哪个动作」，两者合并即是完整伏笔生命周期（与总纲 T2 主题收敛）；③「认知过山车（2 紧张 1 缓冲）」是节奏密疏的具体配方，可进 build/细纲方法卡；④「情感基调迁移」作为每章显式字段（从 X 到 Y）我们没有对应字段。**反面对照**：他们的方法论偏通用写作理论（雪花/三幕/弧光），中文网文特有的爽点设计、期待感管理、金手指/升级节奏几乎没有——mo-shu 的 commercial-core-methods 与扫榜体系在这一维明显更强，无需向其学习。
- 结论：理念可学（四个具体字段/配方级补强点，挂 B58/细纲模板批次考虑；均为提示词层知识，不涉代码移植）。

## 4 （推断）与存疑

1. **（推断）「定稿槽=强档」的原意是终稿重写**：`final_chapter_llm` 命名与默认 Pro 档暗示设计意图为「强模型出终稿」，但 `finalize_chapter` 无重写步骤，仅簿记+可选扩写。可能历史上存在重写环节后被移除，或从未实现。对 mo-shu 的教训已记入 M1（档位语义须与任务实义对齐）。
2. **文档宣称与代码事实三处偏差**（README_zh-CN.md:240-249，标（文档宣称））：①宣称 Step3 生成 `outline_X.txt`——全仓 grep 无任何 outline 文件写入；②宣称 Step4 更新 `plot_arcs.txt` 剧情要点——代码从不写该文件（`plot_arcs` 仅在 `consistency_checker.py:36,49` 作为恒空参数 `generation_handlers.py:453` 传入，及一个只读查看按钮 `:803-824`）；③宣称「状态追踪系统：伏笔管理系统」——伏笔仅存在于蓝图字段与 prompt 文案，无任何独立管理机制。**README 功能表以上三处不可信，本研究全部以代码为准**。
3. **两处代码内部不一致**（代码事实，映射时勿当作设计）：单章模式扩写用定稿槽模型而批量模式用草稿槽模型（`generation_handlers.py:371-381` vs `:669-681`）；角色名单单章按逗号分隔、批量按换行分隔（`:202` vs `:595`）。
4. **（推断）每章重算短摘要与检索词的成本问题**：Step3 每次调用 3 个 LLM（摘要/检索词/知识过滤）+1 次正文生成，前三章摘要无缓存。对长篇是稳定的 token 开销；mo-shu 派生视图方案（提交时更新、写作时直读）成本结构更优。
5. **（推断）百分比阈值无实证依据**：70% 字数触发扩写、重复度 20/40% 分档、继承 70/30 配比、摘要 2000 字上限等数字均为 prompt 内自造常数，无实验支撑（宪法反模式 #5 的外部标本；mo-shu 若吸收 M6/M9 理念须自行定验收标准）。
6. **（存疑）星数与活跃度**：5962★ 为任务书给定（2026-08-27），未在本次会话重测 API；最新 commit 2026-06-25 与 push 2026-08-01（任务书）之间的差异或来自 dev 分支/issue 活动，未深究。README 自述重构版在 dev 分支开发中——若后续作者需要，可对 dev 分支补一轮（存疑，未看）。
7. **（推断）`chapter_directory_parser.py` 的别名表是为容忍 LLM 输出漂移演进出来的**：文件头注释名 `chapter_blueprint_parser.py` 与实际文件名不一致（`chapter_directory_parser.py:1`），且有独立 88 行测试——（推断）曾因蓝图格式漂移导致解析失败而专项加固。此演化路径支持 M10 的「别名容错」借鉴价值。
