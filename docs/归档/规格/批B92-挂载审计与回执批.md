### 2. 加载回执机制（输入侧可见性）

**2a. 三 workflow 各 Stage/大步骤首行加回执格式**（~5 行规格写进各文件文头或方法节）：
- 格式：「📋 本步加载：{文件名列表}｜{每个一句要义}」——AI 在 Stage 开始时报告
- 落点：workflow-outline（Stage 1/2/3+终审）、volume-workflow（Phase A 单元构建/整合检验/定稿+Phase B 打磨环）、workflow-daily（D1 快速加载步天然是回执位——D1 本身就是加载步，格式化其输出即可）
- 成本：~20-30 字/Stage；**实测三期凭回执核对「声明 vs 发生」**——首次拿到触发率定量数据
- 注记：回执不是拦截——漏加载不阻断，但可见（评审/复盘可查）

**2b. `docs/治理/开发标准.md`** 补一条「方法论加载回执」纪律（三句话：每个 Stage 开始报加载清单；回执进对话不进文件；实测期凭回执登记触发率）。

### 3. 挂载守卫脚本 `scripts/check-methodology-wiring.sh`（确定性收口）

**功能**（Python 实现，输出 JSON 两列——沿用 check_outline 的 blocking/candidate 模式）：
- 扫描全部 `skills/*/references/*.md`（排除 genre-prose-cards/ 子卡目录——按文件级扫描）
- 对每个文件在「流程权威文件集」（三 workflow + chapter-core + cold-path + outline-workflow + 七 SKILL.md）中 grep 挂载引用
- **强度分级**（与静态盘点同口径）：MUST（必读/强制）> LOAD（按需/先读/加载/读取）> REF（见/链接/参考）> MENTION > DEAD（零引用）
- **blocking**：方法论文件 DEAD（零流程引用）——**新增方法论文件必须 ≥LOAD 才过**（新文件=git 新增的 .md，脚本比对 git ls-files 或维护清单）；shared-assets 副本不计 DEAD（以 source 侧判定）
- **candidate**：REF 级方法论（建议升级——不拦截）；MENTION 级（同）
- 退出码：0=通过（含仅 candidate）/1=blocking
- 已知 DEAD 白名单初值：`moshu-import/character-state-reverse`（import 逆向工程专用，流程在 import SKILL 内联——须复核后决定：有流程引用则不是 DEAD；真 DEAD 则随批处置或白名单）、`moshu-review/quality-rubric`（同上复核）——**本批随脚本一并处置三个 DEAD：outline-causality 升 MUST（改 1a）；另两个复核后处置（有内联流程引用→脚本补该文件进流程权威集；真死→删除或白名单+注释）**
- 守卫接入：`scripts/README.md` 索引 + `.github/workflows/cross-platform.yml` + `CONTRIBUTING.md`（CI 三处同步，§2.5 纪律）+ **正式回归测试** `scripts/test_methodology_wiring.py`（守护对象声明+fixture：一个 DEAD 样例触发 blocking / 一个 MUST 样例通过 / 白名单通过）

### 4. 挂载强度规则入开发标准

`docs/治理/开发标准.md` 方法论节补「挂载强度分级规则」表：
- 影响产出结构的方法论（模板/字段类）→ **必须 MUST**（流程步必读）
- 影响产出质量的方法论（参照/设计类）→ **至少 LOAD**（按需+触发条件明确）
- 纯工具查询类（起名卡/词典类）→ 允许索引级（SKILL 参考表）
- **新方法论文件入库检查**：跑 check-methodology-wiring.sh，DEAD=不准合入
