## 2. 测试分层哲学

### 2.1 SparkArc 测试纪律 5 原则（`spark-arc-studio/AGENTS.md:415-524`，代码事实）

1. **分层收口**：`server/test/architecture/` 只放长期「基础建筑测试」（守护稳定协议：三模态、工具注册真相源、Chat NDJSON 时序、流桥接、`_apply_patch`/`TokenTextSplitter` 等收口底座）；业务回归下沉到 `server/test/<领域>/`。判定口诀：只有同时满足「跨模块稳定不变量 + 直接覆盖统一 registry/facade/pipeline/protocol + 普通迭代不频繁改断言」三项才进 architecture（`:458`）。
2. **测协议，不测实现**：禁把 prompt 完整文案、DOM 细碎层级、CSS class、LLM 生成正文写成长期断言；测「事件名/形状/终态/注册表一致性/恢复回放/工具 UI 元数据」这类不变量（`:496`）。
3. **禁止真实上游依赖**：基础建筑与常规回归不得调真实 LLM/联网/远程 API/token 鉴权；用 fake/monkeypatch/内存对象/临时目录（`:426-427,499`）。
4. **失败先判因，再改测试**：测试红了禁止直接改断言变绿，先判「代码回归 / 契约有意变化 / 层级错 / fixture 过时 / 环境依赖」，只有契约有意变化或测错层级才准改测试（`:500`）。
5. **命名与位置即审查项**：`test_<能力>.py`、函数名表达「条件+预期行为」，禁用缺陷编号/「临时测试」伪装层级；评审时把「测试位置本身」作为审查项（`:461-462`）。

### 2.2 临时测试生命周期要点（`AGENTS.md:468-487`，代码事实）

- 仓库只允许两种测试状态：**临时验证**（不进正式树、用完删）与**正式回归测试**（长期守护价值、进领域目录）。
- 临时测试固定放 `/.tmp/tests/<本次任务>/`，命名 `verify_*/probe_*/inspect_*`（禁用 `test_*`/`*.spec.ts`），不得加入 pytest/Vitest/CI/coverage。
- **用完即删**，即使 `/.tmp/` 已 gitignore 也不把清理责任留给用户；结束前检查 git 状态。
- 口诀：**只回答「现在是否正常」→ 临时验证并删除；要防「以后再次坏掉」→ 才写正式回归测试。** 揭示可复发缺陷时，把核心场景**重写**为正式测试，不原样移动探针。

### 2.3 v7 里程碑出口判据实例（`webnovel-writer-v7/docs/architecture/v7-implementation-plan.md`，代码事实）

- 排程总则 #3/#4（`:26-27`）：**验收前置**——beta 的两条 CI（Windows 中文路径全链路、删 `.cache` 全量重建）在 M0/M1 就建起来「全程绿着往前走」；**每个里程碑出口判据可验证**，对应 PRD §4 验收方式或 §7 发布判据的具体条目，「不接受『做完了』」。
- M5 出口（`:156`）：干净 Windows 中文用户名环境**一条命令装出工作目录并建第一本书（CI + 手测各一）**；写章八阶段每步有宿主可调 CLI 通道，`finalize→next` 端到端可经 CLI 跑通。
- M6 出口（`:177`）：PRD §4 #15 验收——自动模式端到端 + **注入错误的恢复演练（批内污染不出批次）**。
- M7 出口（`:184`）：`/migrate` 在 **≥3 个真实 v6 项目**跑通是 7.0.0 判据；beta 判定是「用 v7 真实写一本书到 50 章」。

### 2.4 mo-shu 对照一句话

（推断）mo-shu 的测试若照搬 SparkArc 分层会偏重：mo-shu 是技能/插件产品而非大型多 Agent 后端，**最值得移植的是「临时测试用完即删 + 失败先判因再改测试 + 精确数字标存疑」三条纪律，而非照搬 architecture/领域目录树**。

## 3. 治理宪法要点

### 3.1 SparkArc AGENTS.md 值得 mo-shu 移植的 3-5 条（代码事实，节选自 `AGENTS.md`）

1. **统一收口、不复制实现**（§2）：新能力先判断能否接入现有收口点，而非新开平行管线；「大统一基建」（`_apply_patch` 统一局部替换、`TokenTextSplitter`/`SemanticChunker` 统一切分）严禁各 Agent 自写正则/`.replace()`/`split()`。
2. **三模态提示词真相源唯一**（§4.5）：`system`/`chat_system`/`pipeline_system` 是**互斥选择**而非叠加；共享片段抽 `base` 字段、产出规范走 `_get_tool_prompt_references` 挂在落盘工具上，禁「格式同 system」这类无效引用。
3. **反模式清单（§9）**：把 11 条「禁止堆屎山」写成显式红线（如临时入口不接 registry、改模型不走迁移、测试产物污染 Git 目录），每条配「正确方式」。
4. **AI 权限安全红线（§12）**：未经用户明确要求，AI 只准用只读 git 命令；**禁止把自动批准当成用户主观意图**，git 写入一律显式确认。→ 这与本轮「绝对只读」铁律同源，mo-shu 可直接照搬为仓库级约束。
5. **提交前自检清单（§11）**：8 条硬确认（接收口/无重复状态机/双端一致/走迁移/补测试/临时测试已删/写锁/无反依赖），任一为否先修架构再提交。

### 3.2 文档先行铁律（`v7-implementation-plan.md:190`，代码事实）

> 「接受的意见：先修 PRD/spec（0.6 → 0.7，走任务流程），再动代码——**文档先行是铁律**。」

配合排程原则（`:24`）「RFC 开放期只做格式不敏感的地基」：**需求/格式未收口前，不动依赖具体格式的代码；文档（PRD/spec）永远先于代码。** 这是 v7 用来防止「动一个地方其他地方全受影响」的治理手段。

### 3.3 Trellis 四件套形态（`webnovel-writer-v7/.trellis/tasks/07-03-m5-installer/`，代码事实 + 推断标注）

单任务目录里的「四件套」配合方式：

- **`task.json`**（任务元数据单，代码事实）：`id/name/title/status/priority/creator/assignee/createdAt/base_branch` 等，描述性字段可空。本任务 `status: in_progress`、`priority: P2`、`creator/assignee: codex`、`base_branch: v7`。
- **`prd.md`**（需求说明，代码事实）：三块——`Goal`（一句话目标）、`Background（已确认事实）`（**逐条列已交付/已占位/未做的源码事实**，含「M0-M4 已交付…292 测试绿」「`src/installer/index.js` 是占位空文件」「落盘用例已齐但无 CLI 通道」等）、`Requirements`（分 A/B/C… 逐条对应上游 spec 章节）。背景块的「已确认事实」写法是防「不知道现状就开工」的关键。
- **`check.jsonl`**（上下文清单，代码事实）：本应列出要加载的 spec/research 文件路径（`{"file":...,"reason":...}`），**本任务实际只有 1 行 `_example` 占位，无真实条目** → 说明该清单在本任务是「可选/未启用」状态。
- **`design.md` + `implement.md` + `implement.jsonl` + `review-m1-m5.md` + `review-probe.mjs`**（存在性为 glob 所见，内容本轮未读）：设计与实施落地记录、评审记录、评审探针脚本。

> 配合关系（推断）：`task.json` 管「谁在什么时候做哪个任务、状态如何」→ `prd.md` 管「做什么、现状已确认到什么程度」→ `check.jsonl` 管「AI 开工前要装哪些 spec 上下文」→ `design/implement.md` 管「怎么设计、怎么落地、评审是否通过」。这套「元数据 + 需求 + 上下文清单 + 实施记录」的分工，是 mo-shu 若要做任务化治理可直接照抄的最小形态。
