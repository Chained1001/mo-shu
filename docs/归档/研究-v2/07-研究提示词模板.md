## 任务

当前项目是 **mo-shu**，可能存在缺点或不完善之处。请学习参考几个比较成熟的开源项目：

- `otherMaterials/referProject/DeterminFlow-Plugins`
- `otherMaterials/referProject/spark-arc-studio`
- `otherMaterials/referProject/webnovel-writer-v7`

学习它们的流程、架构、思想、方法论、上下游设计等（不限于此，见下方完整维度清单），用于优化 mo-shu，最终形成一份**给 flash 模型执行的权威实施文档**（pro 规划、flash 干活）。

**重要前提**：当前已有的规划文档是之前做的不太好（研究未落证据、子代理中途失败、结论二手转述）。所以执行顺序必须是：**先全面审计旧文档 → 再基于源码重新研究 → 最后敲定最终文档**。

## 一、研究维度清单（8 层 × 22 维度，逐项覆盖，缺一不可）

## 二、研究纪律（硬约束，违反即返工）

1. **只读红线**：参考项目绝对只读（不修改/不构建/不联网）；其 git 只允许只读命令；本仓库 git 写入必须经用户明确要求，禁止把自动批准当用户意图。
2. **每条论断必须标注证据**：源码相对路径 + 行号；严格区分「代码事实」/「（推断）」/「存疑」三档。
3. **以代码为准，README 只是入口**：禁止整段转述 README；实测类数字必须可复现（如"N 个测试全绿"须有可跑命令或明确标存疑）。
4. **版本标注**：机制必须标注属于哪个版本（v6 vs v7）、是否已被项目自身废弃——照抄淘汰方案是灾难级错误。
5. **子代理防卡死**：每个研究子代理①范围收窄到行号级清单②要求"先写骨架再逐节补充"（任何时点文件都有内容）③超时即中断重启，不等无限期。
6. **旧文档勘误**：若存在旧研究文档，研究档案末尾必须加"旧文档勘误"节，逐条列出与源码不符/过度解读/张冠李戴处。

## 三、执行流程（四个阶段）

**阶段 0：现状审计**
- 审计所有现有规划/研究文档：逐条核对"有源码依据 / 二手转述 / 过度设计 / 与现状不符 / 缺失"
- 建断言核对表（断言 → 验证源 → 结论五档：✅证实 / ❌证伪 / ⚠️部分属实 / ❓无此物 / 🔧待补）
- 同时盘点当前项目自身现状（代码级：规模/结构/P0/P1/P2 缺陷清单）

**阶段 1：源码级并行研究**
- 每路一个子代理，产出统一结构档案：项目概况 / 流程 / 架构 / 思想 / 方法论 / 上下游设计 / **可借鉴清单（分成本，每条含源码位置+落点建议）** / **不可借鉴清单（每条含理由）** / 差异定位 / 待验证问题 / 旧文档勘误

**阶段 2：交叉比对**
- 用研究档案回填断言核对表，统计：证实/证伪/归因错误/自造数字
- 结构性审计：新旧机制职责重叠、批次依赖错误、自造参数无依据、口径矛盾

**阶段 3：敲定最终文档**（面向 flash 执行，见下节）
**阶段 4：治理宪法**——仓库根 AGENTS.md：AI 权限红线（git 只读/禁把自动批准当用户意图/参考项目只读）+ 施工纪律 + 提交前自检清单 + 研究文档纪律 + 不学清单指针。

## 四、最终文档规格（flash 可独立施工）

**形态 = 总纲 + 分批复刻规格**（不是一份大文档）：

**总纲**：产品愿景 / 原则（含证据溯源原则）/ 版本路线与批次表（依赖图）/ 逐单元设计摘要（每单元：目标·来源[项目+文件]·关键决策·验收锚点）/ 兼容回滚 / 测试守卫 / 验收锚点 / 附录（学习点索引·审核结论·不学清单·拆分评估·雷区清单）。

**每批规格九件套**（flash 拿一份就能干）：
1. 目标一句话 + 前置依赖
2. 现状事实（相关文件现状+路径，flash 不用重新摸）
3. 文件级改动清单（每个文件：改什么/怎么改/注意点）
4. 新文件设计（算法级描述 + 参考实现路径）
5. 验收命令（可跑、期望输出明确）
6. 守卫与 CI（全绿标准）
7. 回滚点
8. 禁止事项（硬约束）
9. 提交规范（消息格式）

**设计标注纪律**："移植"必须给源码路径；"mo-shu 自定"必须写清验收标准——无源码依据的参数（如"240 条护栏"）一律删除或显式标注自定。

## 五、常见陷阱清单（本次实战教训，研究时逐项排查）

1. **v6/v7 版本混淆**：tag 备份、五段任务书、BM25 是 v6 机制，v7 已废弃——查清版本再写设计
2. **自造数字**：把源码中无关数字当成设计参数（240 只是字符截断数，不是工单护栏）
3. **文档宣称≠代码事实**：README 的实测数据（如 94.5% 缓存命中）若代码无出处，降级为"文档宣称"
4. **"未接线"vs"已删除"**：翻源码注释确认（validator 是已删除，不是未接线）
5. **清单类断言最易过期**：skill 数/平台数/文件数等文档数字必须实测核对
6. **引文不精确**：引用项目原话前先 grep 原文（"200 万字必然写废设定"实为"200 万字不崩"）
7. **候选与阻断混淆**：机检候选永不拦截是纪律，设计成阻断会误伤正文
8. **AI 裁决架空作者**：参考项目的 observer/arbiter 无作者确认点是其自认弱点，移植必须补确认点
