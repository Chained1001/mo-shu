## 2. 各批详述

### B58 追踪视图按需注入 + 伏笔剧透锁

- **改什么**：① `tracking_commit.py` 的 `render_context()`（B57 已做角色两层）扩展为「点名注入清单」装配：以下一章细纲的出场顺序/本章涉及设定/活跃伏笔为确定性信号，输出本章写作上下文包——出场实体展开、活跃线索相关伏笔展开、其余仅列名（01·M4 滚动窗思想 + 05·M12 强制激活佐证）。② 注入预算闸：预算参数（mo-shu 自定，CLI 可覆盖，标注自定+验收标准）超限时按优先级降级为「仅列名/一行摘要」而非硬砍（05·M7 四件套：双口径/order 先到先得/永不裁剪项/爆表停扫 → 平移为：预算+降级序+永不裁剪项（本章承诺/上一章结尾））。③ 伏笔剧透锁：信息差/伏笔条目带「最早揭示章」且未到章 → 详情不注入，仅编号+一句白描（05·M10 delay→剧透锁映射，全章号驱动，无定时器）。④ 伏笔登记字段对照补强：细纲/信息差登记吸收「操作三态（埋设/强化/回收）+认知颠覆星级+情感基调迁移」（08·M9，与我们密疏预算/信息差同轴互补，合并即完整生命周期）。⑤ 衔接双锚核对：上一章结尾段锚与下一章细纲预注入——A 段清单缺则补一行（08·M4/M5，廉价高效）。
- **为什么**：T1 六源收敛的第一缺口；T2 把「禁止提前释放」从纪律约束升级为物理隔离。
- **挂靠**：不新开管线——扩展 render_context + chapter-core A 段消费口径；机检链不动。
- **触碰检查**：无 §6 冲突（确定性点名，非关键词扫描非 RAG）。
- **验收草案**：无细纲时行为与 B57 完全一致（向后兼容）；有细纲时注入包只含点名实体；伏笔未到揭示章的详情不出现在注入包（脚本断言）；超预算降级可复现（同输入同输出）。
- **风险**：细纲缺失字段的降级路径要三分（缺文件/空字段/坏格式——反模式 #7）。
- **裁决点**：D1 预算默认值口径（字数还是 token 近似）。

### B59 角色语声样本与称谓登记

- **改什么**：① 角色状态快照（`追踪/角色状态/{名}.md` 派生）加两个槽位：最近 5 条台词样本（D 段追踪事务从本章正文回写）+ 双向称谓表（A 称 B 用什么——关系条目，NovelForge 关系边语义，04）；② write A 段注入出场角色的语声样本与称谓，B 段写作时对照（01·M10「台词换人不变味」判据进 self-check 四问）；③ 上一章结尾段锚：核实 A 段是否已含，缺则补（04·lnw 衔接锚）；④ analyze 侧：主对标拆文的角色产物补「对话 DNA 五要素」（口头禅功能位/句长习惯/回避话题等，01·M10），进现有拆文库角色卡模板。
- **为什么**：T3——style 的统计画像管不到「说话不像他了」「A 突然改口叫全名」这类语声/称谓层漂移；百万字后是最常见的走形形态之一。
- **挂靠**：tracking schema 扩展（TRACKING_SCHEMA_VERSION bump + migrate 带备份 + 三副本同步，§3.4）+ chapter-core + analyze 现有模板。
- **触碰检查**：无 §6 冲突。
- **验收草案**：老书 migrate 后零丢失；新章 commit 后样本槽滚动更新（只保留最近 5 条）；注入包含出场角色语声段；analyze 产物含五要素。
- **风险**：schema 变更走批 3 模式拆子步；台词样本提取的确定性边界（谁算台词——用引号规则近似，标注自定）。
- **裁决点**：D2 语声样本载体与步幅：进单权威 state（建议）/ 仅派生层；**可两步走**——第一步只做称谓表+衔接锚（零 schema 成本），第二步再做台词样本槽位（migrate）。

### B60 外科式修订护栏

- **改什么**：① review 工单 schema（Findings Schema 扩展先例）加：PROBLEM 结构化陈述/保留清单（作者点名不许动的句段/事实）/字数系数；② deslop 与 review 整改执行纪律：每章改动两轮上限、保留清单逐条遵守、事实保全校验（确定性：整改后关键事实串 grep 仍在——脚本化小工具或机检候选）、整改前后字数偏离系数超限即停呈报（02·surgical-rewrite 的 skill 化版）；③ 分歧语义：多个 reviewer 意见相反时工单标「编辑决策点」单独呈报作者裁决，不并列混排（02·reader panel 分歧语义）。
- **为什么**：T4——「越改越坏」是修订环最大风险；DukeTwoCan 移植证明这套护栏是 skill 形态必需最小集。
- **挂靠**：review 现有工单机制 + deslop 现有流程 + 机检家族（事实保全校验若脚本化走 §2.5）。
- **触碰检查**：无 §6 冲突（护栏是作者裁决点的放大，不是自动连写）。
- **验收草案**：工单含新字段且旧工单可读（向后兼容）；事实保全 fixture 红/绿用例；分歧工单呈报路径可测。
- **风险**：字数系数阈值自定参数需验收标准；防止护栏本身变成流程噪音（阈值从宽起步）。
- **裁决点**：D3 事实保全校验做成机检候选还是仅流程纪律（建议：先纪律，实测痛了再脚本化）。

### B61 设定指纹与影响面

- **改什么**：build 修订工作流裁决完成后：对被修改的设定/大纲/卷纲文件计算指纹（sha256），与登记指纹比对 → 自动计算受影响章区间（正文引用了该设定的章——按 A 段点名记录反查）→ 生成复查清单进 review 工单（01·M5 `.design-hashes` 思想）。
- **为什么**：T5——正文后的设定改动目前靠人脑记哪些章要复查。
- **挂靠**：revision-workflow 现有 impact_scan + 追踪事务的「本章涉及设定」记录（B58 前就有此细纲字段）。
- **触碰检查**：无 §6 冲突（纯确定性脚本）。
- **验收草案**：改一个设定文件→受影响章清单可复现；指纹登记进 state 或独立小文件（兼容四原则：全可选增量）。
- **风险**：影响面召回依赖「本章涉及设定」字段质量——漏标则漏报（候选语义呈报，不承诺完备，文档明示）。
- **裁决点**：D4 指纹登记载体（state 内 vs 独立文件）。

### B62 数值/进阶一致性候选机检

- **改什么**：① progression 单调性候选：追踪状态中数值类字段（等级/排名/资产——按登记类型识别）新值低于旧值且正文无归因事件时输出候选（04·lnw 五账本单调性校验）；② 数值正本优先级声明：state > 细纲 > 正文回忆，写进 review 指引与 write A 段备查口径（01·四级数值正本思想的网文适配简化版）；③ 成稿长度运行时候选：正文字数 < 目标×0.7 或 > 目标×1.3 → 候选（09 号审计新增——细纲 Σ 预算是设计时约束，成稿后无检查；04·NovelForge 收尾阶梯思想）。
- **为什么**：T6——数值走形（欠款越还越多、伤势自愈、等级回退）是长篇高频硬伤，机检可确定性覆盖一部分。
- **挂靠**：check-* 家族 + candidate 语义（永不拦截）。
- **触碰检查**：无。
- **验收草案**：fixture 构造回退用例出候选、正常升级不出；误报率人工走查一批。
- **风险**：数值字段登记不全则覆盖有限——从「显式登记过的字段」起步，文档明示边界。
- **裁决点**：D5 是否纳入首批（价值依赖登记习惯，可与 B59 合批降成本）。

### B64 组件×模型档位策略

- **改什么**：① agents 模板成文默认档位表——按「任务实义」两档制收敛：创作类（narrative-writer/architect）高档、审查提取类（evaluator/researcher 等）中档，写进 setup agent 模板 frontmatter 约定与 AGENTS spawn 纪律（07·Claude-Book opus 创作/sonnet 审查 与 08·M1 五任务槽互证）。② spawn 协议补温度/档位纪律：判定类任务（评审/提取/校对）低温度、创作类高温度，以任务实际做什么为分配依据（08·M1 的名实偏差反面教训：强档配在只做簿记的槽位、正文由低档直出）。
- **为什么**：模型档位错配=质量或成本双输；两源互证这是成熟项目的标配，而我们 agent 档位目前只有零星默认（evaluator: sonnet）。
- **挂靠**：setup agents 模板 + 各 skill spawn 协议段落；agents_version bump + UPGRADING。
- **触碰检查**：无 §6 冲突（档位策略非多宿主适配——那是 CLI 平台维度）。
- **验收草案**：全部 agent 模板 frontmatter 档位有据可查；spawn 协议档位表一致性守卫（可挂 check-agent-template-rules）。
- **风险**：档位命名与宿主可用模型耦合（用相对档位语义表述，不锁具体型号）。
- **裁决点**：D8 是否引入（零新管线，纯约定+模板成本）。
- **裁决注记（2026-08-27 作者裁定：单模型环境）**：作者确认只会配置一种模型——B64 的档位表失去前提，**不施工**。降级为两条零成本注记：① spawn 协议里判定类任务（评审/提取/校对）用确定式措辞、创作类用发散式措辞（温度不可控，措辞可代偿）；② 07/08 的「组件×模型」对照表留档本研究，未来若配双模型时再启用。08 的名实偏差教训（档位须对齐任务实义）转写进 09 号审计 R 系列备考。
