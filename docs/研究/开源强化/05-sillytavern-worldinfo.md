### M2 词条来源四层 + 插入策略（"world/character/global"自动化）

- 证据：`world-info.js:4363-4476`（getCharacterLore 4363 / getGlobalLore 4415 / getChatLore 4432 / getPersonaLore 4452）；`world-info.js:4496-4513`（排序策略）；`world-info.js:4387-4400`（角色主书+附加书去重）；缓存 `world-info.js:882, 2036-2059`
- 机制：条目来源分四层——**全局选定书**（selected_world_info）、**角色绑定书**（角色卡 `data.extensions.world` + charLore 附加书）、**会话绑定书**（chat_metadata）、**人格绑定书**。四层合并时按"全局>会话>人格"去重（同一本书不会重复进入，4387-4400）。排序三策略：均混排/角色书优先/全局书优先（默认角色书优先，80 行），但**会话书永远最前、人格书次之**（4512-4513）。每书是一个独立 JSON 文件，加载走 StructuredCloneMap 缓存（读时深拷贝防误改，882）。
- mo-shu 映射：mo-shu 的设定天然分层：书级世界观（对应全局书）、角色级（对应角色书）、**某卷/某弧专属设定（对应会话书——按当前写作范围绑定，切换卷时换书）**。B57 的出场顺序分层是运行时分层；来源分层是文件组织分层，二者正交可叠加。
- 结论：**理念可学**——"卷/弧专属设定书"对应 chat lore 思想：写第二卷时第一卷的次要设定自动退场，不需要删文件。

### M3 匹配-评分-排序-注入主管线（重点问题 2）

- 证据：主入口 `checkWorldInfo` `world-info.js:4597-5163`；扫描缓冲区类 `WorldInfoBuffer` `world-info.js:199-474`；对上层返回契约 `getWorldInfoPrompt` `world-info.js:892-915`
- 机制（每次生成前执行一遍）：
  1. **建缓冲区**：最近消息按深度放 depthBuffer（250-260，上限 MAX_SCAN_DEPTH=1000，98 行）；扩展注入（ Authors' Note 等带 scan 标记的提示）进 injectBuffer（318-320, 4607-4614）；递归文本进 recurseBuffer（322-325）。
  2. **算预算**：`budget = round(world_info_budget% × maxContext) || 1`，再被绝对值 `budget_cap` 封顶（4624-4629）。
  3. **取全量条目并定序**：getSortedEntries 四层合并 + 策略排序 + 解析装饰器 + 算内容哈希（4478-4532）。
  4. **主循环**（`while(scanState)`，4654-5068）：每轮遍历全部条目过筛（禁用/触发类型/角色过滤/定时效应/递归开关/装饰器/外部激活/常驻/主键/次键），得本轮候选集；互斥组裁决 → 概率掷骰 → 预算记账；有新激活且开递归则把**新条目正文**追加进 recurseBuffer 进入下一轮；直到无新条目/预算爆/达到递归步数上限。
  5. **组提示词**：全部激活条目按 `order` 降序遍历、按 position 分拣到 8 个容器（5070-5144），随深度条目/示例条目/出口条目一并返回给提示词组装器（905-914；最终拼装在 script.js，本文件外）。
  - 防无限环三闸：递归步数上限（4656-4659）、预算爆停扫（4978 条件含 `!token_budget_overflowed`）、无新条目自然停（5019-5028）。
- mo-shu 映射：mo-shu 的 A 段设定加载是这条管线的**第一步退化版**（细纲清单→减法加载，无匹配无预算）。WI 管线的价值在 2/4/5 步：预算记账与分拣组包。mo-shu 不需要第 1 步的扫描匹配（信号是确定性的），但"选定→记账→分位置→组包"的后半程完全可复用为脚本逻辑。
- 结论：**可移植（后半程）**——匹配前半程不学，预算+分拣+组包后半程是本次研究最大收获。

### M4 评分机制（getScore：键命中计数）

- 证据：`WorldInfoBuffer.getScore` `world-info.js:428-473`；组内用途 `filterGroupsByScoring` `world-info.js:5173-5209`
- 机制：每条目得分 = 主键命中数（每键 1 分）+ 次键命中数按逻辑加权：`AND_ANY` 两分相加；`AND_ALL` 全命中才加、否则只算主键分；**NOT 类逻辑不加分**（460-470"只有正向逻辑影响分数"）。分数只在互斥组内用：同组多条目都触发时**只保留最高分组**（5188-5205），可全局开关或条目级覆盖（5176）。
- mo-shu 映射：mo-shu 信号是确定性的，"评分"天然改为**信号强度**：（推断）出场角色在细纲中被点名的次数/场次权重、伏笔的悬置章距（越接近揭示越重要）都可充当确定性"分"。不需要按键计数。
- 结论：**理念可学**——"同组竞争者按强度裁决"的思想可用确定性强度替代随机加权（见 M6）。

### M5 防误触组合拳（重点问题 3）

- 证据：次键逻辑 `world-info.js:4812-4876`；全词匹配 `world-info.js:349-360`；大小写 268-271；正则键 337-342, 2821-2846；角色过滤 4704-4731；触发类型 4695-4701；delay 666-677, 4737-4740
- 机制（按防误触强度递进）：
  1. **次键组合**（核心）：主键命中只是入场券，还要过次键逻辑。默认 `AND_ANY` = 主键 + 至少一个次键同时在场才算数（4843-4846）——单靠一个宽泛词（如"剑"）不再触发。`NOT_ANY/NOT_ALL` 是负向门：次键出现（全部出现）则**封杀**条目——用于"此场景排除该设定"。
  2. **全词匹配**：单词键用 `(?:^|\W)(键)(?:$|\W)` 边界正则（356），防"assassin"误触"ass"。**关键局限（对 mo-shu 致命）**：JS `\w` 不含汉字，汉字互相之间全部算 `\W` 边界——官方文档明示全词匹配不适用于中日文等无空格语言（文档宣称）。即：**WI 的主力防误触手段对中文正文天然失效**。
  3. **条目级扫描半径/大小写覆盖**（4032-4034）：高误触条目可单独收紧扫描深度。
  4. **角色/标签过滤**（4704-4731）：条目只属于特定角色在场的世界。
  5. **delay**（666-677）：开局 N 条消息内该条目禁止激活——防"第一句话就剧透终盘设定"。
  6. **regex 键**（2821-2846）：`/pattern/flags` 精确模式匹配，最强调词手段。
- mo-shu 映射：这印证了 mo-shu 不做关键词扫描的决策——中文场景 WI 防误触主力（全词边界）失效，剩下的手段（次键逻辑/正则）维护成本极高且不确定。mo-shu 的对应物是**确定性负向门**：（推断）细纲"本章不涉及"清单 = NOT_ANY 的确定性版；信息差登记 = 角色过滤的确定性版（"只有知情人视角才知道的事"按视角过滤注入）。
- 结论：**不学实现，学负向门思想**——"排除清单"与"归属过滤"两个概念可以进 mo-shu 的加载协议。

### M6 互斥组（inclusion group）——同主题竞争条目的唯一胜者

- 证据：`filterByInclusionGroups` `world-info.js:5269-5356`；sticky 胜者 5218-5258；组评分 5173-5209；优先胜者 5325-5329；加权随机 5332-5346；跨轮抑制 5312-5317
- 机制：同组标签（逗号分隔可多组，5272-5280）的条目同轮全部触发时，按四级裁决只留一个：① 组内有 sticky 条目→sticky 直接赢（5226-5238）；② 组评分→最高分赢（5300）；③ `groupOverride=true` 者中 order 最高者确定性赢（5325-5329，"Prioritize Inclusion"，官方文档）；④ 否则按 `groupWeight`（默认 100）**加权随机**选一（5332-5346）。此外：**往轮已激活过该组则本轮新竞争者全部出局**（5312-5317）——互斥是跨扫描轮持久的。
- mo-shu 映射：直接对应 mo-shu 的"同一设定多版本"与"同角色多状态版本"：同一角色在时间线前后有不同状态文件（B57 前的痛点）、同一地点去前/去后两版描写。mo-shu 的裁决信号是确定性的（当前章号/时间线），对应 WI 的第③级 `groupOverride` 而非第④级随机。
- 结论：**可移植（只取 ①③ 级）**——`group=角色名` + 确定性胜者规则（当前时间线版本优先），随机加权与组评分不取。

### M7 预算管理（重点问题 4）

- 证据：预算计算 `world-info.js:4624-4629`；记账与溢出 4890-4954；免预算通道 4898-4906, 4942；溢出停扫（含停递归）4942-4953, 4978；默认值 73, 81 行；老值迁移 946-948；溢出告警开关 76, 4945-4950
- 机制：
  - **两种口径**：`world_info_budget`（上下文百分比，默认 25%）换算成绝对 token，再与 `world_info_budget_cap`（绝对 token 数，0=不限）取小（4624-4629）。
  - **裁剪顺序 = 注入顺序 order**：条目在主循环里按既定序（sticky 优先，其余按排序序，4882-4887）逐条记账，**累计 token 达预算即停止再加新条目**——排序在前（order 大）的先占坑，order 小的后到者被挤掉（4942-4953）。不是逐条砍，而是"先到先得、爆表关门"。
  - **`ignoreBudget` 逃生门**：免预算条目在爆表后仍可进入（4902-4906：爆表后跳过普通条目但继续扫免预算条目）；且免预算条目自身不记账（4942 条件短路）。
  - **预算爆→整个扫描停止**（递归也停，4978）——预算是硬顶，防雪崩。
  - 记账口径细节（代码事实+推断）：跨轮累计基数 `allActivatedText` 只包含参与递归的条目正文（4961 过滤掉 `preventRecursion` 条目，仅其余条目正文在 5020-5024 进入基数），（推断）preventRecursion 条目的 token 会被后续轮记账遗漏，属实现瑕疵，不代表设计。
- mo-shu 映射：mo-shu 的 A 段加载目前无预算概念——设定多时全量塞入。（推断）可平移为"注入预算"：写前加载器按 token/字数上限工作，`order`=设定优先级（核心力量体系>次要风物>路人背景），爆表时低优先级条目自动降级为"仅列名"（比 WI 的硬砍更温和，且 mo-shu 已有 B57 列名机制）；续写状态卡=`ignoreBudget`（永不挤占）。
- 结论：**可移植**——百分比+绝对值双口径、先到先得、免预算逃生门、爆表停扫四件套都可直接进 mo-shu 设计。

### M8 递归扫描（重点问题 5）

- 证据：递归缓冲 `addRecurse/hasRecurse` `world-info.js:372-390`；全局开关 75；步数上限 82, 4656-4659；状态机 43-60；递归文本入池 5019-5025；三开关 4016-4018, 4748-4761, 4961；分级延迟 4641-4650, 5009-5014；min activations 轮不含递归缓冲 322-325
- 机制：全局开关打开时，每轮**新激活条目的正文**被追加进扫描缓冲区（5020-5024），下一轮用"聊天记录+已激活条目正文"再扫一遍——A 条目内容提到 B 条目的键，B 就被拉进来。限制五重：① `world_info_max_recursion_steps` 步数硬上限（0=不限，只受预算约束；4656-4659）；② 预算爆即停（4978）；③ `excludeRecursion`：该条目不许被递归激活（只在初始扫描可触发，4758-4761）；④ `preventRecursion`：该条目正文不进递归缓冲（不触发别人，4961）；⑤ `delayUntilRecursion`：条目**只能**被递归轮激活且可分级（level 2 的要等 level 1 批次激活完才解锁，4641-4650, 5009-5014）——官方文档称之 Recursion Levels，用于"条目 A 引出条目 B，B 再引出 C"的链式揭示节奏控制。注释声明 max_recursion_steps 与 min_activations 互斥（4655，代码注释；（推断）实际是步数上限先生效）。
- mo-shu 映射：mo-shu 的设定有真实依赖链（功法→境界→宗门），但 mo-shu **不需要运行时递归**：（推断）依赖链可在派生视图生成时静态展开——角色状态文件头部声明"依赖设定 X/Y"，加载器一次闭包求解，等价于"编译期递归"替代"运行时递归"，确定性可回放（符合兼容四原则的"渲染规则确定性可重放"）。`excludeRecursion/preventRecursion` 的语义对应"这条设定不因引用而连带加载/这条设定不引发二次加载"。
- 结论：**理念可学（静态闭包版）**——递归机制本身不移植，"条目依赖闭包 + 分级解锁"两个概念值得进设计。

### M9 最少激活数（min activations）——保底机制而非防误触

- 证据：`world-info.js:70-71`（默认 0）；深度推进 `advanceScan/getDepth` 395-404；循环 4991-5007；深度上限 71, 4995-4998；skew 起点语义 281-283
- 机制：设定"本次生成至少要激活 N 条 WI"后，若按常规扫描深度没凑够，引擎把扫描深度 +1 重扫（MIN_ACTIVATIONS 状态），直到凑够、或达到 `min_activations_depth_max`/聊天总长（4991-5007）。即"近处没料就往更早的聊天史里找料"。深度推进轮**不含递归缓冲**（322-325），防止递归内容自我扩大搜索范围。
- mo-shu 映射：这是"上下文保底"思想：（推断）mo-shu 反向使用——不是"最少注入"而是"最多注入"（预算）已覆盖；但其姊妹思想有用：**信号不足时的回退层级**——细纲出场清单为空时回退到"主角状态卡+活跃伏笔前 3"的保底集，保证 AI 永远有最低限度的连续性上下文。
- 结论：**理念可学**（保底集概念），机制本身不需要。

### M10 定时效应三件套（sticky/cooldown/delay）——状态在时间轴上的生命周期

- 证据：`WorldInfoTimedEffects` `world-info.js:479-793`；持久化于会话元数据 559-577；计数口径 `start=chat.length, end=start+N`（604-611）；sticky 结束自动接 cooldown（518-529）；冷却压制 4742-4745；delay 666-677；protected 标志 144, 626-629
- 机制：以**消息条数**为时钟，效果持久化在 `chat_metadata.timedWorldInfo`（键=`world.uid`+内容哈希防串）：**sticky**=激活后保持 N 条消息，期间免概率重掷（4916-4920）、互斥组内直接胜出；**cooldown**=sticky 结束（或手动关闭）后 N 条消息内禁止再激活（4742：`isCooldown && !isSticky` 压制——sticky 期间 cooldown 不生效）；**delay**=开局 N 条消息内不可激活。条目内容改动会使哈希失配，旧效果过期自动清理（624-639）。
- mo-shu 映射：**这是对 mo-shu 伏笔系统最有价值的单一机制**。mo-shu 已有"悬置章距"（updated_chapter 至当前章差值）但只用于告警。WI 提供了完整的状态生命周期词汇：（推断）伏笔条目带 `sticky=揭示后 N 章`（刚揭示的伏笔持续注入防前后矛盾）、`cooldown=回收后 N 章静默`（已回收伏笔退出注入且不再告警）、`delay=埋设章之前对 AI 不可见`（确定性剧透锁——终盘反转设定在揭示章之前物理上不进入上下文，这是"防 AI 无意提前回收伏笔"的硬手段）。时钟单位从"消息条数"换成"章节号"，全部确定性。
- 结论：**可移植（确定性化）**——去掉随机性后，这是伏笔/线索矩阵注入控制的现成语义模型。

### M11 注入位置枚举（position）与最终组包

- 证据：枚举 `world-info.js:855-864`；分拣 5084-5144；深度条目按 (depth,role) 分桶 5116-5128；AN 合并 5149-5153；出口条目 5129-5140；order 降序+unshift 实现块内顺序 5082-5084
- 机制：八位置——`before`（角色定义前）/`after`（角色定义后）/`ANTop/ANBottom`（作者注上下，直接改写 Authors' Note 提示，5149-5153）/`atDepth`（对话第 N 层，可选 system/user/assistant 角色——**把设定伪装成对话历史的一部分**）/`EMTop/EMBottom`（示例对话区）/`outlet`（不自动注入，等 `{{outlet::Name}}` 宏显式拉取，5129-5132）。同一位置内按 order 降序遍历+unshift，最终块内呈现为 order 升序（order 大者靠近上下文末端，官方文档："higher numbers = closer to the end = more influence"，文档宣称，与代码 5082-5084 排序一致）。
- mo-shu 映射：mo-shu 的 A 段加载产物目前是单一清单。（推断）可平移为三层注入位：**状态层**（续写状态卡+活跃角色——对应 `atDepth`，放最贴近生成点处，等效"最高权重"）、**设定层**（本章涉及设定——对应 `before`，世界观背景位）、**参考层**（对标文风样本等——对应 `after`）。深度注入（atDepth）对网文尤有意义：（推断）"上一章结尾原文"放在系统位 vs 对话位对续写连贯性影响不同，值得实验。
- 结论：**可移植**——位置分层+order 权重思想直接平移为"注入清单的分区与排序"。

### M12 装饰器与外部强制激活——确定性的两个后门

- 证据：装饰器 `world-info.js:100, 4540-4586`（`@@activate`/`@@dont_activate` 置于内容首行，`@@@` 转义）；外部激活 `world-info.js:203, 1020-1029, 411-413, 4774-4778, 5156`
- 机制：① 内容首行 `@@activate` = 该条目无条件激活（等效 constant 但写在内容里，随内容一起导入导出）；`@@dont_activate` = 永不激活（仅手动/宏引用）。② `WORLDINFO_FORCE_ACTIVATE` 事件允许**外部代码按 `world+uid` 直接点名激活任意条目**，绕过全部键匹配——扫描结束即清空（5156，一次性）。
- mo-shu 映射：**外部强制激活正是 mo-shu 路线的 WI 官方对应物**——ST 自己也承认键扫描不够用，提供了确定性旁路。（推断）mo-shu 的"细纲出场顺序→点名注入"在 WI 体系里就是 external activation；这说明 mo-shu 不做关键词扫描不是回避 WI 思想，而是选了 WI 体系内更可靠的那个入口。
- 结论：**理念可学**——确认"确定性点名激活"与键扫描并存的双轨设计；mo-shu 只取点名轨。

### M13 兼容层：四格式导入 + 双写映射（Character Card V2 字段面，重点问题 7）

- 证据：`convertCharacterBook` `world-info.js:5498-5555`；NovelAI `convertNovelLorebook` 5448-5496（`budgetPriority→order` 5468）；Risu 5403-5446（`alwaysActive→constant` 5414、`activationPercent→probability` 5425）；Agnai 5358-5401；导入分派 5731-5770；原始数据双写 `originalWIDataKeyMap` 2607-2644 + `setWIOriginalDataValue` 2676-2686

  - 条目级：`keys`（→key）、`secondary_keys`（→keysecondary）、`content`、`enabled`（→!disable）、`insertion_order`（→order）、`constant`、`selective`、`position`（仅 `'before_char'/'after_char'` 两值，ST 的 8 位置放 `extensions.position`，5517）、`comment`；`extensions` 袋装 ST 特有项（depth/probability/selectiveLogic/group/sticky/cooldown/useProbability/role/automation_id/vectorized 等，5518-5550）。条目 `id` 非规格必需，ST 缺失时回填索引（5503-5505 代码注释自证）。
  - （存疑）V3 规格差异未能联网核实（GitHub 超时）：仅从代码看 ST 对 V2/V3 卡走同一 `convertCharacterBook` 路径。
- mo-shu 映射：mo-shu 的拆书产物（moshu-analyze/import）与对标书语料如需带元数据，应学"**核心字段+extensions 袋**"结构：核心字段保持最小稳定（跨工具可交换），自定字段全进 extensions 袋且导出时保留未知键——这是跨系统设定交换的行业标准做法。双写映射表与 mo-shu 追踪系统的 schema 版本化（migrate+备份）同源。
- 结论：**可移植**（数据结构层）：`核心字段+extensions 袋+未知键保留`三原则适合 mo-shu 未来与外部拆书工具交换设定。

## 2 「按需注入」候选设计对本研究的启示（推断，均待作者定夺）

结合 mo-shu 确定性信号（细纲出场顺序 / 活跃伏笔 / 线索矩阵 / 章节号），给出三个候选方向。共同前提：**选择逻辑全部由脚本承担**（三层分工宪法：脚本做确定性），AI 只消费注入结果，作者通过细纲与元数据间接控制。

### 候选 A：条目级触发元数据 + 点名注入清单（对应 M1/M4/M12）

派生视图生成时（追踪事务 commit 时）为每个可注入单元写入触发元数据：角色状态条目带 `出场=主角|配角|背景`（B57 已有语义）、设定条目带 `依赖=[...]`、伏笔条目带 `状态=埋设|活跃|已揭示|回收 + 揭示章号`。写前 A 段由脚本读细纲出场顺序+追踪 state 产出**本章注入清单**（JSON，落在 `追踪/` 派生区）——等价于 WI 的 external activation 通道：不扫描、不猜测、可回放（兼容四原则）。触发语义上"本章出场角色展开详情"= constant+点名，"背景角色仅列名"= 预算外降级位。

### 候选 B：注入预算 + 位置分层（对应 M7/M11）

注入清单分三区并带 token/字数预算：**状态区**（续写状态卡+出场角色详情，`ignoreBudget`，永不裁剪）→**设定区**（本章涉及设定按 `order` 优先级排序，超预算时低优先级自动降为仅列名——利用 B57 既有机制做优雅降级，优于 WI 的硬砍）→**参考区**（文风样本等，最先让位）。预算口径学 WI 双口径：字数百分比 + 绝对上限取小。百万字长跑时这是上下文膨胀的主闸门。

### 候选 C：伏笔生命周期三态（对应 M10，确定性版）

伏笔条目在追踪事务中增加注入生命周期字段（全部由章号驱动，无随机）：`delay=揭示章之前对 AI 不可见`（剧透锁：终盘反转设定物理上进不了写前上下文，防 AI 提前回收）、`sticky=揭示/推进后 N 章持续注入`（防揭示段前后矛盾，N 可默认按悬置章距告警阈值）、`cooldown=回收后 N 章静默退出`（上下文瘦身）。与现有悬置章距计算天然衔接——同一份数据，从"告警信号"升级为"注入控制信号"。信息差登记可进一步做视角过滤（对应 M5 角色过滤的确定性版：仅知情人视角章节注入某线索）。

三者关系：（推断）A 是地基（元数据与清单），B 是容量闸（预算），C 是时间轴（生命周期）；可独立分批落地，A 无破坏性（纯增量字段，兼容四原则满足）。

## 4 （推断）与存疑

1. （推断）预算记账遗漏：`preventRecursion` 条目的 token 不进跨轮累计基数（4961 过滤，5020-5024 仅收其余条目），属实现瑕疵而非设计意图——mo-shu 若做预算应全量记账。
2. （推断）`min_activations` 与 `max_recursion_steps` 互斥（4655 代码注释+官方文档声明）：实际代码是步数上限先生效的优先级关系，非配置层互斥。
3. （文档宣称·二手）V2 规格字段面：GitHub spec 原文两次抓取超时（raw 与页面均失败），字段语义经第三方解析页转述；但 ST 实际读取行为以本地 `convertCharacterBook`（5498-5555）代码事实为准，二者交叉一致。
4. （存疑）V3 规格 character_book 差异未能核实（网络超时）；从本地代码看 V2/V3 走同一转换路径，无 V3 专有分支。
5. （文档宣称）`order` 越大越靠近上下文末端=影响越大：文档表述；代码事实仅支持"order 降序排序+unshift 使块内 order 升序排列"（5082-5084），"影响权重"是提示词工程解释。
6. （文档宣称）`include_names`（扫描文本带说话人名前缀）：开关在设置面（74, 926），实际拼接发生在本文件外的提示词组装层，本研究未取证其实现。
7. worldInfoBefore/After 的最终落点（相对角色定义的确切位置）由 script.js 提示词组装器决定，不在本文件内；本研究只确认返回契约（892-915）。
8. （推断）候选设计 A/B/C 的具体字段名与验收标准需按宪法"证据溯源原则"补"mo-shu 自定（含验收标准）"标注后才能进规格，本文仅给方向。
