# workflow-daily.md：逐章写作工作流（K 参数化——单章与日更统一，B95）

> **头注声明（B95）**：①本文件=**唯一正文车道**（workflow-chapter 已并入；文件名沿用 daily 为引链兼容，语义在标题与内容）；②单章差异=停靠语义并入 K（无数量意图默认 1+防失控停靠保留/日更意图 2-3/点名 N→min(N,3)）；③每章正文执行按 [chapter-core.md](chapter-core.md)（A 段分级/B 三遍法/C 机检/D 事务），本文件承载车道批次控制。

## 开场白（LIGHT 版，B89）

**仅新批次/新卷首次**进入给全表（进入条件+四 Stage 一览：D1 快速上下文加载｜D2 串行逐章写作｜D3 批末质量检查｜D4 批末收尾）；**日常续写一句话定位**（「本批第 N/M 章，Stage 4-D2 中」）——防噪音，不重复全表。

## 进入条件（K 判定规则，B95）

- 项目已有 `正文/` 和 `追踪/` 目录
- **K 判定**：无数量意图（"写/续写"默认）→ **K=1**（单章，防失控停靠语义保留）；日更意图（"日更/多写几章"）→ **K=2-3**；点名 N（"写第 N-M 章"）→ **K=min(N,3)**
- **指定写某章三落点（D1）**：N=下一章 → 顺序写 K=1；N≤已写 → 改稿（workflow-revision 问题修复路）；跳章 → 引导回顺序写
- **裸调用不进车道**：用户未明确写作意图（无"写/续写/日更/第N章"）→ 回 `SKILL.md`「裸调用与停靠点」，只展示当前进度与可选命令，避免自动写章

> **主对标书**：从 `设定/题材定位.md` 读 `主对标书`；指向当前作品时按缺失处理，缺失时按「对标书路径查找」规则（优先 `对标/`，为空回退 `拆文库/`）取字典序第一本并提示补字段（先排除同名或来源指向当前正文的 `对标/{当前书}/`）。写前资料清单/题材卡/文风召回/缺失处理/权威优先级一律按 core A 段与「写前准备契约」，本文件不另立一套。

## Stage 4-D1：快速上下文加载

> **加载回执（B92）**：D1 天然是回执位——输出格式化为「📋 本步加载：{文件名}｜{一句要义}」；只进对话不落盘，漏加载不阻断但可见。

**审查记录**：`.moshu-review/review-log`（如有）读最新未解决写作建议，转为本批约束；并查 `review_tickets.py list --project {项目根} --status open`（该脚本为 moshu-review 侧单副本，本 skill 不分发，执行时按已部署技能目录定位）——有 open 工单时按 [workflow-revision.md](workflow-revision.md)「工单处置」先闭环再开写（open 项是上轮审查留下的待修，续写前不清会让缺陷累积）。

**可选：moshu-explorer 批量加载**（已部署 moshu-explorer agent 时，部署判定见 /moshu-setup）：spawn `Agent(subagent_type: "moshu-explorer", prompt: "项目目录：{dir}\n查询类型：context_load\n查询参数：准备写第 {N} 章\n追踪状态：last_committed_chapter={上一步 check 的值}，state_revision={上一步 check 的值}")` 一次获取全部写作上下文；不可用或返回不完整时回退手动加载。

手动加载（默认方式）：**加载项与缺失处理见 core A2/A3（13 项+召回 (a)-(h)，B95 收口——车道不重复表）**；`追踪/伏笔.md`/`追踪/时间线/`/`追踪/逐章记录/` 默认不整份读取，缺旧信息按下方「旧信息查找步骤」定点查询。

**续写状态卡与追踪事务**：状态卡 7 栏（当前位置/长期约束/核心角色状态/活跃伏笔/近三章速记/下一章承诺/连贯性风险），目标 8192、上限 12288 字节。事务 schema/初始化/失败修复/边缘规则统一见 [tracking-transaction.md](tracking-transaction.md)；每章**提交一次追踪事务**，由 `scripts/tracking_commit.py` 确定性生成全部派生视图，主会话和子 agent 都不得直接改这些最终文件。**首次初始化**（state 缺失）：无正文 → `last_chapter=0` 的 init；已有正文 → `/moshu-import`「旧追踪项目迁移」（旧结构移入 `追踪/_旧追踪存档/`，不删除不参与解析）。**编号与修订号**：`check` 取 `last_committed_chapter + 1` 与 `state_revision`，逐章事务写 `expected_state_revision`；不要把完整 state 读进 prompt。

确定本轮写作范围后直接进入 Stage 4-D2，不做"是否继续"式确认。K 默认 2-3 章；用户明确说"只写1章"/"日更3章"/"逐章确认"时按用户要求调整。用户给出 N>3 时，本轮只写前 3 章并在 Stage 4-D4 进度摘要提示"剩余章节下轮继续"。仅在章节号冲突、细纲缺失、请求范围超过已有细纲、用户要求会改变大纲/追踪，或存在其他会导致写错的阻塞信息时暂停确认。

## Stage 4-D2：串行批量写作

一次加载多章细纲，但**必须在主会话内串行逐章写作**：不得把多章同时交给多个子代理并发写。长篇章节依赖上一章正文和追踪文件，并发会导致上下文断裂、追踪覆盖和标题去重失效。

**批量 continuation 规则**：进入本 Step 后，"继续"/"续写"/"日更"只表示继续当前日更批量流程。不得把这些词解释为跳过「状态筛选」或「对标模块/节奏/题材卡/文风召回」的直接正文续写；也不得在每章之间重复询问是否继续，除非用户明确要求逐章确认或出现阻塞。到达本轮 K（最多 3 章）后必须进入 Stage 4-D3/4 收尾并停止。

1. **读取写作计划**：按 **卷契约 → 当前剧情单元 → 章节细纲** 顺序确定；已写内容仍以正文与 `追踪/` 文件为准。先从 `大纲/卷纲_第X卷.md` 读取卷契约、当前剧情单元（单元ID/位置）、单元情绪引擎、本卷主推线/战果与终局底牌边界，再加载本批细纲。卷纲或细纲缺必需字段先补齐（未知写 `[待补充]`，不在内存临时推断）；已锁定卷纲不得自动改动。只把真正影响后续连续性的结果写入事务，规划推理过程不落追踪。
   - **批次定位与阶段约束**：写本批前从 `大纲/大纲.md`、卷纲与本批细纲提取：本批推进目标、本批可释放/严禁提前释放的信息、章尾钩子边界；按终局储备确认本批主推线与战果，别动用本阶段还不该解锁的终局底牌。未来揭示计划留在大纲，不写入时间线事实；只有下一章必须消费的边界才进 `## 下一章承诺`。
   - **阶段进度自检**：每批写完检查是否超前/拖慢/偏离阶段节奏；偏离时把补偿动作放入 `next_chapter_commitments`、跨多章风险放 `continuity_risks`；不得靠提前泄露后期信息强行提速。
2. **逐章执行**：每章按 [chapter-core.md](chapter-core.md) **A 段分级**（首章全量/批中轻量 A'，见 chapter-core「分级声明 B95」）走 A→B→C→D 完整一遍——**B 段按三遍法执行**（第 1 遍快写约 50% 时间 / 第 2 遍读者重读约 30% / 第 3 遍技艺打磨约 20%；批内时序见 chapter-core「批内时序 B95」）。**喜剧/吐槽/梗场景按需加载 [meme-craft.md](meme-craft.md)**（热梗手法学，B88）。**批量优化（Sanderson"写完再回头"，可选不默认，B95）**：连续写 2-3 章时可先连续完成各章第 1 遍快写，再统一逐章做第 2/3 遍；每章的 C/D 段仍在每章写完后立即执行（保持追踪事务及时性）。**批量场景与上下文隔离的关系**：隔离铁律隔离的是"建细纲的规划讨论"，**不隔离前章正文**——连续快写时后章需要知道前章写了什么（对话衔接/情绪延续），前章正文在上下文中刻意保留。批量模式下叠加下列日更专属动作：
   - **世界级意图分流**：改变世界格局的指令（天灾/势力变动/时代事件）经 `timeline_events` 落为世界事件并同步后续章节；**世界级事件必须带前置因果**，因果缺失时补中间环节或写入 `continuity_risks`。
   - **上一章欠账检查**：写本章前确认上一章无未清 blocking 毒句式（写前 hook 会自动拦；hook 不可用时对上一章跑 `node {SKILL_DIR}/scripts/check-ai-patterns.js --check --fail-on=blocking <上一章正文文件...>`）；有欠账先清，除非上一章标了 `<!-- 去味:跳过 -->`（用户显式豁免）。
   - **状态来源纪律**：不要为取状态/章号把完整 `_tracking-state.json` 加载进 prompt；缺失内容按「旧信息查找步骤」定点查询，不得用未标明来源的聊天记忆替代。
   - **久别角色交叉检查**：细纲列出的核心复用角色若不在 `## 核心角色状态`，直接读 `追踪/角色状态/{名}.md`；不存在即视为派生视图损坏（先 `check` 再修复）。`设定/角色/{名}.md` 只有静态人设，不能替代动态快照。角色重新活跃后把名字放进事务 `context.active_character_names`。
   - **moshu-explorer 召回的 gaps 分支**（`benchmark_style_load` 一次拿到 `{style_profile_path, …, gaps}` 后按此分流）：`no_benchmark` → 情绪/节奏从本书内部材料取、记「无」；`missing_primary_contract` → 停止准备按 `repair_action` 修复；`conflict`/`module_rhythm_conflict` → 按权威优先级执行、不得让文风覆盖情绪/节奏；`profile_missing`/`profile_degenerate` → 按 core A3(d) 交互提醒；`tone_match_failed` → 只用整书文风；否则原样传给 narrative-writer 的 spawn prompt（`selected_emotion_module` 必须进入情绪目标、`rhythm_reference` 进节奏、`genre_prose_card` 进题材取舍、`matched_chapter_techniques` 进文风召回指令）。写前准备记录必须保留 `gaps` 原值。**无 explorer 时**主会话按 core A3(a)-(f) 手动召回，模块/节奏缺失即 `missing_primary_contract` 停止修复。
   - **写后清零不拖到批末**：写后 hook 推回的毒句式命中当轮清零。
   - 每章写完后**立即提交一次追踪事务**：提取 `result / character_changes / foreshadow_changes / timeline_events / constraints / next_chapter_commitments`，并可选登记**信息差变化** `information_gap_changes`（字段见 [tracking-transaction.md](tracking-transaction.md)「信息差事务」；无变化不填）。事务 9 条细则（快照/退役/暗线核对/细纲失效/设定转正/章后对照）与失败三分类见 [chapter-core.md](chapter-core.md)「D4 追踪事务提交」与 [recovery-protocol.md](recovery-protocol.md)，本文件不重复。
   - **质检提示**（可选）：如需一致性检查，运行 `/moshu-review lean`；批量模式跳过，全部写完统一审查。
3. **不中断但不并发**：一章写完不问用户直接写下一章（除非逐章确认）；下一章必须读取上一章刚写入的正文和追踪更新后再开始。

**资料研究（按需）**：遇到需查证的外部事实，暂停写作，spawn `moshu-researcher` 输出到 `参考资料/`，完成后再继续。

### 旧信息查找步骤

状态摘要里没有、但本章确实需要的旧信息（20 章前埋的伏笔、久别角色当前状态、某个时间锚点），按以下顺序查找，**每一步的读取量都有上限**，不允许退化成读历史记录全文：

| 级别 | 手段 | 成本 |
|------|------|------|
| 1 | 续写状态卡已有 → 直接用 | 0 |
| 2 | 伏笔 ID 查 `grep -n "F007" 追踪/伏笔.md`；角色查 `追踪/角色状态/{名}.md`；读者认知查 `时间线/读者已知.md`，作者真相查 `时间线/作者真相.md` | 一个当前行或一个有界小文件 |
| 3 | 需要变化原因/历史时，调用 moshu-explorer 的 `foreshadow_status / character_status / timeline`（agent 不可用就直接 Grep/Read） | 只返回相关条目 |
| 4 | explorer 不可用 → `grep -R -n --include='第*.md' "F007" 追踪/逐章记录/ 2>/dev/null \| tail -5` | 只读取匹配行 |
| 5 | 仍不够 → `Read` 对应增量或埋设章正文 | 1 个紧凑增量或单章正文 |
| 6 | 全量读取所有逐章增量/正文 | **日更禁止**。只在 `/moshu-review` 或用户明确要求全面审计时 |

**查询次数限制**：单章 Stage 4-D3 和 4-4 合计超过 3 次，说明细纲没写清本章要消费哪些旧信息——一次性让 moshu-explorer 查询多项，批末口头提示细纲需补清回收项。查询结果只有在本章结束后仍影响后续时才进入追踪事务（伏笔由 `foreshadow_changes`、角色由快照、事实/认知由 `timeline_events`）；不要直接改续写状态卡某一行。

## Stage 4-D3：批末质量检查

每章的质量检查已在 Stage 4-D2 随 [chapter-core.md](chapter-core.md)「C/D 段」完成。批末只做下列**跨章**核对，不重复逐章项：

1. **标题去重检查**：汇总本轮新写章节与既有标题；同名或明显重复时，回到对应细纲和正文文件统一重命名
2. **契约与细纲双向核对**：按 `reader-contract-and-progression.md` 检查读者契约、因果权+结算权、关键节点四问、期待所有权、期待债、终局储备（透支两问）、换书债；再核对正文是否消费了细纲的内容概括五段式、情节安排多线、人物关系变化/出场顺序、行动成本（可无）/收益归属；三条写作要求兑现核对（不达标→修复）：①爽点出手前有可指认的危机/期待铺垫；②装逼/打脸/揭露章有在场配角差异化反应；③详略按目的词（爽点/卖点点展开、过渡点带过）。
3. **伏笔盘点（仅本轮增量）**：确认本批新增/推进/回收的每个 ID 在 `追踪/伏笔.md` 恰好一行当前状态，并在对应 `逐章记录/第NNN章.md` 找到本次变化；不得追加第二行历史，也不得扫描全部正文做全量伏笔审计。

批末再对本批全部落盘正文整体跑一遍 [chapter-core.md](chapter-core.md)「C 段」的确定性收尾（`check-ai-patterns.js` → `check-outline-copy.js` → `normalize-punctuation.js` → `check-degeneration.js` → `check-prose-candidates.js --prose <本章> --style 文风库/文风.md --gaps 追踪/信息差.md`（**候选永不拦截**）），确认无回潮。

推进度对账（B68b）：机检链后跑 `python skills/moshu-write/scripts/pace_meter.py --project {书根}`（呈报工具，恒退出码 0）——卷进度 vs 剧情进度背离候选随批末报告呈报作者（裁决归作者，不拦截）；细纲编号缺号列表供拆并章/补纲前核对。

> 若本步修文改变了会影响后续的事实/角色状态/伏笔/时间线/下一章承诺，必须在进入 Stage 4-D4 前为受影响章节提交 `mode=revision` 事务并通过 `check`；`delta` 要重算修订后仍成立的完整当前记录；纯措辞调整不重复提交。

## Stage 4-D4：批末收尾

**本步不再写任何追踪内容**——每章 Stage 4-D2 已完成事务。只做两项验证：

1. 对项目运行 `tracking_commit.py check`；验证 state schema、逐章记录连续/规范/未超限、续写状态卡固定 7 栏且 ≤12288 字节、全部派生视图与 state 一致。
2. 确认本批每章都有对应 `追踪/逐章记录/第NNN章.md`，每个文件 ≤3072 字节。缺失或超限时不手工补文件，回到该章事务修正并重跑 `commit`。

然后向用户口头汇报本批完成情况（章数、字数、漂移、下一批建议），不另存为文件；**汇报含产物路径**（正文/第N章*.md 与 追踪/ 更新摘要）。**滚动补纲预告（B95）**：批末 `ls`/读卷纲探测下一批细纲覆盖——当前单元剩余 ≤2 章或下单元细纲未建 → 汇报选项「现在补下一单元细纲（推荐）/下次再说」，选补即走 [outline-workflow.md](outline-workflow.md) 补纲小流程后收尾。若最新定稿章 = 当前卷卷纲末章，提示作者执行卷复盘（见 [volume-review.md](volume-review.md)）；复盘产出后可选 spawn evaluator（eval_type=structure，对象=卷末体检，B77）独立评审，报告呈报作者。若该卷为大纲登记的末卷（或作者已写 `大纲/完结宣告.md`）：建议作者宣告完结 → 跑 `tracking_commit.py final-report` 全书清账 → **告知作者 final-report 产物路径（追踪/完结清账.md）** → 完结清账评审（B77 缺口补全，可选：spawn evaluator，eval_type=reader，对象=完结清账；target_paths=追踪/完结清账.md，报告呈报作者——作者确认完结宣告前最后一道读者之眼；agent 不可用则 fallback 自评标注 Fallback）→ 按细纲「完结章」形态写终章。

> **漂移处理**：aligned = 按计划推进；adaptive = 细节适配但不改契约；structural 漂移 / 结构性漂移 = 正文已经改变卷契约、单元承诺、推进线或兑现归属，必须修正文或重规划未来章节细纲，不能只在增量里备注。下一章必须修的漂移进入 `next_chapter_commitments`，跨章风险进入 `continuity_risks`；两者都受续写状态卡上限约束，完整语义以紧凑增量和大纲为准。

## 细纲缺失补建流程

## 每章执行序（13 步，B95 自 workflow-chapter 并入）

1. **检查细纲** → core「A1 检查细纲」（缺必需字段必须先补建，不允许跳过细纲直接写作）
2. **读取上下文** → core「A2 读取上下文」（13 项清单 + explorer 快捷路径）
3. **写前准备** → core「A3 写前准备四步」（分级 A/轻量 A'，见 core「分级声明 B95」）
4. **资料研究（按需）** → core「A4」
5. **标题预检** → core「B0」
6. **第 1 遍·快写（创作帽）** → core「第 1 遍·快写」——禁止边写边改
7. **第 2 遍·读者重读（读者帽）** → core「第 2 遍·读者重读」（四查+修改）——禁止大改结构
8. **第 3 遍·技艺打磨（技艺帽）** → core「第 3 遍·技艺打磨」（五磨+修剪+字数验收）——微张力与章级钩子按需加载 [hooks-chapter.md](hooks-chapter.md)（含段落级微张力节，B99）（微张力管段间不停滑，章尾钩管翻章）
9. **钩子与爽点复核** → 并入三遍（爽点→第 2 遍、钩子→第 3 遍）
10. **元信息扫描** → core「C 段 · 正文元信息扫描」
11. **禁用词扫描** → core「C 段 · 禁用词扫描」（最毒句式速查 + banned-words 全表）
12. **更新追踪** → core「D4 追踪事务提交」（`scripts/tracking_commit.py commit`；含 `information_gap_changes` 信息差登记；失败三分类见 recovery-protocol.md）
13. **中途快照**（每连续 3 章）→ core「中途快照」

## 单章特有补充（B95 吸收自 workflow-chapter）

- **标题预检细则**（Stage 4-C5）→ core「B0」——同名/明显重复时按本章核心事件改名，同步细纲标题与正文文件名。
- **质量检查**（Stage 5，写后同轮）：core「D1-D3」（三维度 + consistency-checker 过桥 + narrative-writer 去 AI 味审查）；**S1/S2 必须显式过桥**——①已修复 ②进 `continuity_risks` ③进 `next_chapter_commitments` 三选一落盘，未判定不得进入下一章。
- **写前准备契约**（缺失文件处理/权威优先级/追踪体积）→ core「写前准备契约」；产物映射与项目结构树见 [artifact-protocols.md](artifact-protocols.md) 开头。
- **第一章专项（B91→B94 接线修复）**：本章为第 1 章首写时——**多版本开头**（2-3 版 300 字级，悬念/画面/对话切入，作者选一版续写；「直接写」跳过）+ **前 300 字打磨**（第一句三秒抓人/前 100 字画面/前 300 字知主角要什么）；日更续写跳过。
