# workflow-revision.md：改稿工作流（两路，B95）

> **两契约声明（B95，D8）**：①write 拥有全部稿件写权——文字打磨为内部无状态工序（不产生工单）；②review 永不改文只出工单（问题修复路的输入）。
> **入口路由（B95）**：**文字打磨路**——存稿章表达层不满（读感/文风/AI 味/文字打磨，无结构事实问题）；**问题修复路**——工单（`review_tickets list --status open`）或自检发现的结构/事实问题（走下方 R1-R5 级联）。
> **三遍法适用（B13 声明）**：修订章的正文修改按三遍法执行（chapter-core B 段——快写改→读者验证→技艺打磨），与新章写作共用同一方法。修订的差异在于输入（工单+原文而非细纲），方法不变。

---

## 文字打磨路（B95，deslop 收编——方法论零丢失）

> 适用：存稿章表达层不满（读感/文风/AI 味/文字打磨），无结构/事实问题。**内部分界（B95）**：第 3 遍（chapter-core）管「写得对不对味」（文风偏差/句式节奏/章首尾钩/对话动力），本路管「像不像 AI」的深度清理（去 AI 味）。

### 外科手术纪律（B60 迁移，章级整改护栏）

> 整改是外科手术不是重写：工单点哪里修哪里，保留的照旧保留，修完的事实必须还是原事实。

- **章级两轮上限**：每章整改最多两轮全局 pass；第二轮后仍有未解决问题 → 列明残留上报，不进入第三轮（段级「连续两轮无新改动→停止」继续有效，两者取更先触发）。
- **保留清单遵守**：工单 `preserve` 列出的句段/事实**逐条不动**——整改前后各 grep 一遍引文确认在位（流程纪律，不脚本化）；reviewer/write 不得自填 preserve（填写权只在作者与 `[需复核]` 转正）。
- **事实保真**：整改后对关键事实串（人名/数值/事件顺序）grep 自查，改动不得引入与追踪 state 冲突的事实——修问题不是改故事。
- **字数系数**：工单带 `length_coefficient`≠1 时，整改后字数应落在 原×系数×[0.9, 1.1]；超出即停手呈报，不硬凑。

### 改味三原则（B95 迁移自 deslop）

- **改味优先别当改错**：目标是去 AI 味（读感），不是纠错——功能性写法标 `[需复核]` 保留。
- **改最少效果最大**：只改确实损害读感且无叙事功能的问题；删除服从比例上限与字数下限。
- **过度去 AI 味保护**：不得整段删；删除前确认不丢伏笔/钩子/角色特征/情节推进/情绪承接/因果锚点；删完通读防电报体（非峰值叙述句恢复自然白话）。

### 删除优先判断链（B95 迁移自 deslop）

每条被标记项先判能否删除，再考虑润色：删掉后丢伏笔/钩子/角色/情节/必要信息/必要转折？都不丢则直接删；丢任意一项 → 保留信息进润色（只删「怎么说」的 AI 味，不删「说什么」）。删除服从比例上限与字数下限，跌破下限改降 AI 重写。

### 执行与确定性收尾（B95 迁移自 deslop）

- **去 AI 味执行（agent 调用，deslop Stage 3 迁移）**：已在 moshu-narrative-writer 子代理内 → inline 执行；未在内且已部署 → spawn `Agent(subagent_type: "moshu-narrative-writer", prompt: "项目目录：{dir}
任务描述：去AI味
检查范围：{待处理正文}
删除优先：每条 AI 味项先判能否删除——删后不丢伏笔/钩子/角色/情节/情绪承接/因果锚点的直接删，会丢才润色；删除服从比例上限与字数下限"`；agent 不存在或失败 → 主线程 inline 执行。
- 检测/润色加载 [anti-ai-writing.md](anti-ai-writing.md) 与 [banned-words.md](banned-words.md)（B95 收编后 write 侧单副本）；确定性预检/复扫/机械标点/细纲照搬四脚本在 write scripts 下。
- **自动修复轮次**：服从本章流程「机检修复预算」统一阀门 2 轮（无独立 3 轮上限——B95 收编后不再有独立 deslop 会话）。
- 报告格式：字数协议（原/修订/净变化/是否 tier 内）+修改统计（按 Gate 分桶）+修改前后对比（>30 处仅前 10+末 5）；文件模式落盘只回 ≤200 字代表性片段。

## Stage 4-R1：定位章节

1. 根据"第X章"找到文件：`正文/第{X}章_*.md`
2. 如果用户说的是章节名而非编号，用 `find 正文/ -name "*{关键词}*"` 搜索
3. 找不到时让用户确认具体章节
4. 如果用户指定段落范围（"第3-5段"/"那场打斗"/"对话部分"），记录为局部修改目标

---

## Stage 4-R2：加载上下文

加载比日常写作更多的上下文（因为修改需要理解前后衔接）：

| 序号 | 文件 | 用途 | 如果不存在 |
|------|------|------|-----------|
| 1 | `正文/第{X}章_*.md` | 待修改章节 | 必须存在 |
| 2 | `大纲/细纲_第{X}章.md` | 原始写作计划 | 跳过 |
| 3 | `正文/第{X-1}章_*.md` | 前一章（衔接） | 第1章时加载 `设定/世界观/背景设定.md` 替代 |
| 4 | `正文/第{X+1}章_*.md` | 后一章（衔接） | 末章时检查 `大纲/细纲_第{X+1}章.md`（如有）确保连续性 |
| 5 | `tracking_commit.py check` + `追踪/上下文.md` | 用工具确认唯一 state 与派生视图一致；续写状态卡提供当前连续性，不把完整 state 加入 prompt | 缺 state 时停止；已有正文项目必须经 `moshu-import` 生成标准追踪状态 |
| 6 | `设定/角色/{相关角色}.md` + `追踪/角色状态/{相关角色}.md` | 静态人设 + 动态当前快照 | 动态快照缺失时先运行 `tracking_commit.py check`，再重跑产生该状态的完整事务重建（不得从前文临时推断后直接手写快照——recovery-protocol 同口径） |

**相关角色判定**：从 `大纲/细纲_第{X}章.md` 中提取角色名。如果细纲不存在，从待修改章节正文中搜索 `设定/角色/` 目录下的角色名关键词。将角色名映射为文件名：`设定/角色/{角色名}.md`。

## Stage 4-R3：修改

1. **阅读原文**：读完整章内容，记录原始字数
2. **备份原文**：将原文复制为 `正文/第{X}章_章名_原稿_{YYYYMMDD}.md`，确保可回退
3. **确认修改范围**：问用户是"全文重写"还是"修改特定段落"
   - 全文重写：基于细纲重新写，保留备份
   - 局部修改：只改指定段落（按场景序号或关键词定位），保持其他部分不变
4. **执行修改**：改写文件
5. **字数对比**：修改后与原文字数差异 > 30% 或 > 800 字时提醒用户（取较大值）

**资料研究（按需）**：如果修改涉及需要验证的外部事实（历史年代、地理方位、职业细节等），spawn `moshu-researcher` agent 搜索验证。

## Stage 4-R4：级联检查

修改完成后，用一次 `mode=revision` 追踪事务完成级联更新，协议见 [tracking-transaction.md](tracking-transaction.md)：

1. **重算修订章增量**：对比旧正文/旧增量与新正文，只保留新版本对未来仍有效的 `result / 角色变化 / 伏笔变化 / 时间与揭示 / 约束 / 下一章承诺`。事务工具整份重写 `追踪/逐章记录/第{X}章.md`，不保留被新正文推翻的结论。
2. **伏笔当前值**：对受影响 ID 从第 X 章检查到最后已写章 M，提交修订后的**截至 M 章当前状态**。若修订删除了埋设，但后文仍引用该 ID，先列为正文冲突，不能简单删除；确定整条线不存在时才用 `action=delete`。`伏笔.md` 始终每 ID 一行，不追加修订历史。
3. **时间与读者认知**：为受影响事件提交客观事实、读者截至 M 章的当前认知、实际揭示状态/章节；删掉的事件用 `action=delete`。未来揭示计划仍留大纲。工具把事件合并进 `_tracking-state.json` 并重建作者/读者视图，禁止分别手改。
4. **角色当前快照**：对受影响核心角色从 X 检查到 M，按身份、位置、目标、能力资源、关系对象、已知信息、未结事项分别重算，提交一份截至 M 的完整快照；不得用最后一条单维度变化覆盖其它维度。
5. **导入截止范围**：若 X ≤ `_tracking-state.json.imported_through_chapter`，事务为第 X 章新增覆盖记录；导入截止章不变，当前结构化状态按修订结果更新。
6. **提交与重试**：把修订开始时 `tracking_commit.py check` 返回的 `state_revision` 写入 `expected_state_revision`，再执行 `tracking_commit.py commit`；若期间状态已变化，重新读取当前状态并重构事务。任一步骤失败时保留原事务 JSON，修正写入环境后重跑同一 `commit`；成功并通过 `check` 前禁止继续修下一章或写新章。失败分类与恢复动作见 [recovery-protocol.md](recovery-protocol.md)。
7. **后续影响**：如果修改改变了角色状态/关系/世界观设定，扫描后续章节正文标记受影响项：

```
⚠️ 修改第{X}章后，以下章节可能需要同步调整：
- 第{X+1}章：{原因}（建议检查）
- 第{X+3}章：{原因}（建议检查）
```

8. **正文元信息扫描**：按 [chapter-core.md](chapter-core.md)「C 段 · 正文元信息扫描」执行（标题行外不得出现 `第[一二三四五六七八九十百千万两0-9]+章|上一章|上章|前一章|本章|这一章|前文|后文|伏笔|细纲|读者` 工程词；故事内真实阅读/讨论“第X章”或真实读者身份语境除外）
9. **禁用词扫描**：按 [chapter-core.md](chapter-core.md)「C 段 · 禁用词扫描」执行，并运行 `tracking_commit.py check` 验证 state 与全部派生视图一致

## 工单处置（存在审查工单时）

1. **读工单**：`review_tickets.py list --project {项目根} --status open`（该脚本为 moshu-review 侧单副本，本 skill 不分发，执行时按已部署技能目录定位）——**这是待办的唯一读点**（工单文件可能按分钟戳存在多份，人工挑"最新文件"会漏掉别份里仍 open 的项）；只处理 `open` 项，工单缺失时跳过本节。
2. **逐条处置**：fixed / dismissed 均需一句证据（`status_note`）：`review_tickets.py resolve --project {项目根} --ticket <文件> --id T001 --status fixed|dismissed --note "<证据一句>"`（脚本归属同前条：moshu-review 侧单副本）。**不得绕过 resolve 手工编辑工单 JSON**——status 只允许 open→fixed/dismissed 单向流转。
3. **复审**：全部 open 项处置后重跑 review（`/moshu-review`），只验证工单内 open→fixed 项是否真的修好；复审通过后本轮工单闭环。

### 重听批评（Burroway Ch.9 :6929-6935，处置工单时）

处置审查工单时**听诊断不听建议**：工单里「哪里读不下去/哪里不信/哪里逻辑断」是诊断（真信息，逐条核实改）；工单给出的「怎么改」是解决方案——「一旦薄弱环节被指出，作者几乎总能想出比读者建议好的解决办法」，拿到诊断后自己设计修改。**一遍集中修一个维度**（结构→场景→对话→文字），多维并改无法判断哪刀起了作用。

## Stage 4-R5：质量检查

对修改后的章节执行 Stage 5 质量检查（至少包含）：

1. **禁用词扫描**：如 Stage 4-R4 未覆盖全章，再次扫描
2. **正文元信息扫描**：同「级联检查」中的「正文元信息扫描」，确认覆盖全章。
3. **人物一致性**：修改后的角色行为是否与角色设定一致
4. **节奏检查**：修改是否破坏了章节节奏

> 完整检查清单见 [chapter-core.md 的「D 段」质量检查与确定性收尾](chapter-core.md)。

## 常见问题

| 问题 | 处理 |
|------|------|
| 用户没说改哪里 | 问"你想改哪一章？哪方面？情节/节奏/对话/描写？" |
| 修改后字数暴增/暴减 | 提醒用户，由用户决定是否调整 |
| 连续改多章 | 逐章修改，每章独立执行 Stage 4-R2~4-5 |
| 改完发现后续不一致 | 列出受影响章节，由用户决定是否现在修改 |
